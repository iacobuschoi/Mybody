# InBody 사진 수집 파이프라인 설계 (Photo → Structured Numbers)

**문서 범위:** Mybody 앱의 "인바디 사진 넣기" 단계 전체 — 촬영/업로드부터 검증된 숫자가 플래너에 들어가기 직전까지. 이번 단계(프로토타입)에서 실제로 구현할 것과, v1/v2에서 붙일 것을 분리해서 기술한다.

**전제:** 프로토타입은 정적 파일(단일 HTML + vanilla JS), 빌드 없음, 네트워크 호출 없음, 데이터는 localStorage. 모든 화면/팝업/버튼에 고유번호 배지.

---

## 0. 요약 (읽을 시간이 없다면)

> **구현 상태 (2026-09).** 아래 3층이 전부 들어갔다. 0층과 1층은 의존성 0,
> 네트워크 0으로 돌고, 2층은 사용자가 설정에서 직접 켜야 돈다. 0층과 1층만으로
> 앱은 완성이다 — 2층은 타자를 줄여줄 뿐이다.

| 층 | 하는 일 | 파일 | 켜짐 |
|---|---|---|---|
| **0층** | 사진을 띄워 놓고 숫자 세 개를 손으로 넣는다 | `photo.js`, `screens/upload.js` | 항상 |
| **1층** | 넣은 값을 결과지 안의 다른 값과 검산한다 | `crosscheck.js`, `screens/review.js` | 항상 |
| **2층** | 서버가 사진을 읽어 초안을 만들어 준다 | `sync.js`, `server/ocr.js` | 꺼짐(기본) |

| 항목 | 결론 |
|---|---|
| 브라우저 OCR(tesseract.js)은? | **안 쓴다.** 손에 든 사진 조건에서 31건 중 0건, 13건 중 0건. 모델 파일만 10~15MB. |
| 2층 구현 | **Vision LLM (Claude) + 도구 강제(JSON Schema)**, 자가호스팅 서버가 프록시 |
| 왜 CLOVA/Google OCR이 아닌가 | 어려움은 글자를 알아보는 데 있지 않고 "한 줄의 숫자 일곱 개 중 어느 것이 값인가" 에 있다. 눈금 미끼(`골격근량 28.1 kg \| 55 70 85 100 115 130`)를 글자 인식기는 구분할 방법이 없다. |
| 비용 | 스캔 1건당 약 $0.03~0.04 (Opus 5 기준). 월 4회면 연 $2 미만. 서버가 사람당 하루 횟수를 막는다(`OCR_PER_DAY`, 기본 40). |
| 절대 빼면 안 되는 것 | **검토/수정 화면(P04)** — 선택이 아니라 필수 게이트 |
| 항상 존재해야 하는 것 | **수동 입력 경로** — OCR은 편의기능, 수동이 바닥(floor) |
| 개인정보 | 건강정보 = 민감정보. 사진은 기기에만 저장. 2층을 켜고 판독 버튼을 누를 때만 나간다. |
| OCR 신뢰도 점수는? | **안 쓴다.** 맞은 값 24.8 에 14점, 틀린 값 19.3 에 39점을 줬다. 화면의 점은 이제 **검산 상태**(검산됨/미검산/모순)다. |

핵심 원칙 3가지:
1. **플래너가 실제로 필요한 숫자는 5개뿐이다** — 측정일시, 체중, 골격근량(SMM), 체지방량(BFM), (프로필의) 신장. 나머지는 전부 보너스. 파이프라인 신뢰도는 이 5개로만 평가한다. 0층이 묻는 것도 정확히 이 셋 + 날짜다.
2. **추출기는 절대 값을 말없이 고치지 않는다.** 검증기는 "의심"과 "제안"만 만들고, 확정은 사람이 한다.
3. **추출기와 검증기는 분리된 순수 함수다.** 추출기는 통째로 교체돼도(사람 손 ↔ 서버) `crosscheck.js` 는 그대로다.

## 1. 인바디 결과지의 실물 구조

### 1.1 기기/출력물 종류

| 구분 | 출력 형태 | 특징 | 수집 난이도 |
|---|---|---|---|
| **InBody 270** | A4 컬러 또는 **감열지 영수증(58/80mm)** | 헬스장·약국 보급형. 항목 수가 적음. 영수증 인쇄가 압도적으로 흔함 | 높음 (감열지) |
| **InBody 370 / 370S** | A4 결과지 | 270 + 세포외수분비, 부위별 체수분 등 추가 | 중 |
| **InBody 570** | A4 결과지 | 체수분 분석(ECW/TBW), 내장지방 관련 항목, BMR 상세 | 중 |
| **InBody 770** | A4 결과지 (항목 밀도 최고) | 의료용. 부위별 세포외수분비, 위상각, 영양평가까지 | 중 (글자 작음) |
| **InBody Dial / H20N / 앱 스크린샷** | 휴대폰 화면 캡처 | 텍스트 선명, 레이아웃 완전 다름 | 낮음 (단, 별도 레이아웃) |
| **타사(Accuniq, Tanita 등)** | 자체 양식 | 항목명은 유사하나 배치 다름 | 높음 |

> 참고: 모델별 정확한 항목 유무(예: 내장지방레벨 VFL이 270에 있는지, 내장지방면적 VFA가 570에만 있는지)는 펌웨어/결과지 버전에 따라 달라진다. **파서는 "이 모델이면 이 항목이 반드시 있다"고 가정하면 안 되고, "있으면 읽고 없으면 null"로 동작해야 한다.**

### 1.3 감열지(헬스장 영수증) 차이점

- 폭 58/80mm → **라벨과 값이 줄바꿈으로 분리**되는 경우가 많다 (`골격근량` / 다음 줄에 `28.1 kg`).
- 막대그래프가 `|####----|` 같은 문자 블록으로 인쇄됨 → OCR이 `#`, `|`, `l`, `1`을 섞어 읽는다.
- 항목 수 축약: 부위별 분석이 아예 없거나 % 만 있음.
- 글꼴이 도트/축약형, 소수점이 한 픽셀 점.
- **감열지는 시간·열·마찰로 바래며**, 가방에 며칠 두면 대비가 무너진다. 이게 실사용 실패의 1순위 원인.

### 1.4 OCR을 어렵게 만드는 요인 (실패 모드 카탈로그)

| # | 요인 | 증상 | 완화책 |
|---|---|---|---|
| F1 | **반사광/글레어** | 형광등 아래 코팅지 → 한 줄 통째로 하얗게 날아감 | 촬영 가이드(그림자 피해 비스듬히), 재촬영 유도 |
| F2 | **원근 왜곡/기울기** | 사다리꼴, 행 정렬 붕괴 | 4점 검출 후 perspective warp, 또는 LLM에 맡김 |
| F3 | **감열지 바램** | 저대비, 숫자 뭉개짐 | 적응형 이진화, CLAHE. 근본적으로는 "찍자마자 찍기" 안내 |
| F4 | **저조도/모션블러** | 소수점 소실 | 셔터 가이드, 재촬영 |
| F5 | **가장자리 잘림** | 측정일시나 단위가 프레임 밖 | "네 귀퉁이 다 보이게" 오버레이 프레임 |
| F6 | **소수점 소실** | `63.4` → `634` | 범위 검증에서 반드시 잡힌다 (25~250kg) |
| F7 | **눈금 숫자 미끼** ★가장 위험★ | `골격근량 28.1 kg \| 55 70 85 100 115 130` — 한 줄에 숫자 7개 | **단위 토큰 앵커링**: 라벨 오른쪽 첫 숫자 중 바로 뒤에 `kg/%/kcal`이 붙은 것만 채택. 등간격 정수 3개 이상 연속 = 축 눈금으로 판정해 제외 |
| F8 | **표준범위 괄호 미끼** | `28.1 kg (24.8~30.3)` | 괄호 안 숫자 제외 |
| F9 | **2단 편집 → 읽기 순서 붕괴** | 좌/우 컬럼이 교대로 섞인 텍스트 덤프 | bbox 기반 컬럼 분리, 또는 레이아웃을 이해하는 LLM |
| F10 | **체지방`량` vs 체지방`률`** | 한 글자 차이로 kg↔% 혼동 | 단위 검증 + PBF=BFM/체중 교차검증에서 즉시 걸림 |
| F11 | **손글씨/도장 오버레이** | 이름란에 펜 글씨 | 해당 필드만 저신뢰 처리 |
| F12 | **비인바디/구형 양식** | 라벨 자체가 다름 | 기기 감지 실패 시 → 수동 입력으로 우아하게 강등 |
| F13 | **앱 스크린샷 / 좌우반전 셀피** | 레이아웃 전혀 다름, 거울상 | 별도 프로파일, 거울상은 LLM이 대체로 처리 |
| F14 | **측정일시 누락/잘림** | 시계열이 망가짐 | EXIF 촬영일시를 prior로, 없으면 사용자에게 필수 입력 |

**파싱 황금 규칙** (LLM 프롬프트에도, 규칙 기반 파서에도 동일하게 적용):
> 값 = 라벨 토큰의 오른쪽(또는 감열지면 바로 아랫줄)에서, **단위 토큰이 바로 뒤따르고**, **괄호 안에 있지 않고**, **등간격 정수 나열(축 눈금)의 일부가 아닌** 첫 번째 숫자.

## 2. 실제 구현 선택지와 트레이드오프

### 2.1 옵션 비교표

| 기준 | (a) Vision LLM (Claude) | (b) 클라우드 OCR (CLOVA / Google Vision) | (c) 온디바이스 OCR (tesseract.js) | (d) 수동 입력만 |
|---|---|---|---|---|
| **좋은 사진 정확도** | 매우 높음 | 매우 높음 (CLOVA 템플릿 시 최고) | 중간 | 100% (오타 제외) |
| **나쁜 사진(글레어/기울기/감열지) 정확도** | **높음** — 레이아웃 의미를 이해, 눈금 미끼를 구분 | 중간 — 글자는 읽어도 "어느 숫자가 값인지"는 내가 코딩해야 함 | 낮음 | 해당 없음 |
| **미지 모델/타사 양식 대응** | **그대로 됨** (zero-shot) | 템플릿 새로 만들어야 함 | 정규식 새로 써야 함 | 그대로 됨 |
| **구현 공수** | 낮음 (프롬프트 + 스키마) | **높음** (bbox 행 그룹핑, 앵커링, 미끼 제거, 모델별 분기) | 높음 + 전처리(OpenCV.js) | 매우 낮음 |
| **유지보수** | 프롬프트 1개 | 인바디 모델 늘어날 때마다 증가 | 동일 | 없음 |
| **비용** | 스캔당 ~$0.03 (Opus 5) / ~$0.014 (Sonnet 5) | 스캔당 수 원 이하 | $0 | $0 |
| **지연시간** | 3~8초 | 1~3초 | 5~20초 (모바일) + 10~15MB 모델 다운로드 | 0초 |
| **프라이버시** | 이미지가 API로 나감 (보관 정책 확인 필요) | 이미지가 클라우드로 나감 (CLOVA는 국내 리전 = 한국인에겐 가점) | **완벽 — 기기 밖으로 안 나감** | **완벽** |
| **정적 클라이언트에서 직접 호출** | 불가 (API 키 노출) → 프록시 필요 | 불가 → 프록시 필요 | 가능 | 가능 |
| **주요 실패 모드** | **그럴듯한 환각** — 틀린 숫자를 자신 있게 반환 | 못 읽으면 빈칸(정직한 실패) | 조용한 오인식 | 사용자 이탈/귀찮음 |
| **오프라인** | 불가 | 불가 | **가능** | **가능** |

### 2.2 각 옵션 상세 메모

**(a) Vision LLM — Claude**
- 요청 형태: `image` 콘텐츠 블록(base64 또는 Files API `file_id`) + **구조화 출력** `output_config: {format: {...}}` 으로 JSON Schema 강제. (`client.messages.parse()` 헬퍼로 검증까지.) 구버전 `output_format` 파라미터는 폐기됨.
- 모델: **`claude-opus-5`** (1M 컨텍스트, $5/MTok in, $25/MTok out). 사고(thinking)는 기본 on(adaptive), 깊이는 `output_config: {effort: "medium"}` 정도면 충분. 더 싸게 가고 싶으면 `claude-sonnet-5`($2/$10)나 `claude-haiku-4-5`($1/$5)가 있으나 **모델 하향은 사용자가 결정할 일**이므로 기본은 Opus 5로 둔다.
- 이미지 토큰 ≈ (width×height)/750. 1092×1092로 리사이즈 시 ≈ 1,590 토큰.
- **스캔 1건 비용 산정 (Opus 5)**: 입력 ≈ 1,600(이미지) + 900(프롬프트/스키마) = 2,500 토큰 → $0.0125 / 출력 ≈ 900 토큰(JSON) → $0.0225 → **합계 ≈ $0.035**. 주 1회 스캔이면 **연 $1.8**. 비용은 의사결정 요인이 아니다.
- 프롬프트 캐싱: 스키마/지시문이 항상 동일하므로 system+schema 프리픽스에 `cache_control` 걸면 입력 비용 대부분이 캐시 히트가 된다 (이미지는 매번 다르므로 브레이크포인트는 이미지 **앞에**).
- **환각 방어 장치(필수)**: 필드마다 `rawText`(그 값을 읽어낸 원문 라인 그대로)를 함께 반환하게 강제 → 사람이 감사 가능. 그리고 "읽을 수 없으면 추측하지 말고 `value: null, confidence: 0`" 을 프롬프트에 명시. 이 두 가지 없이는 LLM 추출을 신뢰하면 안 된다.

**(b) 클라우드 OCR**
- **Naver CLOVA OCR**: 한국어 인식이 강하고, **템플릿 빌더**로 필드 영역을 지정해 key-value 추출을 만들 수 있다(영수증/신분증 등 문서 특화 모델 계열). "InBody 270 감열지" 템플릿을 정확히 만들면 그 양식에서는 최고 정확도. 반대로 **템플릿 밖 양식에서는 0에 수렴.** 국내 리전 = 데이터가 한국에 머문다는 점은 한국 사용자에게 설득력 있는 프라이버시 논거.
- **Google Cloud Vision (`DOCUMENT_TEXT_DETECTION`)**: 단어 단위 bbox + confidence를 주므로 행 그룹핑/앵커링을 내가 짜면 정확한 통제가 가능. 대신 §1.4의 F7~F9를 전부 직접 코딩해야 한다. 가격 저렴(대략 1,000건당 수 달러 수준, 현재 단가는 확인 필요).
- 결론: **1인용 앱에서 이 공수는 회수되지 않는다.** 다만 v2에서 "제2의 눈"으로는 훌륭하다(§2.4).

**(c) 온디바이스 OCR (tesseract.js)**
- 프라이버시 만점, 비용 0, 오프라인 가능.
- 현실: `kor.traineddata` + 감열지 + 기울어진 사진 = 실사용 불가 수준. 쓰려면 OpenCV.js로 그레이스케일 → 적응형 이진화 → 4점 원근보정 → 디스큐 전처리가 선행돼야 하고, 그래도 좋은 사진에서 필드 정확도 60~80% 체감.
- 번들 비용: wasm + traineddata 10~15MB. 정적 프로토타입 철학(빌드 없음, 가벼움)과 충돌.
- **용도**: 완전 오프라인 폴백, 또는 "이 사진이 인바디 결과지가 맞는지"만 판별하는 사전 필터.

**(d) 수동 입력만**
- 정직한 기준선. 실제 필요한 건 5개 필드 → **20~30초**. "10개 넘게 타이핑" 이 아니다.
- 100% 정확, 0원, 프라이버시 완벽, 오늘 당장 구현 가능.
- **다른 모든 옵션은 이것보다 나아야 정당화된다.** 그리고 어떤 경우에도 이 경로는 지워지면 안 된다 (사진이 없을 때, 기기가 타사일 때, 인터넷이 없을 때, 사용자가 업로드를 원치 않을 때).

### 2.3 권고

> **수동 입력을 바닥으로 깔고, 그 위에 Vision LLM(Claude `claude-opus-5`)을 v1 주력 추출기로 올린다. 검토 화면은 어떤 경로에서도 필수.**

근거:
1. **사용자가 1명, 스캔 빈도 월 1~4회.** → 비용·레이트리밋 고려 불필요. 반대로 **공수 회수가 안 되는 설계(b)는 탈락.**
2. **입력 사진의 분산이 크다.** 헬스장 감열지, 병원 A4, 폰 스크린샷이 섞인다. 템플릿/정규식 기반은 이 분산에서 무너지고, LLM은 버틴다.
3. **LLM의 유일한 치명적 약점(환각)은 이미 필요한 장치로 막힌다.** 검토 화면은 OCR 품질과 무관하게 어차피 있어야 한다(§5). 따라서 LLM 채택의 한계비용이 사실상 0.
4. **(c)는 프라이버시가 하드 요구사항이 될 때만 이긴다.** 현재는 아니며, 프록시 + 이름 마스킹 + 이미지 미보관으로 충분히 방어된다.

### 2.4 단계별 경로

| 단계 | 추출기 | 검증기 | 저장소 | 네트워크 | 목표 |
|---|---|---|---|---|---|
| **P0 (지금 — 프로토타입)** | **스텁** (가짜 지연 + 내장 샘플 3종) + 수동 입력 | **진짜 규칙 전부 구현** | localStorage | **0건** | UX·스키마·검토화면 검증받기 |
| **P1 (v1)** | Claude Vision + 구조화 출력, 서버리스 프록시(Cloudflare Worker/Vercel) 경유 | 동일 (변경 없음) | localStorage/IndexedDB | 이미지 1회 왕복 | 실사용 |
| **P2 (v2)** | LLM + (선택) CLOVA/Vision 병행 → **2중 판독 교차검증**: 두 판독이 일치하면 자동 승인 후보, 불일치하면 무조건 검토 강제 | + 교차판독 합의 규칙 | 동기화 고려 | 최대 2회 왕복 | 정확도·신뢰도 상승 |
| **P2+ (선택)** | (H) 체성분 이력 표 backfill, 온디바이스 사전 크롭/디스큐, tesseract 오프라인 폴백, 로컬 VLM | — | — | — | 편의·프라이버시 강화 |

P0→P1 전환 조건: **함수 시그니처를 바꾸지 않는 것**. `extractInBody(input, opts) → Promise<ExtractionResult>` 의 몸통만 교체된다.

## 3. 추출 계약 (Extraction Contract)

### 3.1 설계 원칙

- **필드를 생략하지 않는다.** 못 읽었으면 `{ value: null, confidence: 0 }`. 키 자체가 없으면 하류 코드가 `undefined`를 만나 조용히 깨진다.
- **모든 값 필드는 스칼라가 아니라 객체다.** 값 하나만 던지면 신뢰도·출처·원문·수정이력을 붙일 곳이 없다.
- **`rawText`는 전역과 필드 단위 양쪽에 둔다.** 전역 원문이 있으면 이미지 없이도 재파싱 가능(스키마 버그 수정 후 소급 적용).
- **추출 결과(ExtractionResult)와 확정 기록(ScanRecord)은 별개 객체다.** 추출 결과는 불변으로 보관, 확정 기록이 플래너의 입력이 된다.

### 3.2 필드 객체 (`Field`)

```jsonc
{
  "value": 28.1,            // number | string | null  — 못 읽으면 null
  "unit": "kg",             // "kg" | "%" | "kcal" | "L" | "cm2" | "level" | "point" | null
  "confidence": 0.93,       // 0.0 ~ 1.0
  "source": "llm",          // "llm" | "ocr" | "manual" | "derived" | "default" | "sample"
  "rawText": "골격근량 28.1 kg (24.8~30.3)",  // 이 값을 읽어낸 원문 라인 그대로
  "bbox": [0.31, 0.42, 0.18, 0.03],           // [x,y,w,h] 0~1 정규화, 없으면 null
  "edited": false,          // 사람이 고쳤는가
  "originalValue": null     // 고쳤다면 원래 추출값 (추출기 정확도 측정용)
}
```

**신뢰도 의미 정의 (프롬프트에 그대로 명시할 것):**

| 구간 | 의미 |
|---|---|
| `0.95 ~ 1.00` | 숫자가 선명하고, 라벨과 단위가 모두 확인됨 |
| `0.80 ~ 0.94` | 읽히지만 한 가지 불확실 요소 존재(흐림, 단위 미확인, 인접 미끼 숫자) |
| `0.50 ~ 0.79` | 추정. 자릿수나 소수점 위치에 의심이 있음 |
| `0.01 ~ 0.49` | 거의 못 읽음. 참고용 |
| `0.00` | 읽지 못함 (`value: null`). **추측 금지** |

### 3.4 확정 기록 (`ScanRecord`) — 플래너가 읽는 것

검토 확정 시점에 `ExtractionResult`에서 파생되는 얇은 객체. 플래너는 `Field` 객체를 몰라도 되게 한다.

```jsonc
{
  "scanId": "scn_…",
  "measuredAt": "2026-09-19T07:50:00+09:00",
  "weightKg": 63.4,
  "smmKg": 28.1,
  "bfmKg": 17.2,
  "pbfPct": 27.1,
  "heightCm": 169,          // 프로필에서 보충 가능
  "bmi": 22.2,
  "bmrKcal": 1385,
  "vfl": 8,
  "segmentalLeanKg": { "rightArm": 2.4, "leftArm": 2.3, "trunk": 21.9, "rightLeg": 7.6, "leftLeg": 7.5 },
  "provenance": { "engine": "claude-vision", "confirmedAt": "…", "editedFields": ["pbfPct"] },
  "extractionRef": "scn_…"   // 원본 ExtractionResult는 불변 보관
}
```

**필수 최소 집합(Minimum Viable Scan):** `measuredAt`, `weightKg`, `smmKg`, `bfmKg` + 프로필 `heightCm`. 이 5개가 확정되지 않으면 플래너를 실행하지 않는다.

### 3.5 LLM 프롬프트에 반드시 들어갈 지시 (요약)

1. 인바디 결과지 이미지에서 아래 JSON 스키마로만 답하라 (구조화 출력으로 강제).
2. **못 읽은 값은 추측하지 말고 `null` + `confidence: 0`.**
3. 각 값은 그 값을 읽어낸 **원문 라인을 `rawText`에 그대로** 담아라.
4. **막대그래프 축 눈금 숫자(55, 70, 85, 100, 115 …)와 괄호 안 표준범위는 값이 아니다.**
5. 단위를 같이 읽어 `unit`에 넣어라. 단위가 확인되지 않으면 confidence를 0.8 미만으로 내려라.
6. `체지방량`(kg)과 `체지방률`(%)을 구분하라.
7. 전체 텍스트를 읽은 순서대로 `rawText`에 덤프하라.
8. 계산하지 마라. 결과지에 인쇄된 값만 옮겨라. (파생값은 우리 검증기가 만든다.)

## 4. 검증 규칙 (Validation) — OCR 오류가 플래너를 오염시키기 전에 잡기

검증기는 **순수 함수**: `validate(extraction, { profile, previousScans }) → { status, issues[] }`. 네트워크 없음, 부작용 없음, 프로토타입에서 **진짜로 구현**한다.

### T0. 구조 검증

- 필수 키 존재 (없으면 스키마 버그 → `rejected`)
- 숫자 파싱 가능, `NaN`/`Infinity` 아님
- 단위가 기대 단위와 일치 (`weightKg.unit === "kg"`), 불일치 시 `error`
- `measuredAt` 파싱 가능, **미래 아님**, 10년 이내
- `schemaVersion` 호환

### T1. 범위 검증 (필드별, 성인 기준)

두 단계 임계값: **hard**(벗어나면 값 폐기, 필수 수정) / **soft**(경고 후 사람 확인).

| 필드 | hard 범위 | soft(흔한) 범위 | 비고 |
|---|---|---|---|
| 체중 kg | 25 ~ 250 | 40 ~ 120 | 소수점 소실(`634`)이 여기서 잡힘 |
| 신장 cm | 120 ~ 220 | 145 ~ 195 | 프로필과 대조 |
| 골격근량 SMM kg | 8 ~ 60 | 18 ~ 42 | |
| 체지방량 BFM kg | 1 ~ 120 | 5 ~ 45 | |
| 체지방률 PBF % | 2 ~ 65 | 남 8~30 / 여 18~38 | 성별 반영 |
| BMI | 10 ~ 55 | 16 ~ 35 | |
| 제지방량 FFM kg | 20 ~ 130 | 35 ~ 70 | |
| 체수분 TBW L | 15 ~ 90 | 25 ~ 50 | |
| 단백질 kg | 3 ~ 25 | 7 ~ 14 | |
| 무기질 kg | 1 ~ 10 | 2.5 ~ 5 | |
| 기초대사량 kcal | 700 ~ 3500 | 1100 ~ 2000 | |
| 내장지방레벨 | 1 ~ 30 | 1 ~ 15 | 정수 |
| 내장지방면적 cm² | 5 ~ 350 | 20 ~ 150 | |
| 복부지방률 WHR | 0.55 ~ 1.30 | 0.75 ~ 1.00 | |
| 세포외수분비 | 0.330 ~ 0.450 | 0.360 ~ 0.390 | |
| InBody 점수 | 0 ~ 100 | 55 ~ 95 | 정수 |
| 나이 | 5 ~ 110 | 15 ~ 80 | |

### T2. 내부 일관성 검증 ★가장 강력★

인바디 결과지는 **내부적으로 수식이 맞아떨어지는 문서**다. 이게 OCR 오류를 잡는 최고의 무기다.

| ID | 규칙 | 허용오차 | 잡아내는 오류 |
|---|---|---|---|
| `C1` | `FFM = 체중 − BFM` | ±0.3 kg | 셋 중 하나의 오독 |
| `C2` | `PBF = BFM / 체중 × 100` | ±0.5 %p | **체지방률 소수점 오류, 량/률 혼동** |
| `C3` | `BMI = 체중 / (신장m)²` | ±0.3 | 체중/신장 자릿수 오류 |
| `C4` | `TBW + 단백질 + 무기질 + BFM = 체중` (체성분분석 열의 정의) | ±0.5 kg | A구역 전체 검산 |
| `C5` | `TBW ≈ 0.72 × FFM` | ±10% | TBW 오독 |
| `C6` | `SMM < FFM` **그리고** `SMM / FFM ∈ [0.45, 0.65]` | — | **`33.2`를 `53.2`로 읽는 유형을 잡음 (핵심)** |
| `C7` | `Σ(부위별 근육 5부위) ≈ FFM × 0.80` | ±15% | 부위별 표 오독 |
| `C8` | 좌/우 팔 차이 ≤ 25%, 좌/우 다리 차이 ≤ 25% | — | 한쪽 자릿수 오류 (실제 좌우 비대칭은 이 정도로 안 벌어짐) |
| `C9` | `BMR ≈ 370 + 21.6 × FFM` (Katch-McArdle) | ±15% | BMR 오독 |
| `C10` | 성별별 PBF 상식: 남 3~40, 여 10~50 | — | 성별 오독 또는 PBF 오독 |
| `C11` | `체중조절 = 적정체중 − 체중` (부호 포함) | ±0.5 kg | 조절 박스 검산 |
| `C12` | VFL과 PBF의 방향 일치 (PBF 낮은데 VFL 15 = 의심) | 느슨 | info 수준 경고 |

> 실무 팁: **C2와 C6만으로 실제 OCR 오류의 대부분이 잡힌다.** 최소 구현이라면 C1~C3 + C6부터.

### T3. 스캔 간 변화량 검증 (이전 확정 스캔이 있을 때)

몸은 빠르게 안 변한다. 급격한 점프는 거의 항상 **OCR 오류이거나 남의 결과지**다.

| 필드 | 주당 경고(warn) | 주당 에러(error) | 근거 |
|---|---|---|---|
| 체중 | \|Δ\| > 2.0 kg | \|Δ\| > 5.0 kg | 수분 변동 포함해도 주 2kg이 상한 |
| 골격근량 SMM | \|Δ\| > 0.5 kg | \|Δ\| > 2.0 kg | 자연 트레이니는 월 0.2~0.5kg |
| 체지방량 BFM | \|Δ\| > 1.5 kg | \|Δ\| > 4.0 kg | |
| 체지방률 PBF | \|Δ\| > 2.0 %p | \|Δ\| > 6.0 %p | |
| 신장 | \|Δ\| > 1 cm | \|Δ\| > 3 cm | **다른 사람 결과지 신호** |
| 성별 | 변경 시 | — | 다른 사람 결과지 신호 |

부가 규칙:
- `measuredAt`이 최신 스캔보다 **과거**면 → 오류 아님, `backfill`로 표시하고 시계열에 삽입.
- `measuredAt` + `weightKg`가 기존 스캔과 동일 → **중복 스캔**. "이미 등록된 측정입니다" 모달로 병합/취소 제시.
- `imageHash` 동일 → 같은 사진 재업로드. 즉시 기존 기록으로 안내.
- 경과일이 1일 미만인데 변화가 크면 임계값을 비례 축소하지 말고 **일 단위 최소 임계**를 둔다(하루에 체중 ±1.5kg는 정상적 수분 변동).

### T4. 자릿수 오류 자동 제안 (Digit Repair Heuristic)

flag된 값 `v`에 대해 아래 변형을 시도하고, **변형 후 T1·T2를 모두 통과하는 유일한 후보**가 있으면 구체적 제안으로 올린다.

1. 소수점 한 칸 이동: `v/10`, `v*10` → `634 → 63.4`, `2.21 → 22.1`
2. 앞 두 자리 자리바꿈: `53.2 → 35.2`
3. 흔한 문자 혼동 치환: `8↔3`, `5↔6`, `1↔7`, `0↔8`, `4↔9`
4. 소수점 삽입 위치 이동: `281 → 28.1`

제안 메시지는 반드시 **이유를 붙인다**: `"체지방률 2.21% → 22.1%? (체지방량 17.2kg ÷ 체중 63.4kg = 27.1%와는 아직 다릅니다)"`

### T5. 파생 및 조정 (Derivation)

- `{체중, BFM, PBF, FFM}` 중 **정확히 하나만** 비어 있고 나머지가 서로 일관되면 계산해서 채운다 → `source: "derived"`, `confidence = min(입력들) × 0.95`.
- 두 값이 충돌하면(인쇄된 PBF vs 계산된 PBF) **둘 다 보여주고 사람이 고른다.** 자동 채택 금지.
- `heightCm`이 결과지에 없으면 프로필에서 → `source: "default"`.
- `measuredAt`이 없으면 EXIF 촬영일시 → `source: "derived"`, confidence 0.7, 그래도 **검토 화면에서 사용자 확인 필수**.

### T6. 상태 판정

```
각 검사 실패 → 관련 필드들의 confidence에 패널티(error: ×0.3, warn: ×0.7)
2개 이상의 검사에 걸린 필드 → OCR confidence와 무관하게 강제 flag

status =
  "rejected"     if  T0 실패 OR 필수 5필드 중 하나가 hard 범위 밖이며 복구 불가
  "needs_review" if  error 이슈 존재 OR 필수 필드 중 confidence < 0.85 인 것 존재 OR warn 이슈 존재
  "ok"           otherwise
```

**그러나 `status === "ok"` 여도 검토 화면은 건너뛰지 않는다** (§5 참조). "ok"는 **초록 일색 + 버튼 한 번**을 의미할 뿐이다.

## 5. 사람이 개입하는 교정 UX (Human-in-the-Loop)

### 5.1 왜 검토 화면이 "선택"이 아니라 "필수"인가

1. **OCR/LLM 오류는 눈에 띄지 않는다.** 깨진 값이 아니라 *그럴듯한 값*이 나온다. 골격근량이 28.1 대신 25.1로 들어가도 화면은 멀쩡해 보이고, 사용자는 자기가 한 번도 본 적 없는 숫자를 그대로 믿게 된다.
2. **이 숫자는 몇 주짜리 계획을 결정한다.** 체지방량이 2kg 틀리면 감량 목표와 일일 적자 칼로리가 ~200kcal 어긋나고, 골격근량이 틀리면 단백질 목표(g/kg 제지방량)와 볼륨 처방이 통째로 어긋난다. 틀린 채 4주를 보내면 사용자는 "앱이 틀렸다"가 아니라 **"내 몸이 이상하다"**고 결론짓는다. 최악의 실패 모드.
3. **검토가 비싸지 않다.** 전부 초록이면 버튼 한 번, 2초. 필수화의 비용이 사실상 없는데 얻는 것은 "사용자가 자기 숫자를 한 번은 본다"는 보장.
4. **소유권/동의의 순간이 된다.** "이건 내 스캔이고, 이 날짜가 맞다"를 사람이 확정한다. 건강 데이터 앱에서 이 체크포인트는 그 자체로 가치가 있다.
5. **추출기 품질 계측의 유일한 수단.** 사용자가 고친 필드(`edited`, `originalValue`)를 누적하면 **필드별 실측 오류율**이 나온다. 이게 있어야 나중에 "신뢰도 0.97 이상은 자동 승인" 같은 완화를 *데이터에 근거해* 결정할 수 있다. 처음부터 자동 승인하면 이 데이터가 영원히 생기지 않는다.

### 5.2 화면 구성

```
┌────────────────────────────────────────────── P11 검토·수정 ───┐
│  [STUB]  인식 결과를 확인해 주세요      ⚠ 확인 필요 2건        │
├──────────────────────────┬─────────────────────────────────────┤
│                          │  측정일시  2026-09-19 07:50  🟢 F44 │
│      [사진 뷰어]          │  체중      63.4 kg           🟢 F40 │
│   핀치 줌 / 팬            │  골격근량  28.1 kg           🟡 F41 │
│   필드 탭 시 해당         │    └ 원문: "골격근량 28.1 kg …"     │
│   위치로 확대 +           │    └ [확인] [수정]                  │
│   하이라이트 박스          │  체지방량  17.2 kg           🟢 F42 │
│                          │  체지방률  [  2.21 ] %       🔴 F43 │
│  B35 사진 다시 찍기       │    ⚠ 계산값 27.1%와 다릅니다        │
│  B37 이름 가리기 ▢        │    └ [제안값 22.1 적용] B36         │
│                          │    └ [ − ] [ + ]                    │
│                          │  ▸ 더 보기 (BMI, BMR, 부위별 …)      │
├──────────────────────────┴─────────────────────────────────────┤
│  B33 직접 입력으로 전환         B38 취소      ▶ B34 모두 맞아요  │
└────────────────────────────────────────────────────────────────┘
```

### 5.3 신호등 규칙

| 색 | 조건 | 표시 방식 |
|---|---|---|
| 🟢 초록 | `confidence ≥ 0.90` **그리고** 관련 검사 전부 통과 | 한 줄로 압축 표시, 값 탭하면 수정 가능 |
| 🟡 노랑 | `0.60 ≤ confidence < 0.90` **또는** `warn` 이슈 | 펼쳐서 표시 + `rawText` 원문 노출 + `[확인]` 체크 |
| 🔴 빨강 | `confidence < 0.60` **또는** `value === null` **또는** `error` 이슈 | **빈/강조된 필수 입력**, 제안값이 있으면 선택된 상태로 프리필 |

- 상단에 `⚠ 확인 필요 N건` 칩 → 누르면 첫 번째 빨강으로 스크롤.
- **빨강이 하나라도 남으면 `B34 모두 맞아요`는 비활성.** 노랑은 통과 가능하지만 시각적으로 "미확인" 표시가 남는다.
- 필수 5필드가 아닌 항목(부위별, 위상각 등)의 빨강은 **차단하지 않는다** — "이 항목은 비워둘게요"로 넘어갈 수 있어야 한다. 차단은 오직 플래너가 필요로 하는 필드에만.

### 5.4 수정 수단 (전부 제공)

1. **큰 숫자 입력 필드** — `inputmode="decimal"`, 소수점이 이미 배치된 상태, 탭하면 전체 선택.
2. **제안값 칩** (`B36`) — 검증기가 구체적 제안을 만들었을 때만 노출. 이유를 같이 표시.
3. **±0.1 스테퍼** — 한 자리 틀린 걸 고칠 때 키보드보다 빠름.
4. **원문 보기** — `rawText`를 작은 고정폭 글꼴로. "아 이래서 저렇게 읽었구나"가 보이면 신뢰가 생긴다.
5. **사진 확대 연동** — 필드 탭 → 뷰어가 해당 `bbox`로 팬/줌 + 박스 하이라이트. (bbox가 없으면 이 기능만 비활성, 나머지는 동작.)
6. **`B33` 직접 입력으로 전환** — "이 사진으론 못 읽겠어요". 같은 화면이 빈 수동 입력 폼으로 바뀐다 (별도 화면 아님).
7. **`B35` 사진 다시 찍기** — 촬영 가이드 모달(`M21`)을 띄우고 다시 시작. 가이드 문구: *평평한 곳에 펴놓기 / 그림자·반사 피해 약간 비스듬히 / 네 귀퉁이 모두 프레임 안에 / 감열지는 받자마자 촬영*.

### 5.5 실시간 재검증

- 값을 고칠 때마다(디바운스 250ms) **검증기를 다시 돌린다.**
- 체중을 고치면 PBF 검사(C2)와 BMI 검사(C3)가 즉시 초록으로 바뀌는 게 보인다. 이 순간적 피드백이 **"이 앱이 내 숫자를 진짜로 검산하고 있다"**는 인상을 만든다. 신뢰 구축 장치이자 디버깅 도구.
- 수정된 필드는 `source: "manual", confidence: 1.0, edited: true, originalValue: <원래값>` 으로 전환.

### 5.6 확정 직후 델타 확인

확정을 누르면 저장 전에 한 줄 요약을 띄운다:

> `지난 측정(8/15) 대비 · 체중 −1.7kg · 골격근량 +0.5kg · 체지방률 −2.1%p`

T3에 `warn`/`error`가 남아 있으면 **질문형 모달(`M24`)**로 바꾼다:

> `한 주 만에 체중이 −4.1kg 입니다. 맞나요?`
> `[맞아요, 저장]` `[수정할게요]` `[이건 다른 날 측정이에요]`

마지막 선택지가 중요하다 — 사용자가 "아 이거 지난달 결과지였네"를 여기서 고칠 수 있다.

### 5.7 저장 정책

- `ExtractionResult`(원본, 불변) + `ScanRecord`(확정) **둘 다 저장.** 나중에 파서 버그를 고치면 원본 `rawText`로 재파생할 수 있다.
- `review.editedFields`를 누적해 **필드별 교정률 대시보드**(개발용)를 만든다. 이게 §2.4 P2의 "자동 승인 완화" 결정 근거.

## 6. 개인정보 (건강 데이터)

### 6.1 이 데이터의 성격

인바디 사진에는 보통 **이름 / 회원ID / 나이 / 성별 / 측정일시 / 체성분 수치**가 함께 인쇄된다. 한국 개인정보보호법상 **건강에 관한 정보는 민감정보**이며 별도의 명시적 동의 대상이다. 1인용 개인 앱이라도 다음 이유로 동일하게 취급한다:

- 나중에 지인/가족에게 공유할 가능성이 있다.
- 헬스장 공용 출력물을 찍으면 **남의 정보가 프레임에 들어올 수 있다.**
- 건강 데이터는 유출 시 되돌릴 수 없다.

### 6.2 원칙

| 데이터 | 어디에 |
|---|---|
| 원본 이미지 | **기기에만.** 기본값: 검토 확정 후 삭제. 보관은 명시적 opt-in |
| 확정 수치 (`ScanRecord`) | 기기에만 (localStorage/IndexedDB) |
| `rawText` | 기기에만 |
| 플랜/목표 | 기기에만 |
| **v1에서 외부로 나가는 것** | **추론 시간 동안의 이미지 바이트 1건, 그뿐** |
| 이름/회원ID | 기본적으로 **추출 후 저장하지 않음**. 플래너가 쓰지 않는다 |

### 6.3 v1 프록시 요구사항 (API 키를 정적 클라이언트에 넣을 수 없으므로 필수)

프록시(Cloudflare Worker / Vercel Function)는 다음을 **반드시** 지킨다:

1. API 키는 서버 환경변수. 클라이언트에 절대 노출 금지.
2. **요청 본문(이미지) 로깅 금지.** 로그는 상태코드/지연시간/토큰수만.
3. 저장 금지 — 디스크에도, 캐시에도, 오브젝트 스토리지에도.
4. 전달 전 **EXIF GPS 등 메타데이터 제거** (클라이언트에서 canvas 재인코딩으로 한 번 더 제거하는 게 더 확실하다).
5. 응답 외 아무것도 클라이언트로 돌려주지 않음.
6. 레이트리밋 (남이 URL을 알아내도 내 지갑이 털리지 않게).

클라이언트 측 추가 방어:
- **`B37 이름 가리기` 토글 (기본 ON 권장)** — 업로드 전에 canvas에서 결과지 상단 헤더 밴드를 검은 사각형으로 덮는다. 플래너는 이름/회원ID가 전혀 필요 없다. *다만 측정일시도 같은 밴드에 있으므로, 마스킹 시 날짜를 사용자에게 직접 확인받는다.*
- 업로드 전 리사이즈(긴 변 1600px) + JPEG q0.85 → 전송량 감소, 토큰 비용 감소, 부수적으로 EXIF 제거.

### 6.4 사용자에게 무엇을 말할 것인가

업로드 **직전에**, 약관 깊숙이가 아니라 화면에서 (`M22 개인정보 안내`):

> **사진 분석 방식**
> ○ **기기에서만 처리** — 사진을 어디에도 보내지 않습니다. 숫자는 직접 입력해요.
> *(구현됨. 단 이 문구는 고정으로 박으면 안 됩니다 — 자동 판독을 켜면 거짓이 됩니다.
> 실제 코드는 `MB_SYNC.canOcr()` 을 보고 문장을 바꿉니다.)*
> ● **클라우드 분석 (정확도 높음)** — 사진이 분석 서버로 1회 전송됩니다.
>   · 전송되는 것: 사진 1장 (위치정보 제거됨)
>   · 저장: 저희 서버에 저장하지 않습니다
>   · 결과 숫자와 사진은 이 기기에만 보관됩니다
>   · 언제든 설정에서 끌 수 있어요

그리고 상시 설정으로 동일 토글 노출. **한 번 고르면 다시 묻지 않되, 언제든 바꿀 수 있어야 한다.**

> 구현 시 확인할 것: 사용하는 API 제공자의 현행 데이터 보관·학습 이용 정책(기본적으로 API 입력은 모델 학습에 쓰이지 않으며, 별도의 무보관(ZDR) 옵션이 존재한다). 이 문구는 **실제 계약 조건을 확인한 뒤** 확정할 것 — 지키지 못할 약속을 UI에 쓰면 안 된다.

### 6.5 반드시 있어야 하는 두 버튼

- **전체 내보내기** — 모든 스캔/플랜을 JSON 한 파일로 다운로드.
- **전체 삭제** — localStorage + IndexedDB + 보관 이미지 전부 지우기. 확인 2단계.

건강 데이터 앱에서 이 둘은 협상 대상이 아니다.

### 6.6 기타

- 스캔 관련 화면에는 **서드파티 스크립트 0개**, 애널리틱스 0개. CDN 폰트조차 넣지 않는다.
- 프로토타입은 **네트워크 요청이 0건**이어야 하고, 그 사실을 화면에 써 둔다:
  > ~~`이 프로토타입은 사진을 어디에도 보내지 않습니다. 모든 데이터는 이 브라우저에만 저장돼요.`~~
  > **이렇게 하지 마세요.** 이 고정 문자열이 자동 판독이 붙는 순간 거짓이 됐습니다.
  > 지금은 로그인 여부와 자동 판독 on/off 를 읽어서 문장을 만듭니다.
  이 한 줄이 없으면, 검증 피드백이 기능 얘기 대신 "이거 내 사진 어디로 가요?"로 오염된다.

## 7. 정적 프로토타입에서의 스텁 설계

> **지난 이야기.** 이 절은 "진짜 판독 없이 검토 화면을 평가하자" 던 때의 설계다.
> 지금은 0층·1층이 실제로 들어갔고 2층까지 붙었으므로, 아래 내용 중 살아 있는
> 것은 `file://` 제약(7.1)과 고유번호 예약(7.9)뿐이다. 나머지는 왜 그런 선택을
> 했는지의 기록으로 남긴다.
>
> 바뀐 것 두 가지를 적어 둔다:
> - **EXIF는 스텁이 아니다.** `photo.js` 가 APP1 세그먼트를 직접 읽어
>   `DateTimeOriginal` 을 꺼낸다(라이브러리 0개). 측정일의 공짜 prior가 됐다.
> - **내장 샘플 3종은 하나로 줄었다.** 진짜 사진을 넣을 수 있게 되면서 샘플의
>   역할이 "판독 흐름 시연" 하나만 남았다.

목표: **네트워크 0건으로, 검토 화면을 제대로 평가할 수 있을 만큼 진짜처럼 느껴지게.**

### 7.1 file:// 제약 (실전 함정)

- **ES 모듈(`type="module"`)은 `file://`에서 CORS로 막힌다.** → 클래식 스크립트(`<script src="…">`)만 쓰거나 전부 인라인.
- **`fetch('./samples.json')`도 `file://`에서 막힌다.** → 샘플 JSON은 **JS 파일 안에 인라인 리터럴**로 둔다.
- HEIC은 브라우저가 디코드 못 할 수 있다 → 실패 시 썸네일 없이 진행하고 "미리보기를 표시할 수 없어요"만 안내.
- EXIF 파싱 라이브러리 없이는 촬영일시를 못 읽는다 → **프로토타입에서는 EXIF도 스텁**. (v1에서 붙이면 `measuredAt`의 공짜 prior가 된다.)

### 7.2 추출기 인터페이스 (v1과 동일, 몸통만 교체)

```js
// extractor.js  — 이 시그니처는 v1에서 바뀌지 않는다
// input: { kind: "file"|"sample"|"manual", file?: File, sampleId?: string }
// opts:  { onProgress(stage, pct), signal }
// return: Promise<ExtractionResult>
async function extractInBody(input, opts) { … }

const EXTRACTOR = "stub";   // "stub" | "llm"
```

### 7.3 가짜 파이프라인 (지연이 "느림"이 아니라 "일하는 중"으로 보이게)

단계마다 실제 UI 상태를 만들어 둔다 — v1에서 그대로 재사용된다.

| 단계 | 표시 문구 | 소요 |
|---|---|---|
| 1 | `사진 불러오는 중…` | 200ms |
| 2 | `기울기·밝기 보정 중…` | 600ms |
| 3 | `문자 인식 중…` | 1200ms |
| 4 | `항목 추출 중…` | 700ms |
| 5 | `값 검증 중…` | 400ms |

합계 ≈ 3.1초, 각 단계에 ±20% 지터. 결정적 진행바 + 단계 라벨. **`B38 취소`가 실제로 동작해야 한다**(`AbortSignal`) — v1에서 필요한 경로다.

### 7.4 내장 샘플 3종 (원클릭, 파일 불필요)

`M20 샘플 선택` 모달에서 고른다. 셋 다 `extractInBody`를 거쳐 같은 지연·같은 검토 화면으로 들어간다. **특별 취급 없음.**

| ID | 이름 | 목적 | 심어둔 문제 |
|---|---|---|---|
| **S1** | `깨끗한 A4 (InBody 570)` | 해피 패스 | 없음. 전부 🟢, 버튼 한 번으로 확정 → "검토가 부담스럽지 않다"를 보여줌 |
| **S2** | `헬스장 영수증 (InBody 270, 감열지)` | 노랑 흐름 | 골격근량 `confidence 0.72` (rawText에 축 눈금 미끼 포함), 측정일시 일부 잘림, 부위별/VFA 항목 없음 |
| **S3** | `빛 반사 + 기울어진 사진` | 빨강 흐름 + 델타 경고 | 체지방률을 `2.21`로 오독(C2 위반 → 제안값 22.1), 체중 `null`(🔴 필수 입력), S1 대비 T3 경고 발생 |

**썸네일**: 용량을 아끼려면 실제 사진 대신 **CSS/인라인 SVG로 그린 가짜 결과지**로 충분하다 (막대그래프, 표, 한글 라벨까지). S3용으로는 그 위에 `transform: skewY()` + 흰색 그라디언트 밴드(글레어)를 얹으면 감이 온다. 파일이 가벼워지고 `file://`에서도 잘 뜬다.

### 7.5 실제 파일 업로드 경로

```html
<input type="file" accept="image/*" capture="environment">
```
- 실제 썸네일을 `URL.createObjectURL(file)`로 보여준다 (여기는 진짜).
- 그리고 **S1~S3 중 하나를 무작위로** 반환한다.
- **검토 화면 헤더에 `STUB` 칩을 반드시 표시**하고 "데모 결과입니다 — 실제 사진을 읽은 게 아니에요"를 한 줄 명시.
  → 이 정직함이 없으면 사용자가 "내 골격근량을 잘못 읽었네"라는 **무의미한 피드백**을 주게 되고, 이번 검증 라운드가 통째로 낭비된다.

### 7.6 수동 입력 경로 (일급 시민)

- 어디서든 진입 가능 (`P10`의 `B33`, `P11`의 `B33`).
- 동일한 `ExtractionResult` 객체를 만들되 모든 필드 `source: "manual", confidence: 1.0`.
- **검토 화면(`P11`)이 곧 입력 폼이 된다.** 화면을 두 개 만들지 않는다 — 코드 경로 하나, 진입점 둘.
- 필수 5개만 크게 보이고, 나머지는 `▸ 더 보기`로 접어둔다.

### 7.7 검증기는 스텁하지 않는다

`validate.js`에 T0~T5를 **실제로** 구현한다. 이유:
- 순수 함수라 싸다 (한 파일, 외부 의존성 0).
- 검토 화면이 "진짜로 검산하고 있다"고 느껴지는 유일한 이유다.
- v1에서 **한 줄도 안 바뀌고** 그대로 쓰인다. 지금 만들어두면 나중에 공짜.
- 개발용 숨김 토글로 값을 흔들어 보며 검사들이 실시간으로 뒤집히는 걸 확인할 수 있게 한다.

### 7.8 저장소

```
mybody.profile          { heightCm, gender, birthYear, ... }
mybody.scans            ScanRecord[]           (확정된 것만)
mybody.extractions      ExtractionResult[]     (원본, 불변)
```
