## 2. 측정된 오차

### 2.1 NutriBench — 검증 완료, 단 **이미지가 아니라 텍스트**

`DongXzz/NutriBench` (22★, 마지막 푸시 2025-04-10)에서 README 전문 확인.

- **논문:** *NutriBench: A Dataset for Evaluating Large Language Models on Nutrition Estimation from Meal Descriptions*
- **게재:** ICLR 2025 (2025-02-11 accept 공지)
- **저자:** Hua, Dhaliwal, Burke, Pullela, Qin
- **arXiv:** 2407.12843 (본문 접근 불가 `[미검증]`)
- **v2 (2025-04-08):** 24개국으로 확장, 식사 설명 다양성 개선
- 부가: 미국 번호 문자(+1 866-698-9328) / WhatsApp(+1 555-730-0221)로 식사 설명 보내면 탄수 추정해주는 서비스 운영 중

**README에 실린 reference result (Meta-Llama-3.1-8B-Instruct):**

| Task | Accuracy@7.5 | MAE |
|---|---|---|
| `nutribench_v2_base` | **0.3301** | **36.18** |
| `nutribench_v2_cot` | **0.3527** | **37.17** |

해석 (단위는 탄수화물 g):
- **Accuracy@7.5 = 정답 ±7.5 g 안에 든 비율.** 33~35%. **세 번 중 두 번은 7.5 g 밖입니다.**
- **MAE 36 g.** 탄수 36 g = 밥 약 2/3공기. 한 끼 추정에서 밥 2/3공기만큼 틀린다는 뜻입니다.
- CoT(생각하게 함)가 정확도를 0.3301 → 0.3527로 **아주 조금** 올리고 **MAE는 오히려 악화**(36.18 → 37.17)시켰습니다. — **"더 생각하게 하면 나아진다"가 여기선 성립하지 않습니다.**

> ⚠️ **가장 중요한 단서:** NutriBench는 **"meal descriptions"(글로 쓴 식사 설명)** 입력입니다. 사진이 아닙니다. 즉 **모델에게 "닭가슴살 200g과 현미밥 1공기"라고 이미 말해준 상태**에서도 8B 모델이 세 번 중 두 번 틀립니다. 사진은 여기에 **"무엇이 얼마나 있는지 알아내는 단계"가 하나 더 붙습니다.** NutriBench의 오차는 사진 파이프라인 오차의 **하한선(floor)** 입니다.
>
> 그리고 이건 Llama-3.1-8B 수치입니다. 프런티어 모델(Claude/GPT-4급)이 같은 벤치마크에서 얼마나 하는지는 **논문 본문에 있을 것이나 접근 불가** `[미검증]`. 8B보다 낫다는 건 거의 확실하지만, **얼마나 나은지 이 세션에서 확인하지 못했습니다.**

### 2.3 이 표가 말하는 것 — **요청하신 프레이밍이 정확히 맞습니다**

세 줄을 나란히 놓습니다:

```
재료가 뭔지 맞히기          →  F1 0.9558   (거의 풀린 문제)
양을 알려주고 칼로리 계산    →  MAE 24.1 kcal
사진만 보고 칼로리          →  MAE 70.6 kcal   ← 2.9배
```

**칼로리 오차의 약 2/3가 "얼마나 있는지"에서 나옵니다.** 질량 MAE 40.4 g이 그 원인을 직접 보여줍니다.

그리고 이건 **Google이**, **자체 제작 스캔 리그로**, **depth 센서까지 써서**, **자기네 구내식당 음식 5,006접시로 직접 학습해서** 얻은 숫자입니다. 통제된 조건의 상한선에 가깝습니다.

우리 조건은 전부 더 나쁩니다:
- depth 없음 (휴대폰 단일 RGB)
- 고정 리그 없음 (각도·거리·조명 제멋대로)
- 학습 데이터 없음 (zero-shot)
- 도메인 불일치 (구내식당 접시 vs 반상)
- **접시가 여러 개** (Nutrition5k는 한 접시, 반상은 밥+국+반찬 5종)

> **따라서: 포션 추정을 얼버무리는 어떤 추천안도 틀렸다는 지적은, 제가 찾은 증거와 정확히 일치합니다.** 그리고 이 앱은 이미 인바디 노이즈 바닥(체중 ±1.0kg / 골격근 ±0.6kg / 체지방 ±1.0kg)에서 같은 기준을 세웠습니다. 여기서만 느슨해지면 앱의 정체성이 깨집니다.

### 2.4 ★ 그런데 왜 그래도 쓸만한가 — 이 앱만의 이유

산수를 해봅니다. 한 끼 오차 70 kcal이라고 하면:

**오차가 무작위(unbiased)라면** — 하루 3끼 √3 × 70 ≈ **121 kcal/일**. 일주일이면 ±320 kcal 정도로 상쇄. 무시 가능.

**오차가 편향(biased)이라면** — 예: 밥 양을 늘 과소평가 — 3 × 70 = **210 kcal/일 = 1,470 kcal/주 ≈ 체지방 0.19 kg/주**.

**후자가 감량 계획 전체를 삼킵니다.** 주당 0.19 kg면 적당한 감량 속도의 대부분입니다. 그리고 실제 식단 기록 오차는 압도적으로 **편향** 쪽입니다(같은 음식을 같은 방식으로 늘 틀리게 추정).

**그런데 — 이 앱에는 이미 답이 있습니다.**

> `engine.js`와 P08 주간 체크인이 **실측 체중 변화로 칼로리를 재조정**합니다. 즉 이 앱은 **섭취량의 진짜 절대값이 필요 없습니다.** 필요한 건 **일관된 값**입니다.
>
> 기록이 늘 250 kcal 과소평가라면, 체크인은 "목표보다 적게 먹었다는데 체중이 안 줄었다 → 목표를 250 내린다"로 **편향을 자동 흡수**합니다. 그 다음부터 기록 대비 상대 변화는 정확해집니다.

**이게 이 앱이 식단 기록을 정당하게 할 수 있는 이유이고, 동시에 설계 제약을 만듭니다:**

1. **추정기가 바뀌면 편향도 바뀝니다.** → **모든 기록에 `source`(photo/manual/barcode)와 `model_version`을 박습니다.** 추정기가 바뀌면 체크인이 그 사실을 알아야 합니다.
2. **사진과 수동을 섞으면 편향이 흔들립니다.** → 주간 요약에 **경로별 비율**을 노출합니다.
3. **기록 안 한 날이 편향보다 훨씬 치명적입니다.** → **기록률(logging rate)이 달성률보다 위에 와야 합니다.** (§7.4)
4. **체크인 화면에서 기록 평균과 실측 역산치를 나란히 보여주는 것이 이 탭의 최종 가치입니다.** (§7.6)

### 2.5 검증하지 못한 것 (명시)

요청하신 항목 중 **확인 실패**한 것들입니다. 추측으로 채우지 않았습니다.

## 3. 패턴: 이미지 → VLM(구조화 출력) → 검수 → DB 대조

### 3.1 이미 이 리포가 내린 결론과 동일

`docs/design/photo-ingestion.md` §0을 그대로 인용합니다:

> | v1 실제 구현 | **Vision LLM (Claude, `claude-opus-5`) + 구조화 출력(JSON Schema)**, 얇은 서버리스 프록시 경유 |

**식단 사진에 이 세 줄이 전부 그대로 적용됩니다. 한 줄도 바꿀 필요가 없습니다.** 인바디 판독보다 오히려 더 강하게 적용됩니다 — 인바디는 종이에 정답이 인쇄되어 있지만, **식단 사진에는 정답이 애초에 없기 때문입니다.**

### 3.2 파이프라인

```
 촬영/선택
    ↓

```

### 3.3 "실제로 이렇게 하는 곳이 있나"

**오픈소스로는 없습니다** (§1.1). GitHub에서 찾은 건 전부 스타 한 자릿수의 Gemini/GPT 호출 래퍼이고, 구조화 스키마도 검수 게이트도 범위 출력도 없습니다 — **그냥 자유 텍스트로 칼로리를 물어보고 그대로 믿습니다.**

### 4.2 이미지 토큰 (1차 출처 검증 완료, `docs/en/build-with-claude/vision`)

공식 산식:

> Claude는 이미지를 28×28 픽셀 패치(visual token) 단위로 봅니다. 이미지 비용 = `⌈width/28⌉ × ⌈height/28⌉` visual tokens.

| 해상도 티어 | 대상 모델 | 최대 장변 | 최대 visual token |
|---|---|---|---|
| **High-resolution** | Claude 4.7 이후 | 2,576 px | **4,784** |
| Standard | 그 외 | 1,568 px | 1,568 |

문서의 예시 표:

| 이미지 크기 | Standard 토큰 | High-res 토큰 |
|---|---|---|
| 1000×1000 (1 MP) | 1,296 | 1,296 |
| 1920×1080 (2.07 MP) | 1,560 | 2,691 |
| 3840×2160 (8.29 MP) | 1,560 | **4,784** |

문서 자체의 비용 예시로 제 계산법을 검산했습니다: *"Opus 5의 $5/MTok(high-res)에서 1000×1000 이미지는 1,000장당 약 $6.48"* → 1,296 × $5/1M = $0.00648 ✓ 일치.

> **★ 설계 결정: 보내기 전에 반드시 리사이즈합니다.**
> 휴대폰 사진은 4032×3024입니다. 그대로 보내면 Opus 5에서 **4,784 토큰**(상한 직격)입니다. 장변 1024px로 줄이면 **1,036 토큰 — 4.6배 절감**이고, 음식 판별·양 추정에 필요한 정보는 손실되지 않습니다(글자를 읽는 작업이 아니므로). 부수 효과로 **업로드 지연과 프라이버시 노출도 같이 줄어듭니다.**
> `1024×768 → ⌈1024/28⌉ × ⌈768/28⌉ = 37 × 28 = 1,036 visual tokens`

### 4.3 사진 1장당 비용

가정 (보수적):
- system(고정 규칙 + 스키마 + 한국 식기 기준표) ≈ **1,200 tok**
- 사용자 보정 이력 카드 ≈ **300 tok**
- 이미지(1024×768) = **1,036 tok**
- 출력 JSON(요리 3~5개, 범위 포함) ≈ **400 tok**
- thinking(adaptive, `effort: "low"`) ≈ **500 tok** (출력으로 과금)

| 모델 | 입력 비용 | 출력 비용 | **1장 합계** |
|---|---|---|---|

> 이 $0.035는 같은 리포의 `photo-ingestion.md`가 인바디 스캔에 대해 추산한 **"$0.03~0.04 (Opus 5 기준)"** 와 일치합니다. 독립적으로 재계산해서 같은 자리에 떨어졌습니다.

### 4.5 ⚠️ 프롬프트 캐싱은 여기선 소용없습니다 (흔한 착각)

- 캐시 가능한 최소 prefix는 모델별로 **512~4,096 토큰**입니다. 우리 system(≈1,200 tok)은 **Opus에서 최소치 아래일 수 있습니다.**
- 더 결정적으로: **5분 캐시 TTL vs 식사 간격 5시간.** 끼니 사이엔 무조건 미스입니다.
- 1시간 캐시는 쓰기가 **2배 가격**인데 그래도 아침→점심 사이를 못 넘깁니다.
- **결론: 캐싱 설계하지 마세요. 순손해입니다.** (한 끼에 여러 장을 연속으로 찍는 경우만 5분 캐시가 이득 — 그건 그때만 켜면 됩니다.)

## 5. 프롬프트와 스키마 설계

### 5.1 강제할 필드 — `portion_basis`가 핵심 발명

```jsonc
{
  "type": "object",
  "additionalProperties": false,
  "required": ["photo_quality", "meal_type_guess", "dishes",
               "unidentifiable_regions", "overall_caveat"],
  "properties": {
    "photo_quality": { "enum": ["good", "poor", "unusable"] },
    "meal_type_guess": { "enum": ["집밥","외식","배달","편의점","구내식당/학식","불명"] },

    "dishes": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["name_ko","identification_confidence","container",
                     "scale_reference","portion_basis","grams",
                     "kcal","protein_g","carb_g","fat_g",
                     "hidden_fat_risk","db_match_hint"],
        "properties": {
          "name_ko": { "type": "string" },
          "identification_confidence": { "enum": ["high","medium","low"] },

          // ── 양을 어떻게 잰 건지 ─────────────────────────────
          "container": {
            "enum": ["밥공기","국그릇","대접","종지","접시(소)","접시(중)",
                     "접시(대)","불판","편의점도시락","일회용용기","컵","불명"]
          },
          "scale_reference": {
            "enum": ["젓가락","숟가락","손","휴대폰","캔/병","식기크기추정","없음"]
          },
          "portion_basis": {
            "enum": ["scale_reference",   // 기준물로 실제로 쟀다
                     "container_size",    // 그릇 규격에서 유추
                     "typical_serving",   // 이 요리의 통상 1인분
                     "guess"]             // 근거 없음
          },

          // ── 전부 범위 ──────────────────────────────────────
          "grams":     { "$ref": "#/$defs/range" },
          "kcal":      { "$ref": "#/$defs/range" },
          "protein_g": { "$ref": "#/$defs/range" },
          "carb_g":    { "$ref": "#/$defs/range" },
          "fat_g":     { "$ref": "#/$defs/range" },

          "hidden_fat_risk": { "type": "string" },   // "기름량 안 보임. 볶음이면 +100~150kcal"
          "db_match_hint":   { "type": "string" }    // 로컬 DB 조회 키
        }
      }
    },

    "unidentifiable_regions": {           // ★ 모를 자유
      "type": "array", "items": { "type": "string" }
    },
    "overall_caveat": { "type": "string" }
  },

  "$defs": {
    "range": {
      "type": "object", "additionalProperties": false,
      "required": ["low","best","high"],
      "properties": { "low":{"type":"number"}, "best":{"type":"number"}, "high":{"type":"number"} }
    }
  }
}
```

**`portion_basis`가 왜 중요한가.** 이게 없으면 모델은 "220g"이라고만 말하고, UI는 그게 젓가락으로 잰 220인지 순수 추측 220인지 구분할 수 없습니다. 이 필드 하나가 **UI 동작을 완전히 바꿉니다:**

| `portion_basis` | UI 동작 |
|---|---|
| `scale_reference` | 그대로 보여줌. 범위 좁게 표시 |
| `container_size` | 그대로. 그릇 종류를 함께 표시해 사용자가 검증 가능 |
| `typical_serving` | **"통상 1인분 기준"** 배지 + 양 슬라이더를 **펼친 상태**로 노출 |
| `guess` | **숫자를 흐리게 처리하고 "직접 입력" 버튼을 주인공으로.** 저장 전 사용자 확정 강제 |

**즉 모델이 정직하게 "몰라"라고 말하면, 앱이 그걸 받아서 수동 입력으로 우아하게 강등합니다.** 이게 `photo-ingestion.md`의 F12("기기 감지 실패 시 → 수동 입력으로 우아하게 강등")와 같은 패턴입니다.

### 5.2 범위(range)를 진짜 범위로 만드는 법

모델을 그냥 두면 `low: 210, best: 220, high: 230` 같은 **가짜 범위**를 냅니다. 프롬프트로 막습니다:

```
양 추정 규칙:
- grams의 low/high는 "이 사진만 보고 배제할 수 없는" 최소·최대다.
  당신의 확신을 표현하는 자리가 아니라, 사진이 허용하는 폭을 표현하는 자리다.
- portion_basis가 "guess"이면 high/low 비율은 최소 2배여야 한다 (예: 120~280g).
  그보다 좁으면 근거가 있다는 뜻이므로 portion_basis를 올려 잡아라.
- portion_basis가 "typical_serving"이면 최소 1.5배.
- 밥·면·국물은 그릇에 가려 바닥이 안 보인다. 보이는 윗면만으로 판단하지 말고
  그릇 규격에서 부피를 유추하고, 안 보이는 만큼 범위를 넓혀라.
- kcal/protein/carb/fat의 범위는 grams 범위와 일관되어야 한다.
  grams가 2배 폭이면 kcal도 대체로 2배 폭이다.
```

**핵심 문장:** *"당신의 확신을 표현하는 자리가 아니라, 사진이 허용하는 폭을 표현하는 자리"* — 이 한 줄이 `[218, 220, 222]` 같은 출력을 막습니다.

### 5.3 "모르겠다"고 말하게 하는 법

단순히 "모르면 모른다고 해"는 잘 안 먹힙니다. 세 가지를 같이 씁니다:

1. **모름을 담을 그릇을 만들어 줍니다.** `unidentifiable_regions[]`가 그것입니다. 배열이므로 비워도 되고 채워도 됩니다 — **모른다고 말할 합법적 자리가 생깁니다.**
2. **모름을 벌하지 않습니다.** `identification_confidence: "low"` + `portion_basis: "guess"`는 **정상 출력**이라고 명시합니다.
3. **개수를 강제하지 않습니다.** "요리 3개를 찾아라"라고 하면 없는 것도 만들어냅니다. `dishes`는 빈 배열도 허용합니다.

```
- 확신 없으면 identification_confidence를 "low"로 두라. 이건 실패가 아니라 정상 출력이다.
- 판별 불가능한 그릇/영역은 추측하지 말고 unidentifiable_regions에 위치와 이유를 적어라.
  (예: "오른쪽 뒤 종지 — 내용물이 그늘에 가려 판별 불가")
- 요리 개수를 채우려 하지 마라. 확실한 것만 dishes에 넣어라. 빈 배열도 정답일 수 있다.
- photo_quality가 "unusable"이면 dishes를 비우고 이유만 적어라.
```

### 5.4 한 사진에 여러 요리 — **한국 밥상의 핵심 과제**

이게 Nutrition5k/Food-101이 전혀 도와주지 못하는 지점입니다. 서양 데이터셋은 **한 접시**를 가정합니다. 한국 밥상은 **밥 + 국 + 반찬 3~5종**입니다.

프롬프트에 **한국 식기 기준표**를 넣습니다. 이게 `portion_basis: "container_size"`를 성립시키는 근거가 됩니다:

```
한국 식기 실측 기준 (양 추정의 1차 근거로 쓰라):
- 밥공기(지름 ~11cm): 가득 ≈ 210g, 8부 ≈ 170g, 반공기 ≈ 105g
- 국그릇(지름 ~15cm): 국물+건더기 ≈ 300~400g
- 종지(지름 ~8cm):    반찬 ≈ 30~60g
- 공깃밥 뚜껑 덮인 상태: 양 판별 불가 → portion_basis="guess"
- 삼겹살 1인분(구이용 생고기) ≈ 180~200g
- 편의점 도시락 1개 ≈ 400~600g
- 배달 1인분 용기: 매장 1인분보다 대체로 많다
※ 이 숫자는 기준선이다. 사진이 다르게 말하면 사진을 믿어라.

밥상 규칙:
- 밥/국/반찬/메인을 각각 별도 dish로 분리하라. 합치지 마라.
- 종지 반찬(김치·나물·장아찌)은 칼로리가 작다. 과대평가하지 마라.
- 단, 기름 쓴 반찬(잡채·전·튀김·볶음)은 작아 보여도 칼로리가 크다.
  기름량이 사진에서 안 보이면 hidden_fat_risk에 반드시 적어라.
- 국물은 다 먹지 않는 경우가 많다. grams는 "그릇에 담긴 양"으로 적고,
  overall_caveat에 "국물 섭취량은 사용자 확인 필요"라고 남겨라.
```

> **마지막 줄이 특히 중요합니다.** 순대국밥 한 그릇에서 국물을 다 마시는지 아닌지가 나트륨과 칼로리를 크게 바꾸는데, **사진으로는 원리적으로 알 수 없습니다.** 모델이 모르는 게 맞고, UI가 물어봐야 합니다(§7.2의 국물 슬라이더).

**2-pass(1차: 그릇 나열 → 2차: 정량화)는 권하지 않습니다.** 비용 2배, 지연 2배인데 개선폭이 측정된 바 없습니다 `[미검증]`. **§9의 측정에서 1-pass가 명백히 부족하다고 나오면 그때 도입합니다.**

### 5.5 사용자 보정 되먹임

사용자가 검수에서 고친 값을 축적해서 다음 요청에 넣습니다. **이게 §2.4의 "편향을 일관되게 만드는" 장치입니다.**

user 메시지 끝에 붙일 카드(system이 아니라 user에 붙입니다 — system은 고정해 둬야 하므로):

```
[이 사용자의 보정 이력 — 최근 20건 요약]
음식명순으로 정렬:
- 삼겹살:   모델 220g → 사용자 300g  (n=4, 평균 +36%)
- 아메리카노: 모델 15kcal → 사용자 10kcal (n=9)
- 흰쌀밥:   모델 180g → 사용자 210g  (n=7, 평균 +17%)
※ 같은 음식이 다시 나오면 이 보정을 반영해서 추정하라.
※ 목록에 없는 음식에는 이 보정을 일반화하지 마라.

[자주 먹는 음식] 닭가슴살(주5), 현미밥(주5), 편의점 샐러드(주3)
※ 애매하면 이 목록을 우선 고려하되, 사진과 어긋나면 사진을 믿어라.
```

설계 주의:
- **음식명 알파벳/가나다순 고정 정렬** — 순서가 흔들리면 결정성이 깨집니다.
- **최근 20건 상한** — 무한정 늘면 토큰이 새고 오래된 습관이 현재를 오염시킵니다.
- **"목록에 없는 음식에 일반화하지 마라"** 필수 — 없으면 모델이 "이 사람은 늘 과소평가하는군" 하고 전체를 부풀립니다.
- **"사진과 어긋나면 사진을 믿어라"** 필수 — 없으면 보정 이력이 사진을 이겨버립니다.
- 보정 이력은 **`source: "photo"` 기록에서만** 뽑습니다. 수동 입력을 섞으면 다른 추정기의 편향이 들어옵니다.

### 5.6 API 호출 형태 (claude-api 스킬 기준)

```js
// 서버리스 프록시 안. 클라이언트에서 직접 부르면 키가 노출됩니다.
const stream = client.messages.stream({
  model: "claude-opus-5",
  max_tokens: 4096,
  thinking: { type: "adaptive" },          // budget_tokens 아님 — Opus 5에선 400
  output_config: {
    effort: "low",                          // 이 작업엔 low로 충분. 비용/지연 절감
    format: { type: "json_schema", schema: MEAL_SCHEMA }
  },
  messages: [{
    role: "user",
    content: [
      { type: "image", source: { type: "base64", media_type: "image/jpeg", data: b64 } },
      { type: "text", text: `끼니: 점심 (12:40)\n\n${correctionCard}` }
    ]
  }],
  system: FROZEN_RULES        // §5.1~5.4. 절대 요청마다 바꾸지 말 것
});
const msg = await stream.finalMessage();
```

주의사항 (스킬에서 확인):
- **이미지를 텍스트 앞에** 둡니다 (공식 문서 권장).
- `thinking: {type:"adaptive"}` — Opus 5에서 `budget_tokens`는 **400 에러**입니다.
- `effort`는 `output_config` 안에 들어갑니다. 최상위가 아닙니다.
- `output_format`(구버전)이 아니라 **`output_config.format`** 입니다.
- 스트리밍 필수 (§4.6의 UX 이유).
- `stop_reason === "refusal"` 체크 — 음식 사진에 사람 얼굴이 크게 들어가면 거부될 수 있습니다. 그땐 **수동 입력으로 강등**하고 "사람이 나온 사진은 잘라서 다시 찍어주세요"라고 안내합니다.

## 6. 로컬 VLM — 인식용으로는 안 됩니다

### 6.1 검증된 사실

`huggingface/transformers.js` README (2026-09-19 확인):
- 지원 VLM: **Florence-2, Moondream1, SmolVLM(250M·500M), Qwen2-VL, Qwen2.5-VL, LLaVA, LLaVA-OneVision**
- **WebGPU 지원**: `device: 'webgpu'`. 단 문서 자체 경고 — *"The WebGPU API is still experimental in many browsers, so if you run into any issues, please file a bug report."*
- 양자화: `fp32` / `fp16` / `q8` / `q4`

모델:

| 모델 | 리포 | 스타 | 마지막 푸시 | 라이선스 | 크기 |
|---|---|---|---|---|---|
| **moondream** | `m87-labs/moondream` | 10,050 | 2026-04-20 | Apache-2.0 | **2B** / **0.5B** |
| **SmolVLM** | `huggingface/smollm` | 3,894 | 2026-09-17 | Apache-2.0 | 250M / 500M (transformers.js 기준) |
| Florence-2 | (Grounded-SAM-2 등에서 사용) | — | — | — | — |

> moondream README에 **양자화 파일 크기·RAM 요구량·벤치마크 점수·라이선스가 없습니다** (moondream.ai 문서로 안내 — 해당 도메인 접근 불가). 따라서 구체적 용량·속도는 `[미검증]`입니다.

### 6.2 그래도 안 되는 이유 (추론, 근거 명시)

**음식 사진에 대한 이 모델들의 정량 평가는 공개된 것을 찾지 못했습니다** `[미검증]`. 그래서 아래는 측정이 아니라 **구조적 논증**이고, 그렇게 표시합니다.

포션 추정은 두 가지를 동시에 요구합니다:
1. **세밀한 음식 지식** — "순대국밥"과 "돼지국밥"을 구분하고 각각의 칼로리 밀도를 아는 것
2. **3D/스케일 추론** — 그릇 규격에서 숨은 부피를 유추하는 것

그런데:
- **한국 음식은 롱테일입니다.** 롱테일 지식은 큰 모델이 마지막에 얻고, **양자화(q4)하면 가장 먼저 잃는 부분**입니다. 500M 모델은 애초에 가진 적이 없습니다.
- 500M~2B 모델은 일반 VQA("이건 음식이다", "빨간색이다")는 하지만, **"밥공기 8부면 170g"** 같은 정량 추론은 다른 종류의 능력입니다.
- **가장 큰 모델도 이 문제를 잘 못 풉니다** (§2.2: Google이 전용 학습 + depth로도 70.6 kcal). **거기서 100배 작은 모델을 양자화해서 쓰는 건 방향 자체가 틀렸습니다.**

실무적 문제도 있습니다:
- 첫 로드 시 **수백 MB 다운로드** `[크기 미검증]`. 모바일 데이터에서 치명적
- iOS Safari의 WebGPU는 여전히 고르지 않습니다 (transformers.js 문서의 "experimental in many browsers" 경고가 그대로 적용)
- 이 프로토타입은 **빌드 없음 / 의존성 없음 / 네트워크 요청 없음**이 원칙입니다. WebGPU VLM은 이 원칙을 전부 깹니다

**결론: 인식용 로컬 VLM은 넣지 않습니다.**

### 6.3 단, 로컬 모델이 쓸모 있는 딱 한 곳

**API 호출 전 게이트.** 이건 0.5B급 과제입니다:

```
찍은 사진 → 로컬 판정 →  "음식이 아닙니다"        → API 호출 안 함
                    →  "너무 흐립니다"          → 재촬영 유도
                    →  "사람 얼굴이 큽니다"      → 자르기 유도 (거부 회피 + 프라이버시)
                    →  통과                    → API 호출
```

**효과:** 헛돈(월 비용의 10~20% `[추정]`)을 막고, 무엇보다 **쓸 수 없는 사진이 클라우드로 나가는 걸 막습니다**(§8). 이건 정확도가 아니라 **프라이버시 장치**로서 정당화됩니다.

**그런데 이것조차 VLM이 필요 없습니다.** 초점(라플라시안 분산)과 밝기는 **순수 Canvas 2D로 30줄**이면 됩니다. 얼굴 검출은 `FaceDetector` API(Chrome/Android) 또는 생략. **의존성 0으로 80%를 얻습니다.** 여기서 멈추길 권합니다.

## 7. ★ 화면 설계 — 식단 기록 탭

### 7.0 탭바 자리 문제 (먼저 해결해야 함)

현재 `app.js`의 `TABS`는 5개로 꽉 찼습니다:

```js
{ 'P00-N01', '🏠', '홈',    'P02' }
{ 'P00-N02', '📋', '플랜',  'P07' }
{ 'P00-N03', '✅', '체크인', 'P08' }
{ 'P00-N04', '📈', '추이',  'P09' }
{ 'P00-N05', '⚙️', '설정',  'P12' }
```

**6개는 휴대폰에서 너무 많습니다.** 탭바 자리는 **사용 빈도**로 배분해야 합니다:

| 화면 | 실제 사용 빈도 |
|---|---|
| **식단 기록** | **하루 3~5회** |
| 홈 | 하루 1~2회 |
| 플랜 | 주 1~2회 |
| 추이 | 주 1회 |
| **체크인** | **주 1회** |
| 설정 | 월 1회 |

**권장: `P00-N03` 체크인 → 식단(`P14`)으로 교체.**
체크인은 주 1회이므로 탭바 자리를 쓸 이유가 없습니다. 대신:
- **홈 `P02`의 `P02-C4` 다음행동 배너**로 올립니다 (이미 "이번 주 체크인 하기" 배너가 설계되어 있음 — 그대로 씁니다)
- **식단 주간 화면 `P17` 상단**에도 체크인 카드를 둡니다 (§7.6에서 둘이 결합하므로 오히려 자연스러움)

**설계 근거:**

- **`P14-C01`이 범위를 보여줍니다.** "남은 860 kcal"만 쓰면 이 앱이 스스로 세운 기준(§2.3의 노이즈 바닥 원칙)을 배신합니다. 굵은 숫자는 `best`의 합, 아래 괄호는 `low`/`high`의 합입니다.
- **범위 합산 규칙 — 제곱합 금지.** `√(Σσ²)`로 합치면 범위가 좁아 보이는데, 식단 기록 오차는 **상관되어 있습니다**(같은 사람이 같은 식으로 틀림). **보수적으로 선형 합(Σlow, Σhigh)** 합니다. 이게 정직한 쪽입니다.
- **⚠ 배지** = `portion_basis`가 `typical_serving` 또는 `guess`인 항목. 누르면 양 조정 모달(`M26`).
- **`✓수동` / `📷추정` 배지**가 모든 행에 붙습니다. §2.4의 "경로별 편향" 때문에 필수입니다.
- **마크로 3개는 전부 막대**, 링/도넛 아님. 이 앱은 이미 `plan.js`에서 `macroBar()`를 씁니다 — **그대로 재사용합니다.**
- **단백질이 맨 위** — 사용자 요청("단백질 부족하면 알려줘")이자 `engine.js`가 근손실 게이트로 쓰는 값입니다.

**UID 배정:** `P14-C01`(남은 양), `P14-C02`(코칭), `P14-L01`(끼니), `P14-B01`(FAB), `P14-B02`~(끼니별 추가), `P14-G01`(막대 그룹), `P14-S01`(오늘 기록 없음 빈상태)

3. **`P17-C04` 경로 비율.** 편향의 일관성(§2.4)이 유지되는지 보는 계기판입니다. 사진 비중이 크게 흔들리면 `P17-C03`의 해석도 흔들립니다.

4. **월간 = 주간의 확대가 아닙니다.** 월간에서만 의미가 생기는 것을 보여줍니다: 달력 히트맵(습관 패턴 — 주말에 무너지는지), 주차별 추세(편향이 커지는지), 4주 누적 실측 비교(노이즈 위로 올라옴).

### 7.5 ★ 코칭 넛지 — "그만 먹어"를 어떻게 말할 것인가

사용자 요청: *"단백질 부족하거나 뭔가 많이 먹었으면 그만 먹으라 해줘도 좋아"*

**요청은 받되, 문구는 바꿉니다. 이유를 먼저 말씀드립니다.**

> 이 앱은 README 면책에 *"섭식장애 이력이 있다면 전문가와 상의하세요"*를 이미 적어두었습니다. 그런데 **음식에 대한 금지형 명령("그만 드세요", "더 먹으면 안 됩니다")은 섭식 문제를 만들거나 악화시키는 쪽으로 알려진 화법입니다.** 22세 남성 1인 사용자라도, 하루 3번 5년간 반복될 문구를 그 레지스터로 두는 건 위험합니다.
>
> **바꿀 것: 금지(prohibition) → 결과(consequence).** 정보량은 같고, 통제권은 사용자에게 남습니다. 그리고 이게 이 앱의 기존 화법("왜 이 모드인지, 왜 다른 모드가 안 열리는지 설명한다")과도 일관됩니다.

```
   - 14:00 "칼로리 다 썼습니다" → 유용 (저녁을 조정할 수 있음)
   - 23:00 같은 말             → 무의미하고 죄책감만 남김 → 띄우지 않음
   - 칼로리 초과 알림은 21:00 이후 금지
   - 단백질 부족 알림은 19:00~20:30 창에서만 (아직 먹을 수 있는 시각)

B. 오차를 안다
   - 남은 칼로리의 best가 음수여도, high가 양수면 "넘었습니다"라고 단정하지 않음
     → "목표를 넘었을 가능성이 큽니다 (추정 -210 ~ +80 kcal)"
   - 오늘 기록이 전부 portion_basis="guess"면 칼로리 넛지 자체를 띄우지 않음
     → 대신 "오늘 기록이 대부분 추정값입니다. 저녁은 직접 입력해 보세요"

C. 하루 한 개
   - P14-C02 배너는 하루 최대 1개. 우선순위:
     ① 섭취가 kcalFloor 아래 (engine.js의 안전 하한)   ← 최우선, 항상 띄움
     ② 단백질 심각 미달 (목표의 60% 미만 & 저녁 시각)
     ③ 칼로리 초과 (단, 이번 주 3회차부터만)
     ④ 기록 누락 (어제 기록 없음)
   - 나머지는 침묵. 알림 피로가 기록률을 죽이고, 기록률이 전부입니다.

D. 일일이 아니라 주간이 기준
   - engine.js는 주 단위로 시뮬레이션합니다. 하루 초과는 계획을 깨지 않습니다.
   - 칼로리 초과 넛지는 "이번 주 3회차"부터 발동. 1~2회차는 띄우지 않음.
   - 문구에 항상 주간 맥락을 넣음: "이번 주 3번째입니다"
```

**비대칭 원칙:**
- **단백질은 "부족"을 말합니다** (근손실이 진짜 위험이고, `engine.js`가 2.0 g/kg FFM 아래에서 실제로 근손실을 계산합니다)
- **칼로리는 "초과"를 말합니다**
- **칼로리 "부족"은 반드시 말합니다** — `kcalFloor` 아래면 무조건 띄웁니다. 이건 넛지가 아니라 **안전장치**입니다.
- **지방/탄수는 개별적으로 잔소리하지 않습니다.** 칼로리와 단백질이 맞으면 나머지는 따라옵니다.

### 7.6 화면 간 연결

```
P02 홈 ──────► P14 식단 (오늘 요약 카드)
                 │
                 ├─► P15 수동 기록 ──► M26 양 정하기
                 ├─► P16 사진 기록 ──► (검수 게이트) ──► 저장

                                 │
P08 체크인 ◄─────────────────────┘   ★ P17-C03 ↔ P08 양방향
   체크인이 "기록 평균 vs 실측" 비교를 재료로 받아
   칼로리 재조정을 제안. 지금은 체중만 보지만,
   식단 기록이 들어오면 "어디가 틀렸는지"까지 말할 수 있게 됨.

P07 플랜 (식단 탭) ──► 하루 목표 kcal/P/C/F 를 P14에 공급

```

**`P08` 체크인이 실제로 좋아집니다.** 지금은 "체중이 예상보다 덜 줄었다 → 칼로리를 내린다"밖에 못 합니다. 식단 기록이 있으면:

> "계획은 2,140 kcal였고, 기록은 평균 2,050이었는데, 체중은 예상만큼 안 줄었습니다.
>  ① 기록이 실제보다 적게 잡혔거나 ② 계획의 TDEE가 높게 잡혔거나 둘 중 하나입니다.
>  기록의 62%가 사진 추정이었습니다. 다음 주는 저녁만 직접 입력해 보시겠어요?
>  그러면 어느 쪽인지 갈립니다."

**이게 "왜 이 앱에 식단 탭이 필요한가"의 최종 답입니다.** 단순한 칼로리 계산기가 아니라, **기존 체크인 루프에 관측값을 하나 더 넣어서 원인을 분리할 수 있게 만드는 것**입니다.

## 8. 프라이버시

### 8.1 음식 사진에 실제로 담기는 것

인바디 결과지보다 **넓습니다.** 인바디는 숫자 한 장이지만 음식 사진에는:

- **얼굴** — 같이 먹는 사람, 유리·수저에 비친 본인
- **장소** — 식당 인테리어, 간판, 메뉴판, 테이블 번호
- **EXIF GPS** — 정확한 위도·경도. **가장 위험하고 가장 쉽게 잊는 것**
- **EXIF 기기 정보** — 모델명, 일련번호, 촬영 시각
- **생활 패턴** — 몇 시에 어디서 누구와 먹는지가 90장/월씩 쌓임
- **민감 추론** — 할랄/채식/글루텐프리 → 종교·건강 상태

### 8.2 클라우드 API로 나갈 때 / 안 나갈 때

**Anthropic 공식 문서 (2026-09-19 `docs/en/build-with-claude/vision` FAQ, 직접 인용):**

> *"Image uploads are ephemeral and not stored beyond the duration of the API request. Uploaded images are automatically deleted after they have been processed."*
>
> *"Anthropic does not use uploaded images to train models."*

**이건 좋은 조건입니다.** 하지만 이걸 근거로 "안전하니까 그냥 보내자"로 가면 안 됩니다:

| 차이 | 로컬(수동 입력) | 클라우드 API |
|---|---|---|
| 이미지가 기기를 떠나는가 | 아니오 | **예** |
| 제3자 보관 | 없음 | 요청 처리 중에만 (문서 기준) |
| 학습 사용 | — | 안 함 (문서 기준) |
| 네트워크 경로 로그 | 없음 | 프록시·CDN·ISP에 메타데이터 |
| **우리 프록시의 로그** | — | **★ 우리가 통제. 반드시 끕니다** |
| 오프라인 동작 | **됨** | 안 됨 |
| 한국 개인정보보호법상 성격 | 로컬 처리 | **국외이전 + 민감정보 가능성** |

> **한국법 관점** `[법률자문 아님]`: 개인정보보호법상 **건강정보는 민감정보**(제23조)이고 **별도 동의**가 필요합니다. 식단 기록은 체성분·목표체중과 결합되면 건강정보로 볼 여지가 큽니다. 또 클라우드 API는 **국외 이전**에 해당할 수 있습니다. 1인 개인용이라 규제 적용은 희박하지만, **"앱을 다른 사람에게 주는 순간" 달라집니다.** 지금 정직하게 만들어 두는 게 쌉니다.

### 8.3 반드시 할 것

**① EXIF를 전부 제거하고 보냅니다 — 예외 없음**

```js
// Canvas에 다시 그리면 EXIF가 통째로 날아갑니다. 별도 라이브러리 불필요.
async function stripAndResize(file, maxEdge = 1024) {
  const bmp = await createImageBitmap(file);   // EXIF 방향은 여기서 적용됨
  const s = Math.min(1, maxEdge / Math.max(bmp.width, bmp.height));
  const c = document.createElement('canvas');
  c.width = Math.round(bmp.width * s);
  c.height = Math.round(bmp.height * s);
  c.getContext('2d').drawImage(bmp, 0, 0, c.width, c.height);
  return c.toDataURL('image/jpeg', 0.8);       // GPS·기기·시각 전부 소실
}
```

**촬영 시각은 EXIF에서 따로 읽어 `meal.at`에 넣고, 이미지에서는 지웁니다.** 시각은 필요하지만 GPS는 필요 없습니다.

**② 원본 사진을 저장하지 않습니다 (기본값)**
- 저장: **썸네일(장변 200px)만**, 검수 이력 확인용
- 원본 보관은 설정에서 **명시적으로 켜야** 하는 옵션

**③ 프록시에서 이미지를 로깅하지 않습니다**
- 에러 로그에도 body를 남기지 않습니다. 실수의 1순위 경로입니다.
- 요청/응답 저장 안 함. **토큰 사용량 숫자만** 기록

**④ 수동 전용 모드를 일급 기능으로**
- 설정 `P12`에 **"사진 분석 사용 안 함"** 토글
- 켜면 `P16`이 사라지고 `P15`만 남습니다. **앱은 100% 동작합니다.**
- **이걸 숨긴 옵션이 아니라 정당한 사용법으로 제시합니다.**

## 9. ★ 만들기 전에 측정할 것

§2.5에서 **VLM의 음식 사진 정확도에 대한 공개 수치를 찾지 못했다**고 했습니다. 그 불확실성에 대한 정직한 대응은 추측이 아니라 **측정**입니다. 그리고 1인 앱이라 측정이 쉽습니다.

**주말 이틀짜리 실험:**

1. **30끼를 찍고, 같이 계량합니다.** 주방저울로 밥·고기·반찬 각각. 외식은 30끼 중 10끼 정도로 제한(계량 불가하므로 "1인분 표기"를 정답으로).
2. **같은 사진을 3가지로 돌립니다:** Opus 5 / Sonnet 5 / Haiku 4.5
3. **네 가지를 잽니다:**
   - **음식명 정확도** (맞힌 요리 / 전체 요리) — §2.3대로 높을 것으로 예상
   - **중량 MAPE** (|추정g − 실제g| / 실제g) — **이게 진짜 지표**
   - **칼로리 MAE** — Nutrition5k의 70.6 kcal과 비교
   - **범위 커버리지** — 실제값이 `[low, high]` 안에 든 비율. **목표 80% 이상.** 이게 낮으면 §5.2의 범위 규칙이 작동하지 않는다는 뜻입니다.
4. **편향 방향을 봅니다.** 부호 있는 평균 오차가 0에서 멀면 = 일관된 편향 = §2.4에 따라 **오히려 괜찮습니다.** 부호가 마구 바뀌면 = 무작위 = 체크인이 흡수하지 못합니다.

**중단 기준 (미리 정해 둡니다):**
- **범위 커버리지 < 60%**  → 사진 경로를 v1에서 뺍니다. 수동만 출시.
- **중량 MAPE > 50%**      → 사진은 "요리 이름 자동 채우기"로만 쓰고 **양은 항상 사용자 입력**. (이것만으로도 기록 속도가 크게 붙습니다 — 나쁘지 않은 축소안입니다.)
- **커버리지 ≥ 80% & MAPE < 30%** → 설계대로 전부 출시.

> **이 숫자들을 미리 정해두는 것 자체가 설계의 일부입니다.** 결과를 보고 기준을 정하면 항상 통과하게 됩니다.
