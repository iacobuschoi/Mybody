# 영양 DB 스윕 — "이건 제육볶음이고 250g쯤" 을 탄단지로 바꾸는 레이어

조사 범위: **조회(lookup) 레이어**와 **검색(manual logging) 레이어**. 사진 인식 모델은 다른 에이전트 담당이므로 여기서는 "인식 결과를 받아서 숫자로 바꾸는 부분"만 다룬다.

**조사 제약 (먼저 밝힘):** 이 세션의 egress 정책이 `fdc.nal.usda.gov`, `api.nal.usda.gov`, `world.openfoodfacts.org`, `data.go.kr`, `foodsafetykorea.go.kr`, `koreanfood.rda.go.kr`, `platform.fatsecret.com` 을 **전부 차단**했다. 따라서 공식 페이지를 직접 열어 숫자를 확인하지 못했다. 검색 요약과 github.com(유일하게 열린 도메인)에서 확인한 것만 사실로 적고, 나머지는 전부 `[미검증]` 으로 표시했다. **API 스키마와 건수는 실제 구현 전에 반드시 직접 확인해야 한다.**

---

## 0. 결론 먼저

1. **USDA / Open Food Facts / Nutritionix / Edamam / Spoonacular 는 이 앱의 주 DB가 될 수 없다.** 이유는 정확도가 아니라 **커버리지**다. 한국인이 먹는 것의 대부분은 *조리된 복합요리(찌개·볶음·국밥·덮밥)* 인데, 서구권 DB는 원재료(raw ingredient)와 포장 가공식품 중심이다. "pork belly, raw" 는 있어도 "제육볶음 1인분" 은 없다.
2. **유일하게 맞는 1차 소스는 식약처 식품영양성분DB 다.** 이 DB는 `음식 / 가공식품 / 원재료성식품` 3분류를 명시적으로 나눠서 제공하고, **`음식` 분류가 곧 복합요리 테이블**이다. 이게 전체 설계를 결정한다.
3. **프로토타입에는 아무것도 fetch하지 말고, 한국 음식 오프라인 테이블을 페이지 안에 박아라.** 실측했다: **335개 한식 요리 + 1회제공량 + kcal/탄/단/지 = compact JSON 28.5 KB, gzip 6.4 KB.** 이건 비용이라고 부를 수 없는 크기다. 백엔드 없이 오늘 당장 된다.
4. **바코드는 한국에서 반쪽짜리다.** 식약처 바코드 API는 바코드→*제품명/품목보고번호* 만 주고 **영양성분을 직접 주지 않는다.** 영양은 품목보고번호로 가공식품 영양DB에 조인해야 한다. 이 조인이 얼마나 성공하는지는 미검증이고, 아마 꽤 깨질 것이다.
5. **편의점 도시락·삼각김밥의 공개 DB는 없다.** 확인 결과 공식 API도, 오픈 데이터셋도 없다. FatSecret Korea와 필라이즈가 갖고 있지만 크라우드소싱/자체 구축이고 재사용 라이선스가 없다. **이 카테고리는 "사용자가 직접 등록한 나만의 음식"으로 처리하는 게 유일하게 정직한 답이다.**

## 1. 문제를 제대로 세워두기

"사진 → 칼로리"를 3단계로 쪼개면:

| 단계 | 하는 일 | 난이도 | 이 보고서 담당 |
|---|---|---|---|
| A. 인식 | "이건 김치찌개다" | 중 (한식 모델 필요) | ✕ |
| B. 양 추정 | "한 그릇에 400g 들었다" | **최악** | ✕ |
| C. 조회 | "김치찌개 400g = ? kcal/탄/단/지" | **낮음 — 단 DB가 있을 때만** | **○** |

C는 DB만 있으면 산수다. 문제는 **한식용 C의 DB가 서구권에 없다**는 것. 그리고 C가 아무리 정확해도 **B의 오차가 그대로 곱해진다.** 400g로 봤는데 실제 300g이면 25% 틀린다. 이건 DB를 바꿔서 해결되는 문제가 아니다.

그래서 이 앱의 설계 원칙은:

> **C는 정확하게, B는 사용자가 고르게.** 사진은 "무슨 음식인지"까지만 맞히고, **양은 사람이 1인분 / 곱빼기 / 반공기 중에서 탭**하게 한다. 이건 타협이 아니라 유일하게 정직한 구조다. 인바디 노이즈 플로어 아래는 "변화 없음"이라고 말하는 것과 같은 기준이다.

## 2. USDA FoodData Central (FDC)

### 확인된 것

| 항목 | 내용 | 출처 신뢰도 |
|---|---|---|
| 규모 | 전체 데이터 타입 합쳐 **30만+ 식품** | 검색 요약 (공식 사이트 차단) |
| 라이선스 | **퍼블릭 도메인 / CC0 1.0** — 허가 불필요, 출처 표기만 요청 | 확인 |
| 갱신 | Foundation **연 2회**, Branded **월 1회** | 확인 |
| SR Legacy | **동결**. FDC Published 날짜 `2019-04-01` 고정, 더 이상 갱신 없음 | 확인 |
| Survey (FNDDS) | 현재 **FNDDS 2021–2023**, FDC Published `2024-10-31` | 확인 |
| API | REST, 6개 엔드포인트, Foundation/Branded/SR Legacy/Survey/Experimental 전부 커버, `api.nal.usda.gov/fdc/v1/…`, DEMO_KEY 또는 무료 키 | 확인 |
| 벌크 | CSV/JSON 전체 덤프 다운로드 제공 | 확인 |

**데이터 타입별 정확한 건수는 `[미검증]`.** `fdc.nal.usda.gov/download-datasets` 가 차단되어 열지 못했다. 흔히 인용되는 수치(Foundation ~2천, SR Legacy 7,793, Branded 190만+)는 **이 세션에서 확인하지 못했으므로 쓰지 말 것.** 구현 시 API의 `dataType` 필터로 직접 세면 된다.

### CC0 의 의미 — 이게 진짜 가치다

FDC는 **공공 도메인**이다. share-alike 없음, 귀속 의무 없음(요청만 있음), 상업/비상업 구분 없음. **즉 FDC에서 뽑은 값은 Mybody 페이지 안에 그대로 하드코딩해도 법적으로 아무 문제가 없다.** 아래에서 다룰 ODbL 데이터와 결정적으로 다른 점이다.

### 오프라인 SQLite 배포판

`MenuLogistics/USDASQLite` (GitHub) — FDC 전체를 **약 430MB SQLite** 로 말아놓은 것. 퍼블릭 도메인 명시. 다만 **스타 2개, 커밋 2개**, 어느 FDC 릴리스 기준인지 명시 없음 — **신뢰하지 말고 참고만.** 그리고 430MB는 zero-build 정적 페이지에 들어갈 크기가 절대 아니다.

### 한식 커버리지 — 냉정하게

FDC에 한식이 아예 없진 않다. `kimchi` 는 SR Legacy에 있고, Branded에 한국계 수입 제품이 일부 있다. 하지만:

- **조리된 한식 복합요리는 사실상 없다.** 제육볶음·순대국밥·부대찌개 같은 항목은 FNDDS의 recipe 로직으로 미국 내 한인 식단 기준 일부만 존재할 뿐, 한국 표준 1인분 기준이 아니다.
- Branded의 한국 제품은 **미국 수출용 라벨** 기준이다. 국내 판매판과 중량·배합이 다르다.
- **FDC를 한식 앱의 1차 DB로 쓰는 건 틀린 선택이다.** 다만 **닭가슴살·계란·현미·아몬드 같은 단일 원재료의 fallback 으로는 훌륭하다.**

## 3. FNDDS — "찌개는 재료가 아니다" 문제의 교과서

이게 이 조사에서 가장 개념적으로 중요한 발견이다.

FNDDS(Food and Nutrient Database for Dietary Studies)는 NHANES 식이조사에서 사람들이 **"먹었다고 말한 것"** 을 그램과 영양소로 바꾸기 위한 DB다. 확인된 구조:

- 각 FNDDS 코드마다 **가식부 100g 기준 65개 영양소** 값
- **common portions 의 무게(weight)** 를 같이 들고 있음 — "1 cup", "1 slice" 같은 현실 단위 → 그램 변환표
- 결정적: **FNDDS 코드의 70% 가 "recipe calculation" 으로 생성됐다.** 즉 FDC에 그 음식의 실측값이 없어서, **재료 구성비를 잡고 조리 수율(yield)·수분손실을 적용해 역산**한 값이다.

### 이게 왜 Mybody 설계를 결정하는가

한식 DB도 **똑같은 방식으로 만들어져 있다.** 식약처 `음식` 분류 데이터의 출처 설명에 "국민건강영양조사의 식품별 재료량 자료집" 이 명시되어 있다 — 즉 한국도 **"김치찌개 1인분 = 재료 X g + Y g + …" 라는 레시피를 정의하고 역산**하는 구조다.

그래서 얻어지는 두 가지 사실:

1. **복합요리 값은 실측이 아니라 표준레시피 역산값이다.** 같은 김치찌개도 집집마다 다르다. DB가 주는 "김치찌개 400g = 236 kcal" 는 ±20~30% 범위를 가진 **모집단 평균**이지 당신 어머니의 김치찌개가 아니다.
2. **그럼에도 이게 최선이다.** 사용자가 재료를 하나씩 입력하게 만드는 순간 앱은 죽는다. 복합요리 단위 기록이 유일하게 현실적인 UX다.

> **앱이 말해야 할 문장:** "김치찌개는 조리법에 따라 ±25%까지 차이납니다. 이 수치는 표준 레시피 기준 추정치예요."
> 인바디 노이즈 플로어를 말해주는 앱이라면, 여기서도 같은 말을 해야 한다.

## 4. Open Food Facts (OFF)

| 항목 | 내용 |
|---|---|
| 규모 | **400만+ 제품 (2025년 기준)** — 단, 서버 repo README는 아직 "1.7M+ products from 150 countries" 라고 적혀 있다. **두 수치가 충돌한다.** 4M은 검색 요약, 1.7M은 내가 직접 읽은 README. 실제 값 `[미검증]` |
| 라이선스 | **ODbL v1.0** (데이터베이스) + 개별 콘텐츠는 DbCL. 조건 2개: **귀속(attribution)** + **동일조건변경허락(share-alike)** |
| 소프트웨어 | `openfoodfacts/openfoodfacts-server` — **AGPL-3.0, 스타 1.2k, 포크 662, main 브랜치 커밋 36,429개.** 매우 살아있음 (죽은 repo 아님) |
| 접근 | REST API + 전체 덤프 (MongoDB / CSV / JSONL / Parquet), 무료 |
| 바코드 | **핵심 기능.** 바코드가 곧 primary key |
| 기여 | 10만+ 기여자, 앱으로 바코드 스캔 + 라벨 사진 업로드 |

### ODbL 이 개인 앱에 실제로 뭘 요구하는가 — 정직하게

이게 이 보고서에서 사람들이 가장 자주 얼버무리는 지점이다.

확인된 내용: **"OFF 데이터를 다른 DB와 결합하면, 그 결과 데이터베이스도 오픈 데이터로 공개해야 한다."**

Mybody 시나리오별로 갈라보면:

- **개인용, 배포 안 함 (지금 상황):** ODbL의 share-alike 는 "Publicly Use" 시점에 발동한다. 내 노트북에서 나 혼자 쓰는 건 사실상 문제 없다.
- **GitHub Pages 등에 공개 배포:** **share-alike 발동.** OFF 데이터를 식약처 데이터와 섞어서 만든 `korean-foods.json` 은 **ODbL 로 공개해야 한다.** 화면에도 "© Open Food Facts contributors" 귀속 표기 필요.
- **나중에 유료화/상업화:** ODbL 은 상업 이용을 금지하지 않는다. 하지만 **파생 DB 공개 의무는 그대로 남는다.** 이건 제품 전략상 큰 제약일 수 있다.

**권고: OFF 데이터를 번들 테이블에 섞지 마라.** 번들 테이블은 **CC0(USDA) + 공공누리(식약처)** 로만 구성하고, OFF는 **런타임 바코드 조회용으로만** 쓴다(그래도 화면 귀속 표기는 해야 함). 그러면 파생 DB를 만들지 않으므로 share-alike 를 건드리지 않는다. 이 경계선을 지금 그어두면 나중에 아주 편해진다.

### 한국 제품 커버리지

`kr.openfoodfacts.org` 가 존재하고 한국어 UI도 있다. 하지만 **한국 제품 건수는 확인 실패 `[미검증]`** (도메인 차단).

경험적 판단으로 말하면: OFF는 **프랑스·유럽 중심**으로 시작해 기여자 분포가 그대로 커버리지 분포다. 한국 제품은 **드물고 편중돼 있을 가능성이 높다.** 특히 편의점 PB 상품·즉석조리식품은 거의 없을 것으로 본다. **이건 추정이며 검증하지 못했다.** 실제 구현 전에 `kr.openfoodfacts.org` 에서 실측할 것.

## 6. 한국 정부 DB — 여기가 진짜 답이다

### 6-1. 식약처 식품영양성분DB (MFDS) — **1순위**

확인된 구조가 정확히 우리가 필요한 모양이다.

**3분류 체계:**

| 분류 | 내용 | Mybody에서의 역할 |
|---|---|---|
| **음식** | 조리된 복합요리 (김치찌개, 제육볶음, 비빔밥…) | **★ 메인 테이블. 사진 인식 결과와 수동 선택의 착지점** |
| **가공식품** | 포장 제품 (라면, 과자, 음료, 도시락류) | 바코드 조회 + 편의점 |
| **원재료성식품** | 쌀, 돼지고기, 계란 등 원재료 | 직접 요리 기록 fallback |

**제공 필드 (확인됨):** 식품코드, 식품명, 데이터구분코드/명, 식품기원코드/명, 식품대분류/중분류/소분류/세분류, **식품중량**, 에너지, 수분, 단백질, 지방, 탄수화물, 비타민·무기질, **1회 섭취참고량**, 출처, 품목제조보고번호, 업체명, 수입여부, 원산지, 데이터생성방법, 데이터생성일자, 데이터기준일자.

→ **`식품중량` 과 `1회 섭취참고량` 이 둘 다 있다.** 양 추정 UX에 필요한 앵커가 데이터 안에 이미 들어있다는 뜻이다. 이게 중요하다.

**규모 (시계열, 확인된 것만):**

- 농·축·수산물 + 가공식품 등 **총 9만 2천여 건** 공공데이터포털 공개
- 가공식품·조리식품 영양 데이터 **2만 5천여 건** 표준화 추가 제공
- 2023년 7월 규정 개정 — 품목제조보고 시 영양성분 입력 의무화 → **약 4배 많은 2만 1천여 건** 가공식품 영양정보 추가
- 2024년 8월 가공식품 분야 **1만 6천 건** 추가

→ **현재 총계는 10만 건을 훌쩍 넘을 것으로 보이나 정확한 최신 수치는 `[미검증]`.** 시계열이 보여주는 건 **이 DB가 적극적으로 성장 중**이라는 것 — 죽은 데이터셋이 아니다.

**⚠️ 주의할 숫자:** 검색 결과 하나가 `전국통합식품영양성분정보(음식)표준데이터` 를 **"548건"** 이라고 했다. 이건 **의심스럽다.** 548개면 `음식` 분류치고 너무 적다(위에서 실측한 민간 CSV조차 335개다). 특정 제공기관 한 곳의 부분 집합이거나, 그리드 미리보기 행 수일 가능성이 크다. **`[미검증 · 신뢰 낮음]` 으로 표시하고 반드시 직접 확인할 것.**

**접근 경로 (3개, 확인됨):**

1. **식약처 OpenAPI `I2790`** — `식품영양성분DB(~2023)`
   `http://openapi.foodsafetykorea.go.kr/api/{KEY}/I2790/json/1/200?DESC_KOR={URL인코딩된음식명}`
   응답 필드: `DESC_KOR`(음식명), `NUTR_CONT1`(열량), `NUTR_CONT2`(탄수화물), `NUTR_CONT3`(단백질), `NUTR_CONT4`(지방)…
   **⚠️ 이름이 `(~2023)` 이다 — 레거시로 동결됐을 가능성이 높다.** 한국 개발자 블로그·학습용 예제에서 가장 많이 보이는 게 이것이지만, **최신 데이터는 아래 2·3번에 있을 것이다.**
2. **공공데이터포털 `15127578` — 식품의약품안전처_식품영양성분DB정보** (XML/JSON OpenAPI) — 이게 현행판으로 보임
3. **표준데이터셋 파일 다운로드 (권장)**
   - `15100070` 전국통합식품영양성분정보(**음식**)
   - `15100066` 전국통합식품영양성분정보(**가공식품**)
   - `15100065` 전국통합식품영양성분정보(**원재료성식품**)
   - 그리드 다운로드는 **5만 건 제한**, 전체는 API 사용 (확인됨)
4. 신규 포털: `식의약 데이터 포털 data.mfds.go.kr`, `K-FIND 식품영양성분 데이터베이스 foodsafetykorea.go.kr/fcdb/`

**라이선스:** 공공데이터포털 데이터는 통상 **공공누리 제1유형(출처표시)** 이지만, **데이터셋마다 `이용허락범위` 필드가 다르다.** 차단으로 확인 못 함 `[미검증]`. **다운로드 전에 각 데이터셋 페이지의 이용허락범위를 반드시 볼 것.** 1유형이면 번들해서 공개 배포해도 출처만 표기하면 된다.

### 6-2. 농촌진흥청 국가표준식품성분표 (RDA) — 2순위, 원재료 특화

| 항목 | 내용 |
|---|---|
| 최신판 | **제10개정판 (2022 발간), 국가표준식품성분 DB 10.0** |
| 규모 | **식품 3,272점 × 영양성분 130종 ≈ 25만 건** |
| 배포 | `koreanfood.rda.go.kr` (농식품올바로) 공지사항에서 **PDF 책자 + 엑셀 DB 무료 다운로드** |
| 공공데이터포털 | `15123901`, `15143721`, `15137343` 등으로도 파일 제공 |
| **라이선스** | **공공누리 제2유형 — 출처표시 + 비상업적 이용만** (제10개정판 책자 기준, 확인됨) |

**⚠️ 이 라이선스는 실제 제약이다.** 공공누리 2유형은 **상업적 이용 금지**다. Mybody가 순수 개인용이면 아무 문제 없지만, **나중에 유료화하거나 광고를 붙이면 RDA 데이터를 걷어내야 한다.** 식약처 데이터(1유형 추정)와 라이선스가 다를 수 있으니 **출처를 행 단위로 기록해두는 게 좋다** — 나중에 필터링할 수 있게.

**RDA vs 식약처:**
- RDA = **원재료 정밀 분석** (130종 영양소, 실측 기반). 깊지만 좁다.
- 식약처 = **음식 + 가공식품까지 포함**, 넓지만 얕다(탄단지 위주).
- **Mybody는 식약처가 맞다.** 탄단지 4개만 쓰는 앱에 130종 영양소는 필요 없고, 필요한 건 "제육볶음"이라는 행이다.

## 7. 바코드 → 제품 조회, 한국

여기서 중요한 구조적 발견이 있다.

**식약처 바코드 API 2종 (확인됨):**

| API | 이름 | 제공 필드 |
|---|---|---|
| `I2570` | 유통바코드 | 바코드번호, 품목보고번호, 업소명, 제품명, 최종수정일자, 제품분류 |
| `C005` | 바코드연계제품정보 | 품목보고번호, 보고일자, 생산중단일, 제품명, 유통기한, 식품유형, 제조사명, 업종, 주소, 폐업일자, **바코드** |

호출 예: `http://openapi.foodsafetykorea.go.kr/api/{KEY}/I2570/json/1/5/BRCD_NO={바코드}`

### 🔴 핵심: **이 API들은 영양성분을 주지 않는다.**

두 API의 필드 목록 어디에도 kcal/탄/단/지가 없다. 주는 건 **제품 신원(identity)** 뿐이다.

그래서 한국에서 바코드→영양은 **2-hop 조인**이 된다:

```
바코드 ──I2570/C005──▶ 품목보고번호 ──식약처 가공식품 영양DB──▶ kcal/탄/단/지
```

**이 조인이 얼마나 성공하는지는 `[미검증]`이고, 내 예상은 낙관적이지 않다:**
- 영양성분 입력 의무화가 **2023년 7월부터**다 → **그 이전 등록 제품은 영양 데이터가 비어있을 가능성이 크다.**
- 바코드가 등록된 제품과 영양이 등록된 제품의 집합이 일치한다는 보장이 없다.
- **실측 필요:** 삼각김밥·라면·단백질바 각 10개씩 스캔해서 조인 성공률을 재봐야 한다. 이게 바코드 기능 구현 여부를 결정하는 단일 실험이다.

**대안: `푸드QR` (portal.foodqr.kr)** — 실시간식품정보확인서비스. 바코드가 아니라 QR 기반의 신규 제도. 커버리지는 낮겠지만 영양정보를 직접 포함할 가능성이 있다. `[미검증 · 조사 가치 있음]`

**Open Food Facts 를 바코드 fallback 으로:** 한국 제품 커버리지가 낮을 것으로 보이나, 식약처 조인이 실패할 때의 2차 시도로는 쓸 만하다. 단 ODbL 귀속 표기 필요.

## 8. 편의점 도시락 · 삼각김밥 · 학식 · 배달

**결론: 재사용 가능한 오픈 데이터는 없다. 확인했다.**

검색 결과 요약이 명시적으로 말한다: **"공식적인 통합 API나 공개 데이터베이스는 발견되지 않았습니다."**

현실은 이렇다:

- **법적으로는 정보가 존재한다.** 식약처 식품표시기준에 따라 GS25/CU/세븐일레븐 모두 원재료명과 영양성분을 제품에 표시해야 한다. 확인된 디테일: GS25는 물 제외 중량 구성비율 기준, CU는 쌀 기준, 세븐일레븐은 정제수 넣고 만든 밥 기준으로 표시한다 — **회사마다 기준이 달라서 그대로 비교하면 안 된다.**
- **기계가 읽을 수 있는 형태로는 공개되지 않는다.** 각 사 홈페이지/앱에 흩어져 있고 API가 없다.
- **실제로 갖고 있는 곳:**
  - **FatSecret Korea** (`fatsecret.kr`) — `GS25 콩나물 불고기 삼각김밥`, `GS25 기본김밥` 등 **브랜드별 개별 항목이 실재한다.** 확인함.
  - **필라이즈 (Pillyze)** — `삼각김밥GS25` 등 국내외 음식·브랜드의 kcal/탄/단/지/당/나트륨/콜레스테롤 제공. DB 규모·API 공개 여부 `[미검증]`, 지원 메일로 문의 필요.
  - 둘 다 **크라우드소싱 또는 자체 구축**이며 **재배포 라이선스가 없다.** 스크래핑은 ToS 위반이고 하지 말아야 한다.
- **편의점 제품은 회전이 극심하다.** 시즌 한정·리뉴얼로 분기마다 라인업이 바뀐다. **어떤 정적 번들 테이블도 여기서는 반드시 낡는다.**

### 그래서 정직한 설계

**이 카테고리는 DB로 풀지 말고 UX로 푼다.**

1. **"나만의 음식" 등록** — 사용자가 제품 뒷면 영양성분표를 보고 한 번 입력 → 로컬 저장 → 다음부터 한 탭. 22세 남자 한 명이 반복해서 사 먹는 편의점 제품은 **현실적으로 20~40종**이다. 세 번째 주쯤이면 개인 DB가 완성된다.
2. **영양성분표 사진 OCR** — 사진 인식의 진짜 승부처는 음식 사진이 아니라 **뒷면 라벨**이다. 라벨 OCR은 (a) 인식 정확도가 훨씬 높고, (b) **양 추정 문제가 아예 없다** — 라벨에 "총 내용량 230g, 1회 제공량당 열량 340kcal" 이 인쇄돼 있다. **여기가 사진 기능의 최고 ROI 지점이다.** (인식 담당 에이전트에게 전달 권장)
3. **번들 테이블에는 브랜드 무관 대표값만** — "삼각김밥(참치마요) 대표값", "편의점 도시락(불고기류) 대표값" 수준. 정확도가 아니라 **빠른 근사 기록**용이고, 화면에 "브랜드별로 다릅니다" 를 띄운다.

### 판정

**FatSecret 이 유일하게 진지한 후보다.** 이유:
- **한국 데이터셋을 별도로 보유** — 조사한 상업 API 중 유일하게 `제육볶음`·`GS25 삼각김밥` 급 항목을 실제로 갖고 있는 게 확인됐다.
- Premier Free 가 **학생** 대상이라고 명시 — 22세 사용자 본인이 학생이면 신청 자격이 있을 수 있다. 귀속 표기만 하면 된다.
- 바코드 + 이미지 인식이 같은 API 안에 있어서 통합이 단순하다.

**하지만 프로토타입 단계에서 쓰면 안 된다.** 이유:
- **API 키가 노출된다.** zero-build 정적 페이지 + 백엔드 없음 = 키를 JS 안에 박아야 한다. FatSecret은 OAuth이므로 client secret 노출이 된다. 이건 ToS 위반이자 보안 사고다.
- **한국 데이터셋은 Premier 계열 = 심사/영업 대화가 필요하다.** 셀프서비스로 오늘 시작할 수 없다.
- 심사·계약을 통과하기 전까지 **Basic(미국 전용)** 밖에 못 쓰는데, 그건 한식에 무용하다.

→ **백엔드가 생기는 시점의 Phase 2 후보로 표시해두고, 지금은 건드리지 않는다.**

## 10. 복합요리 문제 — 최종 판정표

**"이 DB에 `제육볶음` 이라는 행이 실제로 있는가?"** 하나만 묻는다.

## 11. 번들 오프라인 한식 테이블 — 실측 기반

### 실측: 진짜 한식 데이터로

GitHub에 공개된 한식 영양 CSV (`boostcampaitech2/final-project-level3-cv-17` → `prototype/assets/Food_info.csv`, 식약처 식품코드 체계 `01011001` 형식 사용)를 받아서 측정했다.

**구성 — 335개 한식 요리, 중복 없음:**

| 카테고리 | 개수 |
|---|---|
| 국·탕·찌개류 | 60 |
| 밥류 | 59 |
| 면·만두류 | 43 |
| 나물·무침류 | 38 |
| 볶음류 | 27 |
| 전·부침류 | 20 |
| 튀김류 | 20 |
| 조림류 | 19 |
| 구이류 | 17 |
| 찜류 | 13 |
| 김치류 | 13 |
| 회류 | 6 |

각 행: 소분류명, **1회제공량(g)**, 칼로리, 탄수화물, 단백질, 지방.

**측정 결과 (`{n,g,k,c,p,f,cat}` 최소 스키마):**

| 형식 | 크기 | 행당 |
|---|---|---|
| compact JSON (UTF-8, 공백 없음) | **29,196 B = 28.5 KB** | 87.2 B |
| pretty JSON | 41.6 KB | — |
| **gzip -9** | **6,566 B = 6.4 KB** | 19.6 B |
| ASCII-escaped (`\uXXXX`) | 40.6 KB | — |

> **⚠️ 구현 주의:** `JSON.stringify` 가 한글을 `\uXXXX` 로 이스케이프하면 **28.5 KB → 40.6 KB (+42%)** 가 된다. **UTF-8 원문 그대로 저장하라.** gzip 후에는 차이가 줄지만 공짜로 낭비할 이유가 없다.

**샘플 행:**
```json
{"n":"쌀밥","g":210.0,"k":313.0,"c":70.0,"p":5.0,"f":1.6,"cat":"밥류"}
```

### Mybody 실전 스키마로 다시 계산

검색 별칭(`제육` → `돼지고기제육볶음`), 분량 프리셋, 나트륨을 더한 현실적 스키마:

```json
{
  "i": 10042,
  "n": "돼지고기제육볶음",
  "a": ["제육", "제육볶음", "돼지불백"],
  "c": "볶음",
  "u": [["1인분",200],["곱빼기",300],["반",100]],
  "kc": 214.0, "ca": 10.2, "pr": 15.1, "fa": 12.4, "na": 720
}
```
→ **행당 203 B** (실측)

| 항목 수 | raw JSON | gzip 추정 (실측 4.45× 압축비 적용) |
|---|---|---|
| 300 | 59.5 KB | **~13 KB** |
| 600 | 119 KB | **~27 KB** |
| **1,000** | **198 KB** | **~45 KB** |
| 2,000 | 397 KB | **~89 KB** |
| 5,000 | 991 KB | **~223 KB** |

### "한국 남자 한 명의 일주일 90%" 는 몇 개인가

**이건 실측값이 아니라 내 판단이다. 그렇게 읽어라.** 근거는 두 가지: (a) 위 335개 리스트는 원래 "한국인이 가장 많이 먹는 음식" 기준으로 뽑힌 이미지 데이터셋 클래스 목록이고, (b) 개인의 식단은 반복성이 극히 높다.

| 티어 | 항목 수 | 추정 커버리지 | raw / gzip |
|---|---|---|---|
| T0 필수 | 150 | ~70% | 30 KB / ~7 KB |
| **T1 권장 — 여기서 시작** | **350** | **~85%** | **71 KB / ~16 KB** |
| T2 충실 | 800 | ~93% | 162 KB / ~36 KB |
| T3 과잉 | 2,000 | ~97% | 397 KB / ~89 KB |

**판단: T1(350개) 로 시작.** 이유:
- **크기가 사실상 0이다.** 71 KB는 사진 한 장보다 작다. 로딩 체감 없음.
- **90%대 후반은 어차피 못 간다.** 나머지는 편의점 신제품·배달 브랜드·학식 메뉴인데, **이건 항목 수를 늘려서 잡히는 꼬리가 아니다.** T3까지 5배 불려도 진짜 꼬리는 그대로 남는다.
- 꼬리는 **"나만의 음식" 기능으로 사용자가 직접 메운다.** 그리고 그게 **완벽하게 정확하다** — 본인이 먹는 그 제품이니까.

### 번들 테이블 구축 절차

1. 공공데이터포털 `15100070` (음식) 파일 다운로드 — **이용허락범위 먼저 확인**
2. `15100065` (원재료성식품)에서 닭가슴살·계란·현미 등 헬스 필수 원재료 50~80개 추려 병합
3. 식약처 대분류로 상위 350개 선별 (국·탕·찌개, 밥, 면, 볶음, 구이, 튀김 편중 유지 — 위 카테고리 분포가 좋은 템플릿)
4. **별칭 테이블 수작업** — 이게 실제 노동이고 UX를 결정한다. `김찌`→`김치찌개`, `제육`→`돼지고기제육볶음`, `순댓국`/`순대국`/`순대국밥` 통합
5. **초성 검색 인덱스 생성** — 한국 앱에서 `ㄱㅊㅉㄱ` → `김치찌개` 는 선택이 아니라 필수. 유니코드 한글 음절에서 초성 추출은 `Math.floor((code-0xAC00)/588)` 산수 한 줄. 라이브러리 불필요
6. 행마다 `src` 필드로 출처 기록 (`mfds` / `rda` / `usda` / `user`) — **나중에 라이선스별로 걷어낼 수 있게**
7. UTF-8 그대로, compact JSON, 서버 gzip

## 12. 권장 스택 및 fallback 순서

### Phase 1 — 지금 (백엔드 없음, 정적 페이지)

```
①  번들 한식 테이블 (350행, 식약처 음식+원재료 기반)   ← 수동 선택의 기본
②  사용자 "나만의 음식" (localStorage)                ← 편의점/배달/학식 전담
③  라벨 사진 OCR로 ②에 등록                          ← 사진 기능의 최고 ROI
④  직접 입력 (kcal/탄/단/지 수동)                     ← 최종 fallback, 항상 열려있음
```

**외부 API 호출 0회.** 키 노출 없음, 오프라인 동작, 지연 없음, 비용 0원.

### Phase 2 — 백엔드가 생기면

```
①  번들 테이블 (캐시 / 즉시 응답)
②  식약처 OpenAPI (음식 + 가공식품 전체, 10만+ 건)      ← 서버에 키 보관
③  바코드 → 식약처 I2570/C005 → 품목보고번호 → 가공식품 영양DB
④  ③ 실패 시 → Open Food Facts 바코드 (ODbL 귀속 표기)
⑤  원재료만 필요할 때 → USDA FDC (CC0, 무제한, 무료)
⑥  사용자 "나만의 음식"
⑦  직접 입력
```

### Phase 3 — 선택 (제품화 시)

- **FatSecret Premier** (한국 데이터셋 + 브랜드 + 바코드 + 이미지 인식 통합). 학생 자격으로 Premier Free 시도 가치 있음.

## 13. 검증하지 못한 것 (구현 전 필수 확인)

1. **FDC 데이터 타입별 정확한 건수** — `fdc.nal.usda.gov` 차단. API `dataType` 필터로 직접 셀 것.
2. **Open Food Facts 총 제품 수** — **4M (검색 요약) vs 1.7M (repo README 직독)** 충돌. 그리고 **한국 제품 수는 완전 미확인.**
3. **식약처 DB 현재 총 건수 및 `음식` 분류 정확한 행 수** — 검색 하나가 "548건" 이라 했으나 **신뢰도 낮음.** 직접 다운로드해서 셀 것.
4. **식약처 각 데이터셋의 `이용허락범위`** — 공공누리 몇 유형인지 미확인. 번들 전 필수.
5. **`I2790` 이 레거시인지** — 이름에 `(~2023)` 이 붙어있어 동결로 보이나 확인 못 함. 현행 엔드포인트 확인 필요.
6. **🔴 바코드 → 영양 조인 성공률** — 가장 중요한 미검증 항목. **삼각김밥·라면·단백질바 각 10개 스캔 실험**으로 결정할 것. 성공률이 낮으면 바코드 기능은 만들지 말 것.
7. **FatSecret 한국 데이터셋의 규모와 Premier Free 학생 자격 조건** — 영업 문의 필요.
8. **필라이즈 API 공개 여부** — `support@pillyze.com` 문의.
9. **Nutritionix / Edamam / Spoonacular 가격** — 전부 **제3자 블로그 출처**다. 공식 페이지 차단으로 직접 확인 못 함. 계약 전 반드시 벤더 페이지에서 재확인.
10. **커버리지 % 추정치 (T0~T3)** — **측정값 아님. 내 판단.** 검증하려면 사용자가 2~4주 기록한 뒤 "테이블에 없어서 직접 입력한 비율"을 재면 된다. **이 지표를 앱에 심어두는 걸 권장한다** — 번들 테이블을 언제 키울지 데이터로 결정할 수 있다.

## 15. 다른 에이전트에게 전달할 사항

**사진 인식 담당에게:**
- **번들 테이블의 350개 음식명이 곧 분류기의 클래스 목록이 되어야 한다.** 인식 라벨과 DB 키가 일치하지 않으면 조회가 통째로 깨진다. 클래스 체계를 식약처 식품코드에 정렬시킬 것.
- **음식 사진보다 영양성분표 라벨 OCR이 ROI가 훨씬 높다.** 정확도도 높고 **양 추정 문제가 원천적으로 없다.** 편의점/가공식품 전체를 이걸로 덮을 수 있다.
- 실제 배포된 한식 이미지 데이터셋의 클래스 분포 참고용 (위 12카테고리 335클래스)이 스크래치패드에 있음.

**UI 담당에게:**
- 양 입력은 **그램 슬라이더 금지, 프리셋 탭**으로. `u: [["1인분",200],["곱빼기",300],["반",100]]` 구조가 그대로 버튼이 된다.
- **초성 검색 필수** (`ㄱㅊㅉㄱ` → 김치찌개).
- 복합요리에는 **"표준 레시피 기준 추정, ±25%" 배지**를 붙일 것. 사용자가 등록한 "나만의 음식"에는 붙이지 말 것 — 그건 라벨 실측값이라 정확하다. **이 구분이 앱의 정직성을 보여주는 지점이다.**
