### 1.3 Food-101 문제 — 요청에서 물어본 것

**"Food-101로 학습한 모델은 한국 음식에 거의 쓸모없다"는 명제는 맞습니다.** Food-101은 101개 서양 요리 클래스입니다. 여기에 김치찌개, 제육볶음, 순대국밥, 편의점 도시락은 **클래스로 존재하지 않습니다.** 존재하지 않는 클래스는 confidence가 낮게 나오는 게 아니라, **가장 비슷하게 생긴 서양 음식으로 자신 있게 틀립니다.** 김치찌개는 아마 `hot_and_sour_soup`이나 `pho`로, 제육볶음은 `pulled_pork_sandwich` 계열로 분류됩니다. 사용자가 보기에 "그럴듯하게 틀린" 결과가 나오고, 그게 침묵하는 실패보다 나쁩니다.

§1.1에서 본 `foodvisionai`가 광고하는 "94% accuracy across 101 categories"도 바로 이 함정입니다. **Food-101 테스트셋 안에서의 94%**이고, 한국 음식 사진에 대해서는 아무 의미도 없는 숫자입니다. 이런 수치를 근거로 제품 결정을 하면 안 됩니다.

FoodSeg103도 마찬가지로 한식 중심이 아닙니다. `p-garden/FoodSeg103_`(★0, 한국인 작성자)이 있다는 건 한국에서 시도는 되고 있지만 공개된 결과물은 없다는 뜻입니다.

## 2. 진짜 어려운 건 "이게 김치찌개다"가 아니라 "얼마나 먹었나"다

요청에서 이 점을 강조했고, 맞습니다. 구체적으로 왜 그런지 한식 기준으로 적습니다.

### 2.1 사진이 물리적으로 볼 수 없는 것

| 음식 | 사진에 안 보이는 것 | 칼로리 진폭 |
|---|---|---|
| **김치찌개** | 국물 아래 잠긴 돼지고기 양과 부위(목살 vs 삼겹), 들기름·참기름 양 | 300 → 700 kcal |
| **제육볶음** | 고추장 양념에 들어간 설탕량, 조리 중 흡수된 기름 | 450 → 900 kcal |
| **비빔밥** | 참기름 1작은술 vs 3작은술 | ±80 kcal (그냥 안 보임) |
| **삼겹살** | **내가 몇 점 먹었는지.** 불판은 공용임 | 400 → 1,400 kcal |
| **순대국밥** | 순대/내장 비율, 들깨가루, 밥 말았는지 | 500 → 900 kcal |
| **배달 치킨** | 조각 수, 튀김옷 흡유량 | 접시 사진 한 장으로 불가 |

카메라는 **표면**을 봅니다. 한식 칼로리의 지배 변수는 대부분 표면 아래에 있습니다(국물 속 고기, 흡수된 기름, 양념 설탕). 이건 모델 성능 문제가 아니라 **정보가 이미지에 존재하지 않는** 문제입니다. 더 좋은 모델로는 못 풉니다.

### 2.2 오차가 무작위가 아니라 편향이라는 게 진짜 문제

만약 사진 추정 오차가 ±30%지만 **무작위**라면, 이 앱은 괜찮습니다(§7에서 설명). 문제는 오차가 **먹는 음식 종류와 상관**된다는 겁니다.

- 닭가슴살·샐러드 → 구조가 다 보임 → 오차 작음
- 김치찌개·제육볶음·치킨 → 기름·설탕이 안 보임 → **체계적으로 과소추정**

즉 **잘 먹은 날은 정확하게, 많이 먹은 날은 적게** 기록됩니다. 이건 앱이 사용자에게 "너 잘하고 있어"라고 거짓말하는 방향으로 편향된다는 뜻입니다. 그리고 이 앱은 체중 변화로 칼로리를 재조정하므로, 로그가 "2,000 먹었다"는데 체중이 안 빠지면 엔진은 **계획이 틀렸다고 판단하고 칼로리를 더 깎습니다.** 실제로는 기록이 틀린 건데요. 이게 이 앱에서 사진 추정이 일으킬 수 있는 가장 구체적인 피해입니다.

### 2.3 그래서 사진의 올바른 역할

**사진은 숫자를 뱉으면 안 됩니다. 사진은 "무엇을 먹었는지"를 맞히고, "얼마나"는 사람에게 물어야 합니다.**

이건 이 앱이 인바디에서 이미 내린 결정과 정확히 같습니다 — OCR이 값을 제안하고, **검수 화면(P04)이 필수 게이트**이고, 사람이 확정합니다. 음식도 똑같이 갑니다.

```
사진 → LLM이 음식 이름 식별 (한식 이름으로, 여기는 잘함)
     → 앱이 양을 사람이 답할 수 있는 형태로 물음
        (공기밥 ½ / 1 / 1½,  고기 손바닥 1장 / 2장,  국물 다 먹음 / 반만)
     → 필수 검수 화면
     → 저장
```

사람도 양을 정확히는 모릅니다. 하지만 **"공기밥 한 공기 먹었나 반 공기 먹었나"는 압니다.** 모델은 그것조차 모릅니다. 사람에게 답할 수 있는 질문만 하면 사람이 모델보다 정확합니다.

### 2.4 한식의 숨은 장점 — 표준 단위가 있다

부정적인 얘기만 했는데, 한식에는 서양식에 없는 이점이 있습니다.

- **공기밥**은 사실상 표준화돼 있습니다. 식당 공기 한 공기는 대체로 일정합니다.
- **편의점 도시락·삼각김밥·컵라면에는 바코드와 영양성분표가 있습니다.** AI가 전혀 필요 없습니다.
- **학식**은 고정 메뉴이고 영양정보가 공개되는 경우가 많습니다.
- **배달음식**은 한 사람이 시키는 가게·메뉴가 매우 반복적입니다.

22세 한국 남성의 실제 식사 구성에서 **편의점 + 학식 + 배달 + 집밥**이 큰 비중을 차지한다면, 이 중 앞의 세 개는 **사진 AI 없이** 더 정확하게 기록됩니다. 이게 §7 결론의 핵심 근거입니다.

## 3. 기록 이탈률 — 검증 실패

**이번 세션에서 확인하지 못했습니다.** 구체적 수치(며칠 만에 몇 %가 그만두는지)를 기억에 의존해 적는 것은 이 문서의 신뢰도를 깨뜨리므로 적지 않습니다.

확실하게 말할 수 있는 것은 방향뿐입니다: **식단 기록의 이탈은 빠르고 크며, 이 앱의 설계에서 가장 큰 단일 리스크입니다.** 이건 §1에서 검증된 사실로도 간접 확인됩니다 — 음식 기록 프로젝트의 사망률 자체가 매우 높습니다(★100~587짜리가 5~6년째 방치).

설계상 이탈을 **전제로** 깔아야 한다는 것이 결론이고, 그건 수치 없이도 확정할 수 있습니다. §5의 "미기록일 처리"와 §7의 "최소 기록"이 그 전제 위에 서 있습니다.

> **다시 조사할 때 검색어:** `dietary self-monitoring adherence attrition randomized`, `MyFitnessPal retention 6 months cohort`, `app-based food logging dropout curve`, `식단 기록 앱 지속률`, `self-monitoring engagement weight loss trial`

## 4. 타 앱의 마찰 감소 장치 — 부분 검증

**MacroFactor, Cronometer, MyFitnessPal, Carbon, 눔의 실제 동작은 이번 세션에서 확인 불가** (전 도메인 차단). 아래는 **이 앱에 적용할 후보 기능 목록**으로만 읽어야 하며, 각 앱이 실제로 어떻게 구현했는지는 미검증입니다.

| 기능 | 이 앱에서의 가치 | 구현 비용 (정적 JS) |
|---|---|---|
| **최근 먹은 음식 / 즐겨찾기** | **최상.** §7 참조 | 낮음 (localStorage 배열) |
| **어제와 동일 복사** | **최상.** 탭 1회 | 낮음 |
| **끼니 템플릿("늘 먹는 아침")** | 높음 | 낮음 |
| **빠른 추가 (kcal+단백질만)** | **최상.** 포기 직전 사용자를 붙잡음 | 매우 낮음 |
| **바코드** | 높음 (편의점) | 중간 (카메라 + DB) |
| 음성 입력 | 중간 | 중간 |
| 위젯 | 해당 없음 (웹앱) | — |
| 사진 인식 | **중간** — §2의 이유로 과대평가됨 | 높음 |

측정된 효과 크기는 확인하지 못했습니다. 다만 **논리적으로 확실한 것**: 최근/즐겨찾기/어제복사는 한 사람의 식단이 반복적일수록 효과가 커집니다. 그리고 한 사람의 식단은 매우 반복적입니다. 사진 인식은 **처음 먹는 음식**에만 가치가 있는데, 그건 전체 끼니의 소수입니다. **즉 가장 비싼 기능이 가장 드문 상황을 처리합니다.** 이게 사진을 1순위로 만들면 안 되는 이유입니다.

## 5. 달성률을 어떻게 보여줄 것인가 (핵심 산출물)

여기부터는 이 저장소의 실제 코드에 근거하므로 신뢰도가 높습니다.

### 5.1 일간 — "남은 단백질 40g"이 "60% 달성"보다 낫다

**결론: 단백질은 "남은 양", 칼로리는 "밴드", 퍼센트는 일간 화면에서 쓰지 않습니다.**

근거:

1. **행동으로 번역되는가.** "단백질 40g 남음"은 다음 행동에 바로 매핑됩니다(닭가슴살 한 팩 ≈ 23g, 계란 2개 ≈ 12g). "60% 달성"은 목표값을 기억해내서 곱셈을 해야 행동이 됩니다. 일간 화면은 **행동 직전에 보는 화면**이므로 남은 양이 맞습니다.
2. **단위가 사용자의 언어와 같은가.** 그램은 음식 단위와 같은 차원입니다. 퍼센트는 아닙니다.
3. **음수가 되는 방향이 다르다.** 단백질은 남은 양이 0이 되면 "달성"으로 끝납니다(음수로 안 감). 칼로리는 남은 양이 음수가 되는데, **"-320 kcal 초과"는 빚처럼 읽히고 이게 §6의 위험 지점입니다.** 그래서 칼로리만 표시 방식을 다르게 가져갑니다.

**칼로리는 점이 아니라 밴드로.** 엔진이 주는 `intakeKcal`은 단일 값이지만, 그 값의 정밀도는 없습니다 (TDEE 추정 오차 + 기록 오차). 이 앱은 이미 인바디에서 "노이즈보다 작은 차이는 차이가 아니다"라고 말합니다. 같은 논리로 **목표 ±10%를 "범위 안"으로 표시하고, 그 안에 있으면 초록**으로 둡니다. 2,400 kcal 목표면 2,160~2,640이 정상입니다. 2,500을 먹고 빨간불이 켜지는 앱은 거짓 정밀도를 파는 겁니다.

**링 vs 바:** **바를 쓰세요.** 이유 두 가지 — (a) 링은 100%를 넘는 상태와 **목표 밴드**를 표현하기 어렵습니다. 바는 목표 눈금(tick)과 밴드 음영을 자연스럽게 얹습니다. (b) **이 앱에는 이미 `macroBar`가 있습니다** (`prototype/js/screens/plan.js:287-289`에서 단백질/탄수화물/지방에 사용 중). 플랜 화면과 기록 화면이 같은 시각 언어를 쓰면 "목표 ↔ 실제"가 한 눈에 대조됩니다. 새 컴포넌트를 만들 이유가 없습니다.

### 5.2 주간·월간 — 여기서는 퍼센트와 평균이 맞다

일간과 반대입니다. 주간/월간 화면은 **행동 직전이 아니라 복기 시점**에 봅니다. 할 행동이 없으므로 "남은 양"은 의미가 없고, 추세와 비율이 의미를 갖습니다.

권장 구성:

**주간 (7칸)**
```
단백질   목표 165g
┌───┬───┬───┬───┬───┬───┬───┐
│▇▇▇│▇▇ │▇▇▇│ · │▇▇▇│▇▇▇│▇▇ │   ← 일별 바, 목표선 가로로 관통
└───┴───┴───┴───┴───┴───┴───┘
 월  화  수  목  금  토  일
 기록한 6일 평균 152g (목표의 92%)     ← 분모를 명시
 · = 기록 없음 (1일)
```

핵심은 **일별 바 + 목표선 + 평균 한 줄 + 기록일수 명시**입니다. 단일 숫자만 보여주면 "평균은 맞는데 널뛰기"인 상태를 놓칩니다. 특히 단백질은 주 평균보다 **매일 충족 여부**가 중요합니다.

**월간**: 7×4~5 캘린더 그리드. 칸 하나 = 하루, 색은 **칼로리 밴드 기준 3색**(범위 안 / 아래 / 위), 칸 안 작은 점 하나로 단백질 목표 충족 여부. 미기록일은 **회색 빗금**(0이 아니라 "없음"). 월간에서 보려는 건 정확한 값이 아니라 **패턴**입니다 — 주말에 무너지는지, 시험기간에 끊기는지.

### 5.3 단일 "순응도 점수"는 사용자에게 보여주지 않는다

**반대 논거 (채택):**
- 4개 차원(kcal, 탄, 단, 지)을 하나로 뭉개면 **무엇을 고쳐야 하는지가 사라집니다.** "72점"은 행동을 지시하지 않습니다. "단백질만 계속 부족"은 지시합니다.
- 점수는 **도덕적으로 읽힙니다.** 82점 → 92점은 성적표이고, 이 앱은 성적을 매기는 앱이 아닙니다. §6 참조.
- **게임 가능합니다.** 목표에 맞춘 기록을 하게 만드는 유인이 생기고, 그러면 로그가 오염되어 §7의 전체 루프가 망가집니다. 이게 실용적으로 가장 심각합니다.

**찬성 논거:** 주간 체크인에 넣을 단일 추세선이 필요하고, 압축이 됩니다.

**결론 — 둘 다 취합니다.** 내부적으로는 점수를 계산합니다. 이 저장소는 이미 그걸 요구합니다:

```js
// prototype/js/engine.js:1010
if (adherence && adherence.dietPct < 70) {
  suggestions.push({ kind: 'adherence', title: '칼로리는 그대로 두고 순응도부터',
    detail: '식단 준수도가 ' + adherence.dietPct + '%입니다. 계획이 틀린 게 아니라 ...' });
  return { status: 'adherence', suggestions: suggestions };
}
```

`checkinAdvice()`는 이미 `dietPct` 하나를 먹습니다. 지금은 그 값이 P08 체크인의 **상/중/하 자기 신고**에서 옵니다 (`prototype/js/screens/checkin.js:7`). 기록 탭이 생기면 **측정값으로 그 자리를 채우되, 사용자에게는 점수를 화면에 띄우지 않고 구성요소만 보여줍니다.**

그리고 자기 신고를 없애지 말고 **검수 패턴을 그대로 적용하세요**: 기록이 충분하면 상/중/하를 자동 선택해 **미리 채워두고**, 사용자가 덮어쓸 수 있게 둡니다. P04에서 OCR이 제안하고 사람이 확정하는 것과 같은 구조입니다.

### 5.4 미기록일 처리 — 이 절이 가장 중요합니다

요청에서 "달성률을 거짓말하게 만드는 고전적 버그"라고 지적했고, 정확합니다. 그리고 **이 앱에서는 그게 단순한 표시 버그가 아니라 처방 오류로 번집니다.**

**산수로 보겠습니다.** 목표 2,400 kcal. 5일은 정확히 2,400 먹고 기록, 2일은 기록 안 함(실제로는 대충 목표치 먹음).

| 처리 방식 | 주 평균 | 화면에 뜨는 말 | 결과 |
|---|---|---|---|
| **미기록 = 0 kcal** (버그) | (5×2400+0)/7 = **1,714** | "목표의 71%" | **재앙** — 아래 참조 |
| 미기록 = 목표치로 채움 | 2,400 | "100% 달성" | 거짓 순응. 실제로 폭식했어도 100% |
| **기록된 날만 평균 + 분모 명시** | **2,400 (5/7일)** | "기록한 5일 평균 2,400 · 2일 기록 없음" | **정답** |

**0으로 채우면 왜 재앙인가:** 엔진은 주간 체크인에서 **실제 체중 변화**와 섭취를 대조해 칼로리를 재조정합니다. 로그가 "주 평균 1,714 kcal"이라고 말하는데 체중이 안 빠지면, 엔진이 내릴 수 있는 결론은 "이 사람 대사가 예상보다 훨씬 낮다"뿐입니다. 그러면 **목표 칼로리를 더 깎습니다.** 실제로는 2,400을 먹고 있었는데요. 미기록일 하나가 사용자의 처방을 실제로 더 굶기는 방향으로 밉니다. 이건 가설이 아니라 `checkinAdvice()`의 동작에서 직접 따라 나옵니다.

**규칙 3개:**

1. **미기록일은 절대 0으로 치환하지 않습니다.** 분모에서 빼고, 뺐다는 사실을 화면에 씁니다.
2. **기록 노이즈 바닥.** 주 7일 중 **4일 미만** 기록이면 **주간 평균을 아예 표시하지 않습니다.** 숫자 대신 이렇게 씁니다:
   > 이번 주 기록이 2일뿐입니다. 평균을 내도 의미가 없어서 표시하지 않습니다.
   
   그리고 같은 조건에서 **`dietPct`를 엔진에 넘기지 않습니다** (`null`로 넘겨 체크인이 자기 신고로 되돌아가게). 이건 이 앱이 이미 하는 일과 정확히 같은 종류의 판단입니다 — "측정 간격이 4주 미만인 추세는 판정에 아예 쓰지 않는다"(README §4). **기록에도 같은 바닥을 놓는 겁니다.**
3. **부분 기록일 구분.** "아침·점심만 기록"과 "하루 종일 기록"은 다릅니다. 끼니 슬롯 기준으로 2/4 이하만 채워진 날은 **부분 기록**으로 따로 표시하고 평균에서 제외하거나 별도 표기합니다.

## 6. 넛지 — 그리고 "그만 먹어"에 대한 정직한 답

### 6.1 연구 부분은 검증 실패

**알림 피로, 제한적 메시지의 역효과, 칼로리 추적 앱과 섭식장애의 연관에 대한 연구를 이번 세션에서 확인하지 못했습니다.** 구체적 연구명·수치·저자를 적지 않습니다.

다만 이 주제에 대해 **연구를 인용하지 않고도 확정할 수 있는 것**이 있고, 그게 실제 설계 결정을 다 커버합니다. 아래는 논증입니다.

> **다시 조사할 때 검색어:** `calorie tracking app disordered eating young adults`, `食 fitness app orthorexia association`, `notification fatigue mHealth disengagement`, `restrictive messaging backfire eating behavior`, `EAT-26 calorie tracking college men`, `칼로리 추적 앱 섭식장애`

### 6.2 "그만 먹어"는 쓰면 안 됩니다 — 이유는 안전 때문만이 아닙니다

오너가 직접 요청한 문구입니다. 거절이 아니라 **더 나은 대안으로 바꾸자**는 제안입니다. 이유 세 가지:

**(1) 명령이 아니라 정보여야 합니다.** "그만 드세요"는 앱이 사용자에게 내리는 **지시**입니다. "오늘 목표치를 다 채웠습니다"는 **상태 보고**입니다. 정보는 같지만 후자는 결정권을 사용자에게 남겨둡니다. 결정권을 뺏는 앱은 (a) 지켰을 때 자기 공로가 안 되고 (b) 어겼을 때 죄책감이 생깁니다. 둘 다 지속성을 깎습니다.

**(2) 행동할 수 없는 시점의 지적은 죄책감만 남깁니다.** 저녁 9시에 "오늘 500kcal 초과했습니다"라고 말해봐야 되돌릴 수 없습니다. 순수한 벌점입니다. **되돌릴 수 있는 시점에만 말하거나, 아예 말하지 않습니다.**

**(3) 22세 남성은 위험군이 아닌 게 아닙니다.** 남성의 섭식 문제는 마른 몸이 아니라 **근육질 몸**을 향하는 형태로 나타나고, 매크로 추적·바디프로필·커팅은 그 경로 위에 정확히 있습니다. 이 앱은 이미 **커팅모드**와 **단기커팅**을 제공합니다. 그 사용자에게 "그만 먹어"를 말하는 앱은 잘못된 방향으로 밀 수 있습니다. 오너 본인이 사용자이므로 이건 추상적 우려가 아닙니다.

### 6.3 설계 규칙: 더하는 넛지는 되고, 막는 넛지는 안 된다

이게 이 절의 핵심 규칙입니다.

| 유형 | 예 | 판정 |
|---|---|---|
| **덧셈형** | "단백질 40g 남았습니다" | **허용.** 행동 가능, 긍정 방향, 목표 지향 |
| **상태 보고** | "오늘 섭취 목표를 채웠습니다" | **허용.** 사실만 |
| **금지형** | "그만 드세요", "더 먹으면 안 됩니다" | **금지** |
| **사후 질책** | "어제 800kcal 초과했습니다" | **금지** |
| **누적 부채** | "이번 주 누적 초과 2,300kcal" | **금지.** 갚아야 할 빚처럼 읽힘 |
| **연속 기록 스트릭** | "17일 연속! 깨지 마세요" | **금지.** 하루 놓치면 완전 이탈 유발 |

단백질 부족 넛지는 **덧셈형이라 안전합니다.** 오너 요청 중 "단백질 부족하면 말해줘"는 그대로 구현하면 됩니다. "많이 먹었으면 그만 먹으라 해줘"만 상태 보고로 바꿉니다.

### 6.4 침묵 규칙

말하지 않는 게 기본값입니다.

1. **첫 14일은 어떤 넛지도 띄우지 않습니다.** 기록 습관이 붙기 전에 평가하면 이탈합니다.
2. **하루 최대 1회.**
3. **마지막 끼니 시간대(설정값, 기본 21시) 이후에는 칼로리 관련 넛지 금지.** 되돌릴 수 없으므로.
4. **단 하루의 초과로는 절대 말하지 않습니다.** 칼로리 관련은 **7일 이동평균이 밴드를 벗어났을 때만.** 하루 변동은 노이즈입니다 — 이 앱의 기존 철학 그대로입니다.
5. **유지모드·회복모드·근성장모드에서는 초과 관련 넛지를 끕니다.** 회복모드는 의도적으로 섭취를 올리는 국면인데 거기서 "많이 먹었다"고 말하면 처방과 모순됩니다.
6. **기록이 부족한 주에는 아무 판단도 하지 않습니다** (§5.4 규칙 2).
7. **설정에 전체 OFF 스위치**를 둡니다. 기본 ON, 한 번의 탭으로 영구 OFF.

## 7. Mybody에 필요한 최소 기록 UX — 그리고 왜 MyFitnessPal 클론이 틀렸는가

### 7.1 결정적 사실: 이 앱은 이미 체중으로 루프를 닫는다

Mybody는 **주간 체크인에서 실제 체중 변화로 칼로리를 재조정**합니다. 이 하나가 모든 걸 바꿉니다.

**체중 변화가 진실이고, 식단 기록은 "왜"를 설명하는 보조 자료입니다.**

따라서 **식단 기록은 절대값이 정확할 필요가 없습니다. 편향이 일정하기만 하면 됩니다.** 로그가 매일 20% 과소 기록해도, 체중 기반 재조정이 그 편향을 흡수합니다. 목표 칼로리가 "로그 기준 2,000"으로 수렴할 뿐이고, 그 숫자로 관리하면 결과는 똑같이 나옵니다.

이게 §2의 사진 정확도 문제를 **거의 해소합니다.** 그리고 동시에 진짜 위험이 무엇인지 알려줍니다:

> **정확도가 아니라 일관성이 전부입니다.**
> ±30% 오차로 매일 기록 > 정확하지만 9일 만에 그만둠
> 그리고 최악: **잘 먹은 날만 기록하고 과식한 날은 안 함** — 이건 편향을 들쭉날쭉하게 만들어 루프를 망가뜨립니다.

설계 우선순위가 여기서 바로 나옵니다: **가장 귀찮은 날에도 기록이 남게 만드는 것**이 1순위이고, 정확도는 2순위입니다. 사진 AI는 정확도 쪽 도구이므로 1순위가 아닙니다.

### 7.2 엔진이 이미 기록 수준을 처방하고 있습니다

코드에서 발견한 것인데, 설계에 직접 써야 합니다.

```js
// prototype/js/engine.js:87-88
p.tracking = a < 0.34 ? '단백질만 대충 기록'
           : (a < 0.7 ? '칼로리 + 단백질 기록' : '4대 매크로 전부 + 주 4회 체중');
```

공격성 `a`에 따라 **필요한 기록 정밀도가 이미 다르게 처방됩니다.** 지금은 플랜 화면에 글자로만 떠 있고 기록 UI와 연결돼 있지 않습니다. **연결해야 합니다.**

| 처방된 tracking | 기록 탭이 요구하는 것 | 화면에 보이는 것 |
|---|---|---|
| `단백질만 대충 기록` (a<0.34, 하 강도) | **단백질 1개** | 단백질 바 하나. 탄수/지방 숨김 |
| `칼로리 + 단백질 기록` (0.34≤a<0.7) | kcal + 단백질 | 바 2개 |
| `4대 매크로 전부 + 주 4회 체중` (a≥0.7) | 전부 | 바 4개 |

**"하" 강도를 고른 사용자에게 탄수화물 그램을 묻는 건 앱이 자기 처방을 어기는 겁니다.** 그리고 "하"는 README가 "중도 포기 확률 최저"라고 설명하는 모드인데, 기록 부담을 최대로 주면 그 설계 의도가 무너집니다.

이게 "최소한의 기록 UX"에 대한 답입니다 — **앱이 이미 답을 갖고 있었고, 화면에 연결만 안 돼 있었습니다.**

### 7.3 MyFitnessPal 클론이 틀린 이유

| MFP가 하는 것 | Mybody에 필요한가 |
|---|---|
| 수백만 개 크라우드소싱 음식 DB | **아니오.** 1인 사용자. 실제로 먹는 음식은 수십 종 |
| 레시피 빌더, 재료 단위 계산 | **아니오** |
| 미량영양소 전체 | **아니오.** 엔진은 kcal/P/C/F만 씀 |
| 소셜, 뉴스피드 | **아니오** |
| 운동으로 칼로리 "벌기" | **절대 아니오.** 이 앱의 TDEE 모델과 이중계산 충돌 + §6 위험 |
| **최근/즐겨찾기** | **예 — 1순위** |
| **빠른 추가** | **예 — 1순위** |
| **바코드** | **예 — 2순위** |

### 7.4 진짜 최소 버전 (단계별)

**1단계 — 이것만으로도 작동합니다 (사진 없음, AI 없음)**

1. **내 음식 테이블**: 사용자가 실제로 먹는 30~60개 항목. 처음엔 비어 있고, 먹을 때마다 쌓임. localStorage.
2. **최근 / 자주 먹음**: 기록 화면 맨 위. **탭 1회로 추가.**
3. **어제와 동일**: 버튼 1개.
4. **빠른 추가**: 음식 이름 없이 `kcal`과 `단백질`만. 외식·술자리처럼 도저히 못 쪼개는 상황용. **이게 "기록 안 함"을 막는 최후의 방어선이고, 가장 저평가된 기능입니다.**
5. **양 프리셋**: 자유 그램 입력 금지. `½ · 1 · 1½ · 2` 배수 + 한식 단위(공기밥, 손바닥, 한 팩).

2~3주 쓰면 최근 목록이 대부분의 끼니를 덮습니다. 이 시점에서 기록 1회 = **탭 2~3번, 5초**입니다. 여기서 이미 이깁니다.

**2단계** — 바코드(편의점). **3단계** — 사진(LLM, 처음 먹는 음식 전용).

**사진이 3단계입니다.** 오너가 1번으로 요청한 기능이지만, 가장 비싸고 가장 드문 상황을 처리하며 §2의 정확도 문제를 안고 있습니다. 1단계가 먼저 돌아가야 사진이 가치를 갖습니다.

### 8.1 번호 배정과 네비게이션

**주의 — 문서와 코드의 번호가 다릅니다.** `docs/design/ia-screens.md`는 P01~P14를 쓰지만 **실제 구현(`prototype/js/app.js:5-8`)은 P00~P13**입니다 (P02 홈, P07 플랜, P08 체크인, P09 추이, P12 설정). **아래는 실제 코드 기준**이며, 다음 빈 번호는 **P14**입니다. 팝업은 M36까지 쓰였으므로 **M37**부터입니다.

**네비 자리 문제 — 정면으로 다룹니다.** 하단 네비는 5칸이 다 찼습니다:


월간은 정확한 값이 아니라 **패턴**을 봅니다. "주말에 끊긴다"는 관찰은 비난이 아니라 정보이고, 실제로 행동을 바꿀 수 있는 유일한 종류의 피드백입니다.

### 8.9 넛지 구현 규칙 (의사코드)

```js
function shouldNudge(state, now) {
  var s = state.dietSettings;
  if (!s.nudges) return null;
  if (daysSinceFirstLog(state) < 14) return null;        // 침묵 1
  if (nudgedToday(state, now)) return null;              // 침묵 2

  var mode = state.plan.mode;
  var today = todayTotals(state);
  var target = state.plan.macros;

  // 덧셈형 — 허용
  var remainP = target.proteinG - today.proteinG;
  if (now.getHours() >= 15 && remainP >= 20) {
    return { type:'protein',
      text:'단백질 ' + remainP + 'g 남았습니다.\n닭가슴살 한 팩(100g) 또는 계란 3개면 채워집니다.' };
  }

  // 초과 관련 — 침묵 3,4,5 전부 통과해야 함
  if (now.getHours() >= s.lastMealHour) return null;                   // 침묵 3
  if (['recovery','maintain','bulk'].indexOf(mode) >= 0) return null;  // 침묵 5

  var w = weeklyMacros(last7Days(now));
  if (!w.sufficient) return null;                                      // 침묵 6 / §5.4
  var over = w.avgKcal - target.intakeKcal;
  if (over > target.intakeKcal * 0.10) {                               // 침묵 4: 7일 평균만
    return { type:'over',
      text:'최근 7일 평균이 목표보다 하루 ' + Math.round(over) + 'kcal 높습니다.\n' +
           '한 주 더 보고 판단해도 됩니다. 지금 계획을 바꿀 필요는 없습니다.' };
  }
  return null;
}
```

`'그만'`, `'금지'`, `'실패'`, `'초과했습니다'` 같은 문자열이 이 함수에서 나오지 않는다는 점을 봐주세요. 의도된 것입니다.

## 9. 오너 요청에 대한 직답

| 요청 | 답 |
|---|---|
| "사진 찍으면 자동 인식해서 칼로리·탄단지 분석" | **부분적으로만 가능합니다.** 음식 이름 맞히기는 LLM으로 됩니다. **양 추정은 안 됩니다** — 모델 성능이 아니라 정보가 사진에 없습니다(§2.1). 그래서 사진 → 음식 식별 → **사람이 양 선택** → 검수 → 저장 구조로 갑니다. 인바디와 같은 패턴입니다. |
| "오픈소스 중에 이런 거 있나 봐봐" | **쓸 만한 게 없습니다.** 한국 음식 인식은 별 1개짜리 학부 과제뿐(§1.2). 포션 추정의 유일한 기반인 Nutrition5k는 **구글이 아카이브했고 5년 3개월째 방치**(§1.1). 살아있는 오픈소스 트래커 3개는 **전부 자체 비전 모델을 포기**하고 바코드/외부 LLM을 씁니다. |
| "직접 선택해서 기록" | **이게 1순위입니다.** 최근/즐겨찾기/어제복사/빠른추가. 2~3주면 탭 2번에 5초. 사진보다 먼저 만들어야 합니다(§7.4). |
| "주간·월간 탄단지 달성률" | §8.4, §8.5. **미기록일을 0으로 치지 않는 것**이 전부입니다. 안 그러면 숫자가 거짓말하고, 이 앱에서는 **처방까지 틀어집니다**(§5.4). |
| "단백질 부족하면 말해줘" | **그대로 구현합니다.** 덧셈형 넛지라 안전합니다. `단백질 40g 남았습니다 · 닭가슴살 한 팩이면 채워집니다` |
| "많이 먹었으면 그만 먹으라 해줘" | **문구를 바꾸자고 제안합니다.** "그만 드세요"는 명령이고, 하루 초과로 말하면 노이즈에 반응하는 것이며, 저녁에 말하면 죄책감만 남습니다. 대신 **상태 보고 + 7일 평균 기준 + 21시 이전에만**: `최근 7일 평균이 목표보다 하루 320kcal 높습니다. 한 주 더 보고 판단해도 됩니다.` 정보는 같고 결정권은 오너에게 남습니다(§6.2~6.5). |
