## 0. 결론 먼저

**사진 자동인식으로 칼로리·탄단지를 "정확하게" 뽑는 것은 2026년 9월 현재 오픈소스로도, 상용으로도 안 됩니다.** 안 되는 이유가 "김치찌개를 못 알아봐서"가 아닙니다. **접시에 몇 g이 올라가 있는지를 사진 한 장으로 알 수 없기 때문입니다.** 이건 모델을 바꿔서 해결되는 문제가 아니라 단안(monocular) 이미지의 정보량 한계입니다.

그래서 권고는 이렇습니다.

| | 권고 | 이유 |
|---|---|---|
| **1순위 · 지금 만들 것** | **수동 기록 (검색 + 1인분 프리셋 칩)** | 한식은 "1인분" 단위 배식이 표준화돼 있어서 서양식보다 수동 추정이 훨씬 정확함. 무료 공공 DB로 커버 가능 |
| **2순위 · 사진은 "보조"로만** | 사진 → VLM이 **음식명 후보 + 기본 1인분**을 채워주고, **사용자가 양을 확정** | 사진의 강점은 "무엇"이지 "얼마나"가 아님 |
| **하지 말 것** | 사진 찍으면 kcal 숫자가 확정값처럼 뜨는 UI | 이게 정확히 NIH 연구가 때린 지점. 앱이 이미 "InBody 측정 노이즈 이하면 변화라고 말 안 한다"는 원칙을 쓰고 있는데, 여기서 그 원칙을 깨면 앱 전체 신뢰가 무너짐 |
| **한국 음식 모델 자체 파인튜닝** | **혼자 쓰는 앱에서는 비추천** | 데이터는 존재하지만 라이선스·용량·유지비 대비 이득이 "음식명 맞히기"뿐이고, 정작 병목인 양 추정은 해결 안 됨 |

**Food-101 기반 모델은 한국 음식에 사실상 무용지물이 맞습니다.** Food-101 101개 클래스 중 한식은 `bibimbap` **1개뿐**입니다. 김치찌개·제육볶음·순대국밥·삼겹살·편의점도시락·학식은 아예 클래스에 없습니다. (Food-101 클래스 목록은 [alpapado/food-101 classes.txt](https://github.com/alpapado/food-101/blob/master/data/meta/classes.txt)에서 직접 확인 가능 — Foodspotting.com 2014년 인기 메뉴 기반이라 서구 편향)

## 1. 핵심 증거: 포션(양) 추정이 병목이라는 것

### 1-1. NIH 연구 (가장 결정적)

- **무엇:** 미국 NIH Clinical Center의 metabolic kitchen에서 **정밀 계량된 102끼**를 사진 촬영 → 사진 기반 칼로리 앱 4종에 투입
- **테스트된 앱:** MyFitnessPal, Lose It!, **Cal AI**, Appediet
- **결과:** 전 앱이 **칼로리를 약 33% 과소추정**. 한 끼당 평균 **250~345 kcal 적게**, **지방은 약 30 g 적게** 계산
- **특히:** 저탄수·고지방(케토) 식단에서 오차 더 큼 — **지방을 일관되게 놓침**
- **연구진 코멘트 (NIDDK, Aaron Hengist):** *"포션을 조정하거나 양을 직접 입력하지 않고 사진 기반 앱을 쓰는 사람은 결과를 걸러서 받아들여야 한다"*
- **발표:** Olivia Charles (NIDDK postbac fellow), **NUTRITION 2026 학회 발표**

⚠️ **정직하게 짚을 점:** 이건 **학회 초록 발표**이고, 제가 확인한 건 2차 보도(Medscape, ScienceDaily, Healio, MedicalDaily, 서울신문)입니다. **피어리뷰 완료된 정식 논문이 아닙니다.** 숫자는 여러 매체에서 일관되게 250~345 kcal / ~30 g fat / ~33%로 보도되고 있습니다. 원 논문 대조는 못 했습니다.

### 1-2. GPT-4V / LLM 계열 연구

- **Dietary Assessment with Multimodal ChatGPT (arXiv 2312.08592):** GPT-4V의 **포션 추정 MAE 54.6 g**, 사람은 43.6 g. 즉 **GPT-4V가 사람보다 못함.** (저조도 조건에선 영양사 48.5 g vs GPT-4V 46.3 g로 비슷 — 조건 의존적)
- **2025~2026 평가 연구들:** 음식 **식별(identification)은 93% precision** 수준으로 잘 함. 그런데 **에너지 추정 MAPE 26~36%**. 재료 목록을 텍스트로 같이 주면 13.9%까지 떨어짐 → **"보는 것"은 되는데 "양"이 안 되고, 텍스트로 양을 주면 확 좋아진다**는 결론
- ⚠️ 이 수치들은 검색 요약 경유이고 arXiv/ScienceDirect 원문은 차단되어 대조 못 함. `[부분 확인]`

### 1-3. 학계의 정리: "vision is fine, volume is the bottleneck"

- **서베이 논문 "Food Portion Estimation: From Pixels to Calories"** (arXiv **2602.05078**, 2026-02-04, Gautham Vinod) — 2D 이미지에서 3D 크기 추정이 근본 한계임을 정리. 해법으로 **depth map, multi-view, template matching**을 다룸 = *보조 입력 없이는 안 된다*는 뜻
- 관련 계열: MFP3D (arXiv 2411.10492, 3D point cloud), "Size Matters" (arXiv 2601.20051, real-scale 3D from monocular), DPF-Nutrition (arXiv 2310.11702, depth prediction + fusion)

### 1-4. Google Nutrition5k — 이 분야 최고 수준의 실측 기준선

- **저장소:** [google-research-datasets/Nutrition5k](https://github.com/google-research-datasets/Nutrition5k) — **실제로 살아있음, CC BY 4.0** (상업적 이용 가능)
- **내용:** 구글 카페테리아 음식 **약 5,000 접시**, RGB 영상 + **depth 이미지** + **재료별 실측 중량** + 고정밀 영양 라벨, 250+ 재료
- **성능 (CVPR 2021 논문):**
  - 2D 직접 예측: **칼로리 MAE 26.1%**, 매크로 MAE 31.9%
  - **Depth 사용 (볼륨 추정 + per-gram 모델):** 칼로리 MAE **16.5%**, 매크로 MAE **26.2%**
- **해석:** 구글이 **전용 스캐닝 리그로 깊이까지 찍어서** 최선을 다한 결과가 **칼로리 오차 16.5%**입니다. 폰 카메라 사진 한 장으로는 그 아래로 못 갑니다. 그리고 **서양식 카페테리아 음식**이라 국·탕·찌개(국물 속에 내용물이 잠겨 안 보임)는 더 어렵습니다.

### 1-5. 한식 특유의 추가 난이도 — 반드시 인지할 것

1. **국물 요리:** 순대국밥·김치찌개는 **내용물이 국물에 잠겨서 위에서 안 보임.** 건더기 양 = 사진으로 원천적으로 불가
2. **비빔밥:** 섞기 전/후 형태가 완전히 다르고, 섞은 후엔 개별 재료 분리 불가
3. **반찬 다수:** 한 상에 5~10개 반찬. 각각 소량이고 **얼마나 먹었는지가 아니라 얼마나 나왔는지**만 사진에 찍힘 (남긴 양 미반영)
4. **기름:** 제육볶음·잡채의 조리 기름은 **사진에 안 보이면서 칼로리의 30~40%**를 차지. NIH 연구에서 지방 30 g 과소추정이 바로 이것
5. **삼겹살:** 불판 위 생고기 → 굽고 기름 빠짐 → 실제 섭취량은 굽기 전 중량과 다름
6. **공기밥:** 식당마다 **180~230 g** 편차. 사진으로는 그릇 크기까지만 추정 가능

### 4-4. 2026년 최신 벤치마크: DiningBench

- **DiningBench: A Hierarchical Multi-view Benchmark for Perception and Reasoning in the Dietary Domain**
- **ACL 2026 Main**, 메이투안(Meituan) 제작, [github.com/meituan/DiningBench](https://github.com/meituan/DiningBench) — **코드 공개**
- 구성: **3,021개 음식**, 항목당 평균 **5.27장** (multi-view), 같은 메뉴 내 hard negative 포함, 검증 기반 영양 데이터
- 평가: **29개 SOTA VLM** (proprietary 10개 — GPT-4o, Gemini-3-Pro 등 / 오픈소스 19개 — Qwen-2.5-VL, InternVL2 등)
- 3단계 과제: **Fine-Grained Classification / Nutrition Estimation / VQA**
- **결과: 최고 fine-grained 정확도 81.83% (Gemini-3-Flash-Preview)**
- 저자 결론: *"현재 VLM들은 일반 추론은 잘하지만 **세밀한 시각 구별과 정밀한 영양 추론에서 크게 고전한다**"*, 5가지 주요 실패 모드 식별
- 영양 추정 방식: 판매자 제공 라벨 + LLM 추정 재료 목록 → USDA FoodData Central 대조 + 수동 검증

⚠️ **메이투안 = 중국 회사이므로 중국 요리 중심일 가능성이 높습니다. 한식 포함 여부 `[미확인]` (arxiv.org, alphaxiv.org, huggingface.co 전부 차단).**

🔴 **그런데 숫자가 말해주는 게 있습니다: 2026년 최신 VLM 29개 중 최고가 81.83%.** 2022년 IEEE 논문의 한식 150클래스 전용 CNN이 **81%**. **4년 차이, 범용 최신 VLM vs 전용 구형 CNN — 거의 같습니다.** 이건 **"전용 모델을 파인튜닝해도 범용 VLM 대비 얻는 게 별로 없다"**는 강력한 증거입니다.

## 5. 6번 질문에 대한 답: 파인튜닝 vs VLM+DB

### 판정: **파인튜닝은 하지 마세요. VLM + 한국 영양 DB 조회가 맞습니다.** 그리고 **둘 다 "보조"여야 합니다.**

**근거:**

| 논점 | 파인튜닝 | VLM + DB |
|---|---|---|
| **달성 가능 정확도** | AI Hub 150클래스로 **81%** (IEEE 2022, 실측) | 최신 VLM fine-grained **81.83%** (DiningBench 2026, 실측) |
| **커버 범위** | **학습한 클래스만.** 150종 밖은 무조건 오답 | 오픈 보캐블러리 — 처음 보는 음식도 이름을 말함 |
| **데이터 획득** | AI Hub 휴대폰 인증 → 자동승인 가능하나 **수백 GB 다운로드**, INNORIX 전용 툴 | 불필요 |
| **학습 비용** | GPU 시간, 실험 반복. 1인 사용자에겐 과투자 | 0 |
| **유지보수** | 새 음식(신메뉴, 편의점 신상)마다 재학습 | DB 한 줄 추가 |
| **라이선스** | **상업적 이용 시 수행기관 별도 협의 필요** | API 약관만 |
| **배포** | 모델 서빙 인프라 필요 → **현재 zero-build static 스택과 정면 충돌** | API 호출 (그래도 프록시는 필요) |
| **🔴 양 추정** | **해결 못 함** | **해결 못 함** |

**마지막 줄이 전부입니다.** 두 경로 모두 **정확도 상한이 같고(~81%)**, 두 경로 모두 **정작 중요한 병목(양)을 못 풉니다.** 그렇다면 **비용이 압도적으로 낮은 쪽**을 택하는 게 당연합니다.

**그리고 진짜 중요한 함의:**

> 81% 정확도 모델을 만드는 데 드는 노력을, **"1인분 프리셋 UI를 제대로 만드는 것"**에 쓰면 **훨씬 큰 정확도 개선**이 나옵니다.
>
> 왜냐하면: 음식명이 틀리면 → 사용자가 3초 만에 고칩니다. 양이 틀리면 → **사용자는 그게 틀린 줄도 모릅니다.** NIH 연구의 345 kcal이 정확히 이 구조입니다.

**🔴 한식만의 결정적 이점 — 이걸 무기로 삼아야 합니다:**

한식은 **배식 단위가 표준화**되어 있습니다.
- 공기밥 = 1공기 (대략 200~210 g, 식당 편차 있음)
- 찌개 = 1인분 뚝배기 / 2인분 냄비
- 국밥 = 1그릇
- 삼겹살 = 1인분 = 보통 150~200 g (주문 단위 자체가 인분)
- 편의점 도시락 = **제품 라벨에 중량과 영양성분이 인쇄되어 있음**
- 학식 = 정량 배식

**서양식은 "접시에 알아서 담기" 때문에 양 추정이 지옥입니다. 한식은 "인분"으로 주문하고 배식됩니다.** 즉 **사용자에게 "몇 인분?"만 물어보면 사진 AI보다 훨씬 정확합니다.** 이건 한국 앱이 미국 앱보다 구조적으로 유리한 지점인데, 아무도 제대로 안 쓰고 있습니다.

**최종 권고 아키텍처:**

```
[사진]  ──옵션──▶ VLM (외부 API)
                    │  반환: 음식명 후보 3개 + 신뢰도
                    ▼
              ┌─────────────────────┐
[직접검색] ──▶│  음식 확정 (사용자)  │◀── 최근 먹은 것 / 즐겨찾기 / 바코드
              └──────────┬──────────┘
                         ▼
              ┌─────────────────────┐
              │ 양 확정 (사용자) ★   │  ← 여기가 정확도의 전부
              │ 0.5 / 1 / 1.5 / 2인분│
              │ + 직접 g 입력        │
              └──────────┬──────────┘
                         ▼
        정적 번들 JSON (식약처 음식 12,200 + 가공식품 상위 N)
```

## 6. 7번 질문: 한국 1인분 중량 기준 — 표준 참조표가 있는가?

### 있습니다. 3중으로.

**① 식약처 식품영양성분DB의 `1인(회)분량 참고량` + `식품중량` 컬럼** ← **가장 실용적**
- 음식 12,200건 각각에 1인분 기준량이 붙어 있음
- data.go.kr 15100070 (음식 표준데이터)에서 CSV로 통째로 받을 수 있음
- **→ 앱의 프리셋 테이블로 그대로 쓰면 됨**

**② 외식 영양성분 자료집 1~5권 (총 432품목)**
- **1회 제공량 + 음식 사진** 동반
- → **"1인분이 이 정도입니다" 시각 가이드**로 활용

**③ 2020 한국인 영양소 섭취기준(KDRIs) 식사구성안 — 1인 1회 분량**

확인된 식품군별 1회 분량 **에너지 기준**:

| 식품군 | 1회 분량 에너지 |
|---|---|
| 곡류 | **300 kcal** |
| 고기·생선·달걀·콩류 | **100 kcal** |
| 채소류 | **15 kcal** |
| 과일류 | **50 kcal** |
| 우유·유제품류 | **125 kcal** |

- 1회 분량은 **국민건강영양조사 자료를 통합 분석**해서 설정 (= 한국인이 실제로 먹는 양 기반)
- 🔴 **실물 사진 총 180건 제공**: 곡류 30, 고기·생선·달걀·콩류 53, 채소 54, 과일 16, 우유·유제품 5, 유지·당류 14, **식기류 8** ← **식기 사진이 있다는 건 "이 그릇 기준으로 이만큼"을 보여준다는 뜻. 앱 UI에 그대로 쓸 수 있는 자산**
- 출처: 보건복지부·한국영양학회, `kns.or.kr` 자료실, 「2020 한국인 영양소 섭취기준 활용 자료 개발」 J Nutr Health 2022;55(1):21

**⚠️ 공기밥 210 g에 대한 정직한 판정:**
- **`[부분 확인]`** — 곡류군 1회 분량이 **300 kcal**라는 것은 확인했습니다. 밥 100 g ≈ 143 kcal이므로 **210 g ≈ 300 kcal로 정확히 맞아떨어집니다.** 따라서 210 g은 KDRIs 곡류 1회 분량과 정합적입니다.
- 그러나 **"밥 210 g"이라고 명시된 공식 표를 직접 열어 확인하지는 못했습니다** (보건복지부·한국영양학회 PDF 및 e-jnh.org 차단).
- **현실 편차:** 커뮤니티 논의에서 식당 공기밥은 **180~230 g** 범위로 언급됩니다. 즉 **210 g은 기준값이지 실측값이 아닙니다.** 앱에서 210 g을 기본값으로 쓰되 **±10% 정도는 잡음으로 간주**해야 합니다.

**앱에 넣을 프리셋 (식약처 DB에서 추출 + 관용값):**

⚠️ 아래 표의 개별 g 값은 **제가 직접 DB를 조회해 확인한 것이 아닙니다.** 식약처 음식 DB를 다운로드해서 `1인(회)분량 참고량` 컬럼으로 **실제 값을 채워 넣으세요.** 아래는 구조 예시입니다.

| 음식 | 1인분 프리셋 | 비고 |
|---|---|---|
| 공기밥 | 210 g | KDRIs 곡류 1회 분량(300kcal)과 정합 |
| 김치찌개 | 1인분 (뚝배기) | 식약처 외식자료집 1권 수록 |
| 제육볶음 | 1인분 | 검색에서 250 g 표기 발견 `[출처 약함 — 필라이즈 등 민간 앱]` |
| 순대국밥 | 1그릇 | 밥 별도/말아서 구분 필요 |

| 비빔밥 | 1그릇 | |
| 편의점 도시락 | **제품 라벨값** | 🔴 **가공식품 DB 76,000건에 있음. 바코드 스캔이 사진 인식보다 100배 정확** |

## 7. 식단 기록 탭 화면 설계

### 7-1. 설계 원칙 (기존 앱 철학과의 일관성)

Mybody는 이미 **"InBody 측정 노이즈 이하의 변화는 변화라고 말하지 않는다"**는 원칙을 씁니다. 식단에도 같은 기준을 적용합니다:

1. **점 추정값 금지, 구간 표시.** kcal은 `1,847 kcal`이 아니라 `1,850 ± 200 kcal` 또는 `1,650~2,050`
2. **모든 기록에 출처 태그.** `수동`(신뢰 높음) / `바코드`(신뢰 매우 높음) / `사진추정`(신뢰 낮음) — 색으로 구분
3. **사진 추정 기록은 목표 달성률 계산에서 별도 표기.** "사진 추정 3건 포함 — 실제와 다를 수 있음"
4. **사진 AI는 절대 숫자를 확정하지 않음.** 항상 "이거 맞나요? 몇 인분?" 확인 단계를 거침
5. **코칭 문구는 임계값 기반, 애매하면 침묵.** 오차 범위 안이면 아무 말 안 함

- 110% 초과: **명확한 초과** (빨강) → 여기서만 "그만 드세요" 발화

### 7-8. 코칭 발화 규칙 — "그만 먹어" 로직

**절대 원칙: 오차 범위 안에서는 말하지 않습니다.**

| 조건 | 시점 | 문구 |
|---|---|---|
| 단백질 잔여 ≥ 40g & 시각 ≥ 18:00 | 저녁 | 🔴 `단백질 58g 남았습니다. 닭가슴살 1개 + 계란 2개면 채워집니다.` |
| 단백질 잔여 ≥ 30g & 하루 종료 1시간 전 | 심야 | `오늘 단백질 34g 부족으로 마감될 것 같습니다. 두유 1팩이라도 어떨까요.` |
| 칼로리 85~100% | 실시간 | 🟡 `오늘 칼로리 320 kcal 남았습니다.` |
| **칼로리 100~110%** | 실시간 | 🟠 `오늘 목표 칼로리를 다 썼습니다. (오차 범위 내이니 크게 신경 쓰지 않아도 됩니다.)` |

| **칼로리 > 130%** | 실시간 | 🔴 `목표를 크게 넘었습니다 (+920 kcal). 내일 줄이기보다 그냥 평소대로 드세요 — 보상 단식은 역효과입니다.` |
| 지방 > 목표 130% & 칼로리 정상 | 실시간 | `지방 비율이 높습니다. 남은 끼니는 기름 적은 쪽으로.` |
| 탄수 > 목표 120% & 단백질 < 60% | 실시간 | `탄수는 채웠는데 단백질이 비었습니다. 다음 끼니는 고기/생선 위주로.` |
| 3일 연속 단백질 < 70% | 주간 | `3일 연속 단백질 부족입니다. 근비대 목표에서는 이게 가장 큰 손실입니다.` |

- 하루 단위 매크로가 조금 어긋남 → **말 안 함.** 매크로는 **주간 단위**로 봐야 의미가 있음
- "살찐다", "죄책감" 유발 표현 금지
- 초과했다고 다음날 목표를 깎지 않음 (보상 행동 유도 금지)

|---|---|---|---|
| **1** | data.go.kr에서 음식 12,200 + 가공식품 상위 N건 받아 → 필드 추려 정적 JSON 번들 | ❌ 불필요 | 하루 |
| **2** | 검색 + 1인분 프리셋 + 「오늘」 화면 + 기록 저장 | ❌ | 2~3일 |
| **3** | 주간/월간 달성률 + 차트 | ❌ | 2일 |
| **4** | 코칭 발화 룰 엔진 | ❌ | 1일 |
| **5** | 체중 변화 역산 vs 기록 대조 (기존 주간 체크인 연동) | ❌ | 1일 |
| **6** | 바코드 스캔 (`BarcodeDetector` API 또는 `zxing-js`) → 가공식품 DB 조회 | ❌ | 1~2일 |
| **7** | *(선택)* 사진 인식 | 🔴 **필요** — VLM API 키 프록시 | 별개 프로젝트 |

**1~6단계에 사진 AI가 전혀 필요 없고, 이게 실사용 정확도의 90%를 만듭니다.** 7단계는 재미와 편의를 위한 것이고, 앱이 완성된 뒤에 붙여도 늦지 않습니다.

**특히 6단계(바코드)를 7단계(사진)보다 먼저 하세요.** 편의점 도시락·과자·음료는 바코드로 **오차 3%**로 기록되는데, 같은 걸 사진으로 하면 오차 30%입니다. 그리고 22세 한국 남성이 실제로 먹는 것 중 바코드 있는 비중이 상당합니다.

## 8. 한 줄 정리

> **데이터는 다 있습니다 (식약처 음식 12,200건 + 가공식품 76,000건, 1인분 중량 포함, 전부 무료). 모델도 있습니다 (AI Hub 150종 15만 장, 81% 정확도). 없는 건 "사진에서 양을 알아내는 방법"이고, 그건 구글이 depth 센서까지 동원해도 칼로리 오차 16.5%, 상용 앱은 끼당 345 kcal를 놓칩니다.**
>
> **그러니 사진에 투자하지 말고, 한식의 "1인분" 구조를 UI로 만드는 데 투자하세요. 한식은 인분 단위로 나옵니다. 사용자에게 "몇 인분?"이라고 묻는 게 어떤 AI보다 정확합니다.**

## 9. 확인하지 못한 것 (정직한 목록)

1. **AI Hub 데이터셋 페이지 원문** — 전부 차단. 클래스 수/이미지 수/라이선스는 검색 요약 경유. **특히 `dataSetSn=242`는 수치가 충돌합니다**
2. **`dataSetSn=74`의 어노테이션에 실제 그램(g) 라벨이 있는지** — "양을 추정"이 목표로만 적힌 건지 실측 라벨이 있는 건지 불명. **가장 확인 가치 높은 항목**
3. **AI Hub 음식 데이터의 상업적 이용 가능 여부** — 이용정책은 "별도 협의", 외부 리포트는 "commercially licensed". 충돌
4. **NIH 연구의 앱별 개별 오차** — 어느 앱이 얼마나 틀렸는지 분해 수치 못 구함. Cal AI −345 kcal만 2차 보도에서 확인
5. **한국 앱 사용자 리뷰의 구체적 불만 내용** — 앱스토어 리뷰 본문 접근 실패. **6번 질문의 이 부분은 답 못 했습니다**
6. **DiningBench에 한식 포함 여부** — 메이투안 제작이라 중국 요리 중심 추정, 미확인
7. **밥 1공기 210 g 공식 표** — 곡류군 300 kcal는 확인, 210 g 명시 표는 원문 미확인 (수치상 정합)
8. **식약처 DB 개별 음식의 1인분 g 값** — 직접 조회 안 함. 7-6 표의 g 값은 예시이며 실제 DB로 채워야 함
9. **arXiv 2409.02448 (한식 계층적 검출)의 코드·가중치 공개 여부**
10. **인바디 앱의 식단 기록 기능 유무**
