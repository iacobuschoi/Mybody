# 포션(양) 추정 — 이것이 진짜 어려운 문제다

**조사 담당 영역:** 사진에서 "얼마나 먹었는가"를 추정하는 문제. 모든 사진 칼로리 앱이 조용히 실패하는 지점.

## 0. 조사 방법과 한계 (먼저 밝힘)

이 세션은 egress 프록시 뒤에 있었고, **학술 사이트가 거의 전부 차단**되었습니다.

| 도메인 | 상태 |
|---|---|
| `github.com` | ✅ 접근 가능 (실제 fetch + GitHub API 검증 완료) |
| `arxiv.org`, `ar5iv.labs.arxiv.org` | ❌ EGRESS_BLOCKED |
| `openaccess.thecvf.com` (CVPR 원문) | ❌ EGRESS_BLOCKED |
| `pmc.ncbi.nlm.nih.gov`, `ncbi.nlm.nih.gov` | ❌ EGRESS_BLOCKED |
| `sciencedirect.com`, `mdpi.com`, `wiley.com` | ❌ EGRESS_BLOCKED |
| `huggingface.co`, `en.wikipedia.org` | ❌ EGRESS_BLOCKED |
| WebSearch | 세션 예산 200/200 소진 (조사 중간에 고갈) |

따라서 **논문 원문을 열어 표를 직접 읽은 건 하나도 없습니다.** 아래 숫자는 검색엔진이 해당 페이지 본문을 근거로 생성한 요약에서 나왔습니다. GitHub 관련 사실(별 수, 라이선스, 아카이브 날짜, README 내용)과 **Mybody 코드베이스 관련 사실만 제가 직접 확인**했습니다.

표기 규칙:
- **[검증됨]** — 제가 직접 페이지를 열어 확인
- **[출처확인·원문미열람]** — 실존하는 피어리뷰 논문의 검색 요약. 숫자는 신뢰할 만하나 표를 직접 보지 못함
- **[출처불명]** — 숫자는 나왔으나 어느 논문인지 특정 실패
- **[미검증 — 신뢰불가]** — 마케팅/SEO 블로그. 1차 출처 없음. **쓰지 마세요**

## 1. 사람과 앱이 사진으로 양을 추정할 때 오차는 얼마나 큰가

### 1.1 전문가도 사진만으로는 절반쯤 틀린다

**Feasibility of Reviewing Digital Food Images for Dietary Assessment among Nutrition Professionals** (PMC6115988) **[출처확인·원문미열람]**

- 영양사·영양학 연구자 **38명**이 디지털 음식 사진을 보고 식품 식별 + 양 추정
- 실제 중량 대비 **차이율: 그릇(bowl) 44.3 ± 16.6% / 접시(plate) 47.6 ± 21.2%**
- **실제 중량의 10% 이내로 맞춘 비율: 접시 23.7%, 그릇 32.3%** — 즉 훈련받은 전문가의 **2/3 이상이 10%도 못 맞춤**

이게 이 조사 전체에서 가장 중요한 숫자입니다. **직업이 이것인 사람이 사진만 보고 ±45% 틀립니다.** 어떤 앱이 "AI가 영양사만큼 정확합니다"라고 말한다면, 그건 칭찬이 아닙니다.

### 1.2 푸드 아틀라스(사진 도감)로 훈련해도 24%

**Development and Validation of a Photographic Food Atlas for Portion Size Estimation (Türkiye)** (PMC13491268) **[출처확인·원문미열람]**

- 아틀라스 훈련 **후** 450회 배식량 관측
- **평균 절대 오차 22.4 ± 22.4 g** (범위 0 ~ 110.8 g)
- **평균 상대 오차 24.0 ± 19.3%** (범위 0 ~ 120%)

표준편차가 평균과 같다(22.4 ± 22.4)는 점에 주목하세요. **오차 분포가 롱테일**입니다. 평균 24%는 "보통 24% 틀린다"가 아니라 "대개 10%대인데 가끔 100% 틀린다"에 가깝습니다.

### 1.3 사진보다 글이 나았다 — 반직관적이지만 중요

**Lucassen et al. 2021, J Hum Nutr Diet, DOI 10.1111/jhn.12878** **[출처확인·원문미열람]**

- 참가자 40명, 점심 1회의 **실제 섭취량을 계량으로 확보**한 뒤 2시간·24시간 후 자가보고
- 텍스트 기반 양 추정(TB-PSE) vs 이미지 기반(IB-PSE) 비교

| 지표 | 텍스트 기반 | 이미지 기반 |
|---|---|---|
| 실제의 **10% 이내** | **31%** | 13% |
| 실제의 **25% 이내** | **50%** | 35% |
| 전체 중앙값 상대오차 | **0%** | 6% |

> ⚠️ 검색 요약의 산문 부분은 "이미지 기반이 더 좋았다"고 썼지만 **제시된 숫자는 정반대**입니다(31% > 13%, 50% > 35%, 0% < 6%). 세 지표가 모두 같은 방향이므로 **텍스트가 더 정확했다**고 읽는 것이 옳습니다. 원문을 못 열었으므로 이 방향성은 **[방향 재확인 필요]**로 표시합니다.

함의: **"반공기/한공기/곱빼기" 같은 언어적 프리셋이 사진 도감보다 나쁠 이유가 전혀 없습니다.** 오히려 이 연구는 더 낫다고 말합니다.

그리고 **중앙값 상대오차가 0%인데 10% 이내 적중률은 31%밖에 안 된다**는 것 — 이게 4번 항목 전체의 핵심입니다. **개별 추정은 엉망인데 집계하면 상쇄됩니다.** 뒤에서 다시 다룹니다.

### 1.4 LLM도 사람보다 못하다

**[출처불명 — 두 논문 중 하나로 추정: arXiv 2312.08592 "Dietary Assessment with Multimodal ChatGPT" 또는 PMC12513282 "Performance Evaluation of 3 LLMs for Nutritional Content Estimation from Food Images"]**

- **GPT-4V 평균 절대 오차 54.6 g**
- **사람 평균 절대 오차 43.6 g**

즉 범용 비전 LLM은 이 과제에서 **사람보다 25% 더 틀립니다.** "최신 LLM한테 사진 주면 되지 않나"의 답은 현재 근거로는 "아니오"입니다.

### 1.5 음식 종류별로 오차 방향이 뒤집힌다 — 한식에 치명적

**[출처불명 — "실시간 추정 연구"로만 요약됨, 전체 오차 4.8±1.8%는 통제된 프로토콜로 보이며 휴대폰 자유촬영에 적용 불가]**

| 음식 형태 | 오차 |
|---|---|
| 고형식(solids) | **+8.3 ± 2.3%** |
| 무정형식(amorphous) | **−10 ± 2.7%** |
| 액체(liquids) | **+19 ± 5%** |

전체 오차 4.8%는 믿지 마세요. 하지만 **부호가 뒤집힌다는 사실**은 중요합니다.

한국인이 찍을 음식을 이 분류에 넣어보면:

| 음식 | 분류 | 예상 문제 |
|---|---|---|
| 삼겹살, 계란 | 고형 | 상대적으로 양호 |
| **김치찌개, 순대국밥, 미역국** | **액체 + 무정형** | 최악. 국물에 잠긴 건더기는 **깊이 정보가 물리적으로 존재하지 않음** |
| **비빔밥, 제육덮밥** | **무정형 혼합** | 한 그릇 안에 밥/고기/나물이 섞여 있어 성분별 분리 불가 |
| 편의점 도시락 | 고형 + 구획 | 실제로는 **바코드가 정답**이라 사진이 필요 없음 |

**한식 로깅에서 사진 추정 편향은 상수가 아니라 그날 뭘 먹었느냐에 따라 부호까지 바뀝니다.** 이것이 나중에 "편향의 안정성"이 정확도보다 중요하다는 결론과 직접 충돌하는 지점입니다.

## 2. 기법별 실제 성능과 "브라우저에서 되는가"

### 2.1 Nutrition5k — 이 분야의 기준점이자 한계선

**[검증됨: GitHub README 직접 fetch]** `google-research-datasets/Nutrition5k`

| 항목 | 내용 |
|---|---|
| 규모 | 약 5,000개 접시 |
| 모달리티 | 회전 측면 동영상 4개 + **오버헤드 RGB-D 이미지** |
| 라벨 | **성분별 중량** + 총 칼로리 + 매크로 |
| 촬영 장비 | **커스텀 스캐닝 리그, 라즈베리파이 카메라 4대, 30°/60° 교차 배치** |
| 라이선스 | CC BY 4.0 (상업 이용 가능) |
| **저장소 상태** | **2026-04-19 아카이브됨 — 읽기 전용** |
| **저자 명시 한계** | **"모든 요리 문화를 포괄하지 않음 — 미국 캘리포니아 소수 구내식당에서만 수집"** |

**[출처확인·원문미열람 — CVPR 2021 원문 차단]** 보고된 칼로리 MAE:

| 모델 | 칼로리 MAE |
|---|---|
| 2D 직접 예측 (RGB only) | **26.1%** |
| **깊이를 4번째 채널로 추가 (RGB-D)** | **18.8%** |

> 깊이 하나 넣었을 뿐인데 오차가 **28% 줄어듭니다.** 이게 "포션이 진짜 문제"라는 말의 정량적 증거입니다. 음식이 뭔지 아는 것보다 **얼마나 있는지 아는 것**이 오차의 대부분을 차지합니다.

후속 연구:

| 방법 | 성능 | 출처 |
|---|---|---|
| RGB-D + FLAVA 대조학습 | **평균 PMAE 14.43%** (전 영양소) | ScienceDirect S0889157525016370 **[출처확인·원문미열람]** |
| RDINet (RGB-D + 성분 특징) | **칼로리 PMAE 14.9%** | Appl. Sci. 2026, 16(1), 454, DOI 10.3390/app16010454 **[출처확인·원문미열람]** |
| 단안 최신 기법 | 평균 **31.10 kcal (17.67%)** | **[출처불명 — arXiv 2404.12257 또는 2601.20051 추정]** |

**결정적 맥락:** 이 14~19%는 전부 **고정 리그, 통제 조명, 알려진 카메라 높이, 서양 구내식당 음식, 학습 분포와 동일한 테스트셋**에서 나온 숫자입니다. 식당에서 손으로 찍은 순대국밥 사진은 **요리 문화·카메라 자세·조명·가려짐·그릇 종류** 전부가 분포 밖입니다.

### 2.3 기준물 관련 — 널리 인용되는 숫자 하나를 반박합니다

검색 중 이런 주장이 나왔습니다: *"신용카드 기준물이 MAE를 34% → 18%로 낮췄다 (50개 음식 통제 실험)"* 및 *"최고 단안 모델 MAE ±25~35%"*.

출처는 **`caleye.fit`** — **경쟁 칼로리 앱의 SEO 블로그**입니다. 1차 논문 인용이 없고, "50개 음식 통제 실험"에 해당하는 논문을 찾지 못했습니다. **[미검증 — 신뢰불가. 문서나 제품에 인용하지 마세요.]**

마찬가지로 `calorietrackerlab.com`의 *"DAI Six-App Validation Study (DAI-VAL-2026-01), Foodvisor ±16.2% MAPE"* — 이 연구 ID는 다른 어디에도 존재하지 않습니다. 제휴 리뷰 사이트의 내부 명명으로 보이며 **[미검증 — 날조 가능성. 사용 금지]**.

### 2.4 가장 효과 큰 "기법"은 비전 기법이 아닙니다

깊이 채널이 26.1% → 18.8%를 만들었습니다. 그런데 **"한공기예요, 반공기예요?"라는 질문 한 번은 그 이상을 합니다.** 사진이 물리적으로 답할 수 없는 바로 그 변수(양)를 직접 묻기 때문입니다.

한국 식기는 서양보다 **훨씬 표준화**되어 있습니다(공기, 국그릇, 대접, 앞접시). 이건 이 앱이 가진 구조적 이점이고, 모델 성능이 아니라 **UI 한 탭**으로 회수할 수 있습니다.

## 3. 상용 앱은 실제로 뭘 하고 있나

### 3.1 유일하게 신뢰할 만한 독립 비교 연구

**Use of Different Food Image Recognition Platforms in Dietary Assessment: Comparison Study** — JMIR Formative Research, 2020 (PMC7752530) **[출처확인·원문미열람]**

- 이미지 **185장**: 단순 자연식품 30 / 단순 가공식품 36 / 음료 47 / **혼합요리 72**

| 플랫폼 | Top-1 | Top-5 |
|---|---|---|
| **Calorie Mama** | **63%** | **88%** |
| Bitesnap | 49% | 71% |
| **Foodvisor** | 46% | 72% |
| **LogMeal** | 위 셋보다 낮음 | — |
| IBM Watson | 위 셋보다 낮음 | — |

> ⚠️ **결정적 주의:** 이건 **"이게 무슨 음식인지" 맞히는 정확도**입니다. **양이나 칼로리 정확도가 아닙니다.** 그리고 이게 **쉬운 쪽 절반**입니다. 최고 성적인 Calorie Mama조차 Top-1이 63% — 10번 중 4번은 음식 이름조차 틀립니다. 그 다음에 양을 추정해야 합니다.

**CALO mama 검증 연구** (PMC8787663, JMIR) **[출처확인·원문미열람]**: 이미지 인식만으로 낸 예측이 **30개 영양소 중 11개, 15개 식품군 중 4개**에서만 정확했습니다.

### 3.2 SnapCalorie — 출처는 좋지만 자기 채점입니다

SnapCalorie는 Nutrition5k 논문 저자(구글 Lens / Cloud Vision 공동창업자)가 만들었습니다. 계보는 이 분야 최고입니다.

주장하는 숫자 **[전부 벤더 자체 주장 — 독립 검증 없음]**:

| 주체 | 주장 오차 |
|---|---|
| SnapCalorie | **~15%** (1,000kcal 식사에 ±150kcal) |
| 영양성분표 법정 허용 | 20% |
| 전문 영양사(사진) | ~40% |
| 타 앱 일반 사용자 | 53% |

문제점 세 가지:
1. **자기 데이터로 자기 채점.** Nutrition5k 검증 세트는 자사 저자가 만든 것입니다. 방법론과 데이터를 공개한 건 이 바닥에서 드문 미덕이지만, 독립 검증은 아닙니다.
2. **15%는 캘리포니아 구내식당 분포 내 숫자**입니다. 순대국밥은 그 분포에 없습니다.
3. "영양사 40%"는 §1.1의 44~48%와 대체로 일치하므로 그 항목만은 신빙성 있음.

## 4. 부정확한 기록이 그래도 효과가 있는가 — 이 앱에서는 **구조적으로 그렇습니다**

이 항목이 Mybody에 가장 중요하고, 저는 문헌이 아니라 **이 앱의 코드**에서 답을 찾았습니다.

### 4.1 코드가 말하는 것 [검증됨 — 직접 읽음]

`/home/user/Mybody/prototype/js/screens/checkin.js:565`

**기록된 칼로리는 이 계산에 단 한 번도 들어가지 않습니다.** 루프는 **체중만** 읽습니다. 기록은 `adherence.dietPct` 게이트에만 쓰이고, 그마저도 `checkin.js:31`에서 **상/중/하 주관 자가평가(기본값 70)** 입니다 — 실제 로그에서 계산되지 않습니다.

### 4.2 그래서 일정한 편향은 루프를 망가뜨리지 않습니다 (제 유도, 인용 아님)

사용자가 실제 섭취 `T`를 `(1−b)` 비율로 과소 기록한다고 하면, 목표 `G`까지 기록을 채우고 멈추므로:

```
T = G / (1 − b)
```

목표를 `ΔG`만큼 조정하면 실제 섭취는 `ΔG / (1 − b)`만큼 변합니다. `b = 0.17`(17% 과소기록)이면 목표 −150 kcal이 실제 −181 kcal이 됩니다. **부호도 같고 크기도 같은 자릿수입니다. 루프는 수렴합니다.**

**편향은 목표값 안으로 흡수됩니다.** 사진이 김치찌개를 매주 15% 과소평가한다면, 체중이 안 빠지는 걸 보고 루프가 목표를 깎고, 사용자는 그 새 목표에 맞춰 (여전히 15% 과소기록하며) 먹고, 결국 목표 체중 궤적을 만드는 실제 섭취량에 도달합니다.

이게 §1.3의 "중앙값 오차 0%인데 10% 적중률은 31%"와 정확히 같은 현상입니다. **집계에서 상쇄되는 성분과, 상쇄되지 않는 성분이 다릅니다.**

### 4.3 루프 자체의 해상도가 이미 ±165 kcal/day입니다 (제 유도)

체크인 임계값은 **주당 0.15 kg**입니다. 지방 1kg = 7,700 kcal이므로:

```
0.15 kg × 7,700 kcal/kg ÷ 7일 ≈ 165 kcal/day
```

**앱이 반응조차 하지 않는 구간이 이미 하루 ±165 kcal입니다.** 2,400 kcal 목표 대비 **약 ±7%**. 기록 정밀도를 ±5%까지 끌어올려 봐야 루프가 구분하지 못합니다. **정밀도 투자 수익이 거기서 끊깁니다.**

### 4.4 무엇이 루프를 망가뜨리는가 — **변하는 편향**

일정한 편향은 흡수됩니다. **변하는 편향은 흡수되지 않고, 루프가 그걸 대사 변화로 착각합니다.**

| 편향 변동 원인 | Mybody에서의 위험 |
|---|---|
| **신선도 감소** — 1주차엔 꼼꼼히, 6주차엔 대충 | 루프가 "정체"로 읽고 칼로리를 깎음 → 실제론 기록만 나빠진 것 |
| **방식 전환** — 이번 주 사진, 다음 주 수동 | 두 방식의 편향이 다름 → 가짜 신호 |
| **선택적 누락** — 치킨은 안 찍음 | 가장 흔하고 가장 파괴적 |
| **한식 음식군별 부호 반전** (§1.5) | 국/찌개 주간 vs 구이 주간에 편향 부호가 바뀜 |

**따라서 이 앱의 설계 목표는 "정확도"가 아니라 "편향 안정성"입니다.** 이건 일반론이 아니라 이 코드에서 나오는 결론입니다.

> **문헌 주의:** 자가보고 에너지 섭취의 체계적 과소보고는 dietary assessment에서 확립된 사실이며(이중표지수 기준), 체지방률이 높을수록 심해진다고 알려져 있습니다. 다만 **이 세션에서는 1차 출처를 열 수 없었고**(PMC/Wikipedia/ScienceDirect 전부 차단, 검색 예산 소진), 검색에서 나온 "사진 칼로리 앱이 1/3 과소평가" 주장은 `pravda.ru` 출처라 **[미검증 — 신뢰불가]** 입니다.

## 6. 정확도를 속이지 않으면서 오차를 줄이는 설계 패턴

### 6.1 포션 프리셋 — 이미 절반은 만들어져 있습니다 ✅

`data.js`의 `FOODS`가 **이미 생활 단위를 쓰고 있습니다** [검증됨]:

```js
{ name: '백미밥',  unit: '210g(1공기)', kcal: 313, ... }
{ name: '된장국(건더기)', unit: '1그릇', kcal: 65, ... }
{ name: '올리브유', unit: '1큰술', kcal: 119, ... }
{ name: '아보카도', unit: '1/2개', kcal: 160, ... }
{ name: '통밀식빵', unit: '2쪽',  kcal: 160, ... }
```

확장 방향: 항목마다 **3단 칩**.

```
백미밥   [반공기 0.5×]  [한공기 1×]  [곱빼기 1.5×]
```

**왜 3단으로 충분한가 (제 유도):** 버킷 경계가 0.75×/1.25×에 있으면 버킷 내 최대 오차는 약 ±25%입니다. 이미 사진 오차 막대 안쪽입니다. **버킷을 더 쪼개도 사용자의 인지 정확도가 그걸 못 따라갑니다** (§1.2에서 아틀라스 훈련자도 24% 오차). 3단 이상은 정밀함을 가장한 마찰입니다.

한국 식기가 표준화되어 있어서 이게 특히 잘 먹힙니다. 다만 **[미검증]** 실제 식당 공기밥 중량 분포(대략 180~230 g로 알려짐)는 한국 식품/외식 자료로 확인이 필요합니다. 확인 전에는 앱 내 210 g을 그대로 쓰되 "가게마다 다릅니다"를 표시하세요.

### 6.2 "지난번과 같이" — 이 앱에서 가장 가치 있는 기능 ⭐

22세 한국 남성의 식사는 **반복적입니다.** 학식, 편의점, 배달 로테이션.

**두 가지 이유로 최고 우선순위:**
1. **마찰:** 2주 지나면 대부분의 기록이 한 탭이 됩니다 **[비율은 제 추정치 — 근거 없음]**
2. **더 중요 — 편향을 상수로 만듭니다.** 같은 항목을 같은 추정치로 재사용하면, 그 항목의 오차가 주마다 흔들리지 않습니다. §4.4에서 본 대로 **루프가 필요로 하는 건 정확도가 아니라 안정성입니다.** "지난번과 같이"는 정확도 기능이 아니라 **안정성 기능**입니다.

### 6.3 프레임 내 기준물 — 선택 기능으로만

동전/카드를 넣으면 스케일 모호성이 풀립니다. 원리는 맞습니다. 하지만:
- 개인용 앱에서 매 끼니 동전 놓을 사람은 없습니다. 2주 뒤 준수율은 0에 수렴합니다.
- 더 나쁜 건, **간헐적 사용이 편향을 변동시킵니다** — 있는 날과 없는 날의 추정 편향이 다르면 §4.4의 실패 모드입니다.

**권고:** "정확도 올리기" 토글로 숨겨두고, 새 음식을 처음 등록할 때만 권하세요. 일상 기록 경로에 넣지 마세요.

### 6.4 개인 보정계수 — 근거는 없지만, 올바른 버전은 이미 이 앱에 있습니다

**질문하신 "사용자의 수정 이력에서 개인 보정계수를 학습하는 것"에 대한 정직한 답: 식이 기록 앱에서 이 메커니즘의 효과를 입증한 논문을 찾지 못했습니다.** 이번 세션의 검색 한계 때문일 수도 있으나, 없다고 보고 설계하는 게 안전합니다.

그리고 **이 버전은 위험합니다.** 사용자의 수정도 추측입니다. 제육볶음을 습관적으로 낮춰 수정하는 사람에게서 학습하면, 앱은 **과소보고를 학습합니다.** 확증편향 증폭기가 됩니다.

**올바른 버전:** 보정계수를 **주관적 수정이 아니라 객관적 체중 추세에 고정**하세요.

```
추정_실제섭취 = 엔진_TDEE + (주간_체중변화_kg × 7700 / 7)
보정계수 = 추정_실제섭취 / 평균_기록섭취
```

완벽히 기록하면 ≈ 1.00. 2,000 기록인데 체중 계산상 2,400이면 1.20.

**반드시 함께 말해야 할 한계:** 이건 **기록 편향과 TDEE 추정 오차를 분리할 수 없습니다.** 체중 데이터만으로는 원리적으로 불가능합니다. 그러니 "당신은 20% 과소기록합니다"라고 말하면 **거짓말**입니다. 정직한 문구:

```
4주간 기록한 평균은 하루 2,010 kcal 이고,
같은 기간 체중 변화는 하루 약 2,400 kcal 를 먹은 것과 맞습니다.

둘 중 하나입니다 —
  ① 기록이 실제보다 약 20% 적게 잡히고 있거나
  ② 당신의 실제 소비량이 추정보다 20% 낮거나.
체중만으로는 둘을 구분할 수 없습니다.

어느 쪽이든 계획은 이미 이 차이를 반영해 조정되고 있습니다.
```

마지막 줄이 중요합니다. §4.2에서 보인 대로 **루프가 이미 흡수하고 있으므로, 이건 경고가 아니라 설명입니다.**

**최소 데이터 조건** — README §4의 자체 기준을 그대로 따르세요:
- **4주 이상** (README: "측정 간격이 4주 미만인 추세는 판정에 아예 쓰지 않습니다")
- **주 3회 이상 체중 측정**, 그리고 **끝점 차이가 아니라 7일 이동평균의 추세 기울기** 사용 (일일 체중은 수분/글리코겐/위장 내용물로 ±1~2 kg 흔들림)
- 조건 미달이면 **숫자를 아예 보여주지 마세요.** README §4가 "기계가 구분하지 못하는 크기"에 대해 하는 것과 같은 처리.

### 6.5 확신도를 값과 함께 저장하세요

각 기록 항목에 `confidence: 'label' | 'preset' | 'photo'`를 저장하고 전파하세요. 그래야 주간 화면이 이렇게 말할 수 있습니다:

```
이번 주 기록의 62%가 사진 추정입니다 → 주간 평균 오차 ±20%
```

이게 없으면 주간 숫자에 정직한 오차 막대를 붙일 수 없습니다.

### 6.6 바코드 — 유일하게 정직하게 타이트할 수 있는 경로

편의점 도시락·삼각김밥·우유·프로틴바는 **라벨이 정답**입니다. 사진이 필요 없습니다. 이 경로만 ±10%를 붙일 자격이 있습니다.

한국은 **식약처 식품영양성분 데이터베이스**가 있습니다 **[API 가용성/약관 미검증 — 검색 예산 소진으로 확인 못 함]**.

## 7. Mybody에 대한 구체적 권고

### 7.1 코칭 넛지는 앱의 기존 tracking 사다리에 붙이세요

`engine.js:87-88` [검증됨]:

```js
p.tracking = a < 0.34 ? '단백질만 대충 기록'
           : (a < 0.7 ? '칼로리 + 단백질 기록' : '4대 매크로 전부 + 주 4회 체중');
```

**엔진은 이미 공격성에 따라 기록 엄격도를 다르게 처방하고 있습니다.** 넛지도 같은 사다리를 타야 합니다. 새 개념을 만들 필요가 없습니다.

| 공격성 | 기존 tracking 처방 | **넛지 정책** |
|---|---|---|
| `a < 0.34` | 단백질만 대충 | **단백질 넛지만.** 일일 칼로리 상한 표시 금지 — 루프 해상도(±165 kcal)보다 작은 걸 관리하라고 하는 셈 |
| `0.34 ≤ a < 0.7` | 칼로리 + 단백질 | 단백질 넛지 + **주간** 칼로리 추세. 일일 하드스톱 없음 |
| `a ≥ 0.7` | 4대 매크로 + 주 4회 체중 | 전 매크로 넛지 + **일일 칼로리 밴드.** 이 강도에선 계획이 드리프트를 못 견디고, 이미 주 4회 체중을 요구했으므로 루프 해상도도 높음 |

### 7.2 단백질 넛지 — 강하게, 정확하게

사용자 요구 그대로 구현 가능하고, 구현해야 합니다.

```
단백질 152g / 목표 190g  ·  38g 남음
닭가슴살 165g 또는 프로틴 1.5스쿱이면 채워집니다
```

**칼로리와 달리 여기선 구체적인 숫자를 보여도 됩니다.** 단백질원은 라벨/프리셋으로 들어오고, 교정 루프가 없어서 미달이 조용히 근손실로 이어지며(`engine.js:251`), 사용자가 명시적으로 요청했습니다.

### 7.3 "그만 먹으세요"는 쓰지 마세요

사용자가 "그만 먹으라 해줘도 좋아"라고 했지만, 그 문구를 그대로 쓰면 안 됩니다.

1. **그 숫자는 ±20%입니다.** "칼로리 다 썼습니다"는 오차 막대를 감춘 단정입니다.
2. README 면책조항이 이미 **섭식장애 이력**을 언급합니다. "그만 먹으세요"는 정확히 그 방향으로 잘못 작동하는 문구입니다.
3. **정보 + 다음 행동이 더 유용합니다.**

```
❌ "오늘 칼로리 다 썼습니다. 그만 드세요."

✅ "오늘 기록 기준 목표에 도달했습니다 (±20%).
    단백질은 아직 38g 남았습니다.
    더 드실 거면 닭가슴살·계란·그릭요거트 쪽이
    지금 남은 여유에 가장 잘 맞습니다."
```

이게 README §4·§6이 다른 데서 취한 태도와 같습니다 — **숨기지도 않고, 단정하지도 않는다.**

### 7.4 가장 큰 통합 기회: `dietPct`를 실측으로 바꾸기

현재 `checkin.js:31` [검증됨]:

```js
return { weightKg: null, workoutPct: 70, dietKey: 'mid', dietPct: 70, ... };
```

`dietPct`는 **상/중/하 자가평가**이고, 이게 `engine.js:918`의 게이트를 통과합니다:

```js
if (adherence && adherence.dietPct < 70) {
  // 칼로리 건드리지 말고 순응도부터
}
```

**이 자가평가를 실제 기록률로 바꾸면**, 새로운 과학 없이 — 포션 추정 정확도를 1%도 개선하지 않고 — 앱의 핵심 루프가 즉시 좋아집니다.

그리고 이건 §4의 결론과 정확히 맞물립니다: **루프가 필요로 하는 것은 정확한 칼로리 숫자가 아니라 "이번 주 기록이 믿을 만한가"입니다.**

권장 정의 (정확도가 아니라 완결성):
```
기록률 = (끼니를 기록한 날 수) / 7      ← 이게 dietPct 로 들어감
```
칼로리 달성률이 아닙니다. **기록했는가**입니다.

### 7.5 주간/월간 화면의 정직한 단위

사용자가 요청한 "주간, 월간 탄단지 달성률"에 대한 답:

| 지표 | 정직한 단위 | 표시 방식 |
|---|---|---|
| **단백질** | **일간 가능** | 하한선(`max(ffm × proteinPerFFM, bw × 1.6)`, `engine.js:670`)을 그은 막대. **"달성"은 ≥ 이지 ≈ 가 아님** — 단백질은 목표가 아니라 바닥 |
| **칼로리** | **주간 이상** | 7일 **평균** vs 목표를 **밴드**로. 일별 막대 7개에 퍼센트 붙이지 마세요 — ±20% 숫자의 일일 달성률은 노이즈 연극입니다 |
| **탄수·지방** | **주간** | 칼로리와 단백질이 정해지면 종속 변수. 별도 달성률 강조 불필요 |
| **기록률** | **주간** | 가장 행동 가능하고, 엔진이 이미 소비 |
| **보정계수 / 캘리브레이션** | **월간(4주)** | README §4가 정한 최소 추세 창과 일치. **월간이 매크로의 정직한 단위입니다** |

칼로리 주간 카드 옆에는 **반드시 체중 추세를 같이 놓으세요.** 그 둘을 함께 놓는 것만이 정직한 진술입니다. 기록 칼로리만 단독으로 크게 보여주면, 앱은 자기가 믿지 않는 숫자를 신뢰하라고 말하는 셈입니다.

## 8. 한 문단 결론

포션 추정은 **풀리지 않았고, 브라우저에서는 더더욱 안 풀립니다.** 최고 공개 벤치마크(Nutrition5k)의 RGB 전용 칼로리 오차는 **26.1%**, 깊이를 넣어야 **18.8%**인데 그건 **고정 리그·통제 조명·캘리포니아 구내식당 음식·학습 분포 내부** 숫자이고, 저자들 스스로 다른 요리 문화를 포괄하지 못한다고 명시했습니다. 훈련받은 영양사는 사진만으로 **44~48%** 틀립니다. 오픈소스 포션 추정기는 **별 10개짜리 AGPL 연구 코드가 최고**이고 한식으로 학습되지 않았습니다. 깊이 센서는 웹에서 못 씁니다. — **그런데 Mybody에서는 이게 생각만큼 치명적이지 않습니다.** 주간 체크인이 **기록된 칼로리를 읽지 않고 체중만 읽기 때문**에(`engine.js:912`), 일정한 편향은 목표값으로 흡수되고 루프는 수렴합니다. 게다가 루프 자체의 반응 임계값이 이미 하루 **±165 kcal (≈7%)** 이라, 그보다 정밀한 기록은 루프가 구분조차 못 합니다. **따라서 이 앱이 사야 할 것은 정확도가 아니라 편향의 안정성입니다** — "지난번과 같이", 3단 프리셋, 항목별 확신도 저장, 그리고 상/중/하 자가평가인 `dietPct`를 실제 기록률로 교체하는 것. 단 하나의 예외는 **단백질**입니다. 단백질에는 체중이라는 교정 경로가 없고, 미달하면 엔진의 근손실 경로가 조용히 켜지므로(`engine.js:251`), 단백질만은 강하고 구체적으로 개입해야 합니다 — 사용자가 요청한 그대로. 사진 추정에는 **단일 항목 ±25~40%(국물류는 부호 불명), 하루 합계 ±20%** 를 표시하고, 프리셋은 **±15~20%**, 바코드만 **±10%** 를 붙일 자격이 있습니다. 그리고 "그만 드세요"가 아니라 **"단백질 38g 남았고 칼로리는 200 남았습니다 — 닭가슴살 165g이 딱 맞습니다"** 라고 말하세요. 그게 더 유용하고, InBody 노이즈 바닥 앞에서 이 앱이 이미 취한 태도와 같습니다.
