# 로그인 · 친구 기능 설계안

> 상태: **계획만**. 아직 구현하지 않았습니다.
> 지금 앱은 백엔드가 없고 모든 데이터가 이 기기의 localStorage에만 있습니다.
> 이 문서는 그걸 깨기 전에 무엇을 얻고 무엇을 잃는지 먼저 정리한 것입니다.

---

## 0. 먼저 — 지금 상태가 가진 것

현재 앱은 **네트워크 요청이 하나도 없습니다.** 인바디 수치도, 사진도, 목표도 이 기기 밖으로
나가지 않습니다. 체성분은 건강정보이고, 한국 개인정보보호법상 **민감정보**입니다.

로그인을 붙이는 순간 이 성질을 잃습니다. 그래서 이 계획의 원칙은 하나입니다 —
**잃는 만큼만 얻어야 합니다.** 친구 기능을 위해 원본 데이터를 서버에 올릴 필요는 없습니다.

---

## 1. 단계 나누기

세 단계는 **독립적으로 가치가 있고, 앞 단계에서 멈춰도 됩니다.**

| 단계 | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **0** (지금) | 로컬 전용 | 완전한 프라이버시 | 기기 바꾸면 끝 |
| **1** | 계정 + 동기화 | 기기 간 동기화, 백업 | 데이터가 서버에 존재 |
| **2** | 친구 + 선택적 공유 | 같이 하는 사람, 지속률 | 남이 내 추세를 봄 |
| **3** | 공동 챌린지 | 동기 부여 | 비교 압박 |

**1단계만으로도 충분히 가치가 있습니다.** 폰을 바꿔도 2년치 인바디 기록이 남는 것은
친구 기능과 무관하게 필요합니다. 친구가 필요 없다고 판단되면 1단계에서 멈추면 됩니다.

## 2. 1단계 — 계정과 동기화

### 무엇을 쓸까

| 후보 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **Supabase** | Postgres + Auth + 행단위 보안(RLS) + 실시간, 서울 리전 있음, 무료 티어로 충분 | OAuth에 카카오가 기본 제공 아님 (커스텀 연동 필요) | **권장** |
| Firebase | 붙이기 가장 쉬움 | NoSQL이라 이 데이터 모양과 안 맞음, 비용 예측 어려움 | 보류 |
| Pocketbase 자가호스팅 | 완전한 통제, VPS 월 5천원 | 백업·업데이트·보안을 직접 책임짐 | 취향이면 |
| Clerk / Auth0 | 인증만 깔끔 | DB는 따로 필요 → 두 벌 관리 | 과함 |

**Supabase + 서울 리전(ap-northeast-2)** 을 권장합니다. 무료 티어(DB 500MB, MAU 5만)로
개인 앱과 친구 몇 명은 여유롭게 덮습니다.

### 로그인 방식

한국 사용자에게는 **카카오 로그인이 사실상 표준**입니다. 이메일/비밀번호는 아무도 안 씁니다.

- 1순위: **카카오** — Supabase의 커스텀 OAuth 또는 Edge Function으로 연동
- 2순위: **애플 로그인** — iOS에서 카카오만 있으면 심사에서 걸립니다
- 3순위: 이메일 매직링크 — 비밀번호 없이, 백업 경로로

### 로컬 우선(local-first)으로 짤 것

**중요합니다.** 서버를 진실의 원천으로 만들면 지금 앱이 가진 가장 좋은 성질(오프라인에서
즉시 동작, 네트워크와 무관)을 잃습니다.

```
localStorage (진실의 원천, 즉시 반영)
      ↕  동기화 레이어
Supabase (백업 + 기기 간 전달)
```

- 모든 레코드에 `id`, `updated_at`, `deleted`(툼스톤)를 붙인다
- 변경 시 디바운스 후 푸시, 앱 열 때 풀
- 충돌: 한 사람이 두 기기를 쓰는 상황이므로 레코드 단위 **최신 우선(LWW)** 으로 충분
- 다만 **인바디 스캔은 사실 기록**이라 조용히 덮어쓰지 않고
  "이 기기의 값이 서버와 다릅니다" 배너를 띄우고 사람이 고르게 한다
- 네트워크가 없으면 그냥 로컬로 계속 동작한다. 동기화는 있으면 좋은 것이지 전제가 아니다

### 스키마 (1단계)

```sql
profiles        (id uuid pk, display_name, avatar_url, created_at)
scans           (id uuid pk, user_id, measured_at, weight_kg, smm_kg, bfm_kg,
                 ffm_kg, pbf_pct, bmr_kcal, vfl, whr, inbody_score,
                 segmental jsonb, impedance jsonb, source, updated_at, deleted)
goals           (id, user_id, weight_kg, smm_kg, bfm_kg, mode_id, deadline_weeks, updated_at)
plans           (id, user_id, goal_id, level, mode_id, start_date, target_date,
                 weeks, payload jsonb, updated_at)
checkins        (id, user_id, at, weight_kg, workout_pct, diet_pct, condition, memo, updated_at)
food_logs       (id, user_id, at, meal, items jsonb, kcal, p, c, f, source, updated_at)
```

RLS는 전부 `user_id = auth.uid()`. 예외 없음. **친구는 이 테이블들을 절대 못 읽습니다.**

## 3. 2단계 — 친구와 공유

### 핵심 결정: 원본을 공유하지 않는다

친구에게 `scans` 테이블 읽기 권한을 주는 순간, 정책 한 줄 실수로 전부가 새어나갑니다.
그래서 **읽기 경로 자체를 만들지 않습니다.**

대신 공유 전용 테이블을 둡니다.

```sql
friendships     (id, requester_id, addressee_id,
                 status: pending|accepted|blocked, created_at, responded_at)
                 -- (requester_id, addressee_id) 유니크, 양방향은 두 행이 아니라 한 행 + 정렬

share_settings  (owner_id, viewer_id,
                 share_weight_trend   bool default false,
                 share_smm_trend      bool default false,
                 share_bfm_trend      bool default false,
                 share_absolute       bool default false,   -- 절대값까지 볼지
                 share_checkin_streak bool default true,
                 share_plan_progress  bool default false,
                 updated_at)
                 -- 기본값이 전부 false 인 것이 이 설계의 핵심

shared_snapshots (owner_id, viewer_id, week_start,
                  payload jsonb,   -- 공유 설정이 허용한 것만 들어 있음
                  computed_at)
```

- `shared_snapshots` 는 소유자 쪽에서 주 1회 계산해 **허용된 항목만** 담아 쓴다
- 친구는 `shared_snapshots` 만 읽는다. 원본 테이블에는 읽기 경로가 없다
- 공유를 끄면 그 행을 지운다 → 친구 화면에서 즉시 사라진다

### 기본값: 아무것도 공유하지 않음

**친구 추가 ≠ 데이터 공개.** 친구를 맺은 뒤 항목별로 따로 켜야 합니다.
그리고 사람마다 다르게 설정할 수 있습니다 — A에게는 체지방률 추세를 보여주고
B에게는 체크인 여부만 보여주는 게 가능해야 합니다.

### 절대값이 아니라 변화를 공유한다

기본 공유 단위는 **"지난 12주 체지방률 −5.3%p"** 이지 **"현재 23.1%"** 가 아닙니다.

절대값 공유는 따로 켜야 하는 별도 스위치입니다. 이유:

- 변화량은 서로 비교해도 덜 해롭습니다. 출발점이 다른 사람끼리 절대값을 비교하면
  잘하고 있는 사람이 못하고 있다고 느낍니다
- 22세 남성의 체지방률 절대값 비교는 신체 이미지 문제와 직결됩니다
- 실제로 동기 부여에 효과가 있는 건 "같이 하고 있다"는 사실이지 "누가 더 낮은가"가 아닙니다

### 순위표는 만들지 않는다

절대 체성분 순위표는 만들지 않습니다. 굳이 비교를 만든다면 **각자 자기 목표 대비 진행률**
이나 **체크인 연속 일수** 같은, 출발점과 무관한 지표로만 합니다.

## 4. 화면 (2단계)

| 번호(예정) | 화면 | 내용 |
|---|---|---|
| `P16` | 계정 | 카카오/애플 로그인, 동기화 상태, 로그아웃, 계정 삭제 |
| `P17` | 친구 | 친구 목록, 요청 보내기/받기, 각 친구의 공유 상태 뱃지 |
| `P18` | 친구 상세 | 그 친구가 나에게 공유한 것만 표시. 내 추세와 겹쳐 보기 |
| `P19` | 공유 설정 | **친구별** 항목 토글. "지금 이 친구가 볼 수 있는 것" 미리보기 포함 |
| `M30` | 친구 추가 | 초대 링크 / 코드 (전화번호·이메일 검색은 안 함) |
| `M31` | 공유 중단 확인 | 끄면 상대 화면에서 즉시 사라진다고 명시 |
| `M32` | 계정 삭제 | 서버 데이터 전부 삭제, 로컬은 선택 |

**친구 찾기는 초대 링크로만.** 전화번호나 이메일로 사람을 검색하는 기능은 넣지 않습니다 —
그건 아는 사람을 찾는 기능이 아니라 모르는 사람에게 발견되는 기능입니다.

## 5. 3단계 — 공동 챌린지 (해도 되고 안 해도 됨)

- "이번 주 둘 다 체크인하기" 같은 **행동 기반** 챌린지
- 체중·체지방 **결과 기반** 챌린지는 만들지 않는다 (탈수·굶기를 유도함)
- 서로의 주간 체크인 완료 여부만 보이는 정도가 적정선

## 6. 법·윤리

- 체성분은 한국 개인정보보호법상 **민감정보**입니다. 개인 앱으로 혼자 쓰는 동안은
  적용 대상이 아니지만, 다른 사람 계정을 받는 순간 **별도의 명시적 동의**가 필요합니다
- 가입 시 동의 화면을 나눠야 합니다: 서비스 이용 / 민감정보 처리 / (선택) 친구 공유
- 계정 삭제 시 서버 데이터를 실제로 지워야 합니다 (soft delete로 남겨두지 않기)
- 미성년자 가입은 받지 않는 편이 낫습니다. 이미 앱이 19세 미만 감량 계획을 거부합니다

## 8. 만들 때의 순서

1. 스키마 + RLS 정책 작성, 정책 자체를 테스트로 검증 (다른 사용자 행이 안 읽히는지)
2. 동기화 레이어 — 로컬 우선, 툼스톤, 충돌 배너
3. 카카오 로그인 연동
4. 기존 로컬 데이터를 계정으로 올리는 마이그레이션 (한 번만, 되돌릴 수 있게)
5. 여기서 한 번 멈추고 실제로 써본다
6. 친구·공유는 그 다음
