주제: **$ARGUMENTS**

CLAUDE.md 의 §1 단계표를 따릅니다. 이 스킬은 그 순서를 빠뜨리지 않게 하는 점검표입니다.

## 0. 접수 (5분)

1. 앱 짧은 이름(slug)을 정합니다 — 영문 소문자 한 단어, 다른 앱과 안 겹치게(`ls apps portfolio`).
2. `portfolio/ideas.md` 표에 한 줄 추가: 날짜 · 주제 원문 · slug · 상태 `조사 중`.
3. `portfolio/<slug>/` 를 만들고 주제 원문을 `brief.md` 맨 위에 인용해 둡니다.

## 1. 조사 — S1

`market-researcher` 에이전트에게 주제와 slug 를 넘깁니다. 결과로 `research.md` · `score.md`.

- **60점 미만** 또는 정책 위험 "높음" → 여기서 멈춥니다. `ideas.md` 상태 `보류(점수 n)`,
  주인에게 세 줄 보고(왜 안 되는지 · 대신 해 볼 만한 변형 한두 개). 끝.
- 통과 → 다음.

## 2. 기획 — S2

`brief.md` (한 쪽, 폰에서 읽힘):
- 한 줄 정의 · 누구를 위한가 · 경쟁 앱 대비 이길 한 가지
- 핵심 반복 행동 하나와 다시 켤 이유(알림 · 위젯 · 이어 가기)
- 첫 판 기능 **3~5개만** (나머지는 `spec.md` 의 「나중에」)
- 수익 모델 · 가격 초안 · 결제 벽 위치 (`docs/factory/MONEY.md`)
- 되돌리기 어려운 결정: 앱 이름 후보 · 번들 ID · 서버가 필요한가 · 저장 데이터와 가는 곳
- 성공 판정: 출시 30일 뒤 볼 지표 하나와 기준값

`spec.md`: 화면 목록 · 흐름 · 데이터 모델 · 측정 이벤트 · 알림 · 정책 위험(store-reviewer 에게 짧게 확인).

`product-critic` 에이전트로 brief 를 한 번 비평하고, 막을 것만 고칩니다.

## 3. 상황판

GitHub 이슈 `[상황판] <앱 이름>` 을 만들고(라벨 `status`, `app:<slug>`), 본문을 CLAUDE.md §5
형식으로 씁니다. 첫 보고에 brief 의 핵심 다섯 줄을 붙입니다.

주인에게 알림 한 번: "새 앱 <이름> — 점수 n, 첫 판 기능 k개, 수익 모델 ○○. 멈추려면 '멈춰'."
**기다리지 않고 진행합니다.** 주인이 멈추라고 하면 그때 멈춥니다.

## 4. 그다음 (S3 ~ S6)

- S3: `design/` 에 화면 시안(플러터 위젯을 골든 스크린샷으로 뽑거나 HTML 시안) → product-critic.
- S4: `apps/<slug>/` 를 공장 템플릿에서 만들고(`flutter create --org io.github.<주인> --project-name <slug>`
  뒤 `packages/` 연결), 기능마다 브랜치 · PR · 시험 · 교차 검토 · 머지. PR 마다 CI 를 구독해서
  빨간색이면 바로 고칩니다.
- S5: `device-lab` 워크플로를 돌려 실기기 결과와 스크린샷을 받고, `qa/<판>/` 에 정리.
- S6: `/release-prep <slug>` 스킬.

단계가 바뀔 때마다 상황판 본문을 고칩니다. 알림은 주인이 해야 할 일이 생겼을 때만.
