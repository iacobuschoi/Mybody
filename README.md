# Mybody

인바디(InBody) 결과지 한 장에서 현재 몸 상태를 읽고, 목표 체중·골격근량·체지방량을 입력하면
**언제 달성 가능한지**와 그때까지의 **운동·식단 계획**을 만들어 주는 개인용 앱.

> 현재 단계: **검증용 프로토타입**. 백엔드도 실제 OCR도 없습니다.
> 오너가 클릭해 보고 피드백하기 위한 뼈대입니다.

---

## 바로 열어보기

```bash
cd prototype && python3 -m http.server 8000
# 또는  npx http-server prototype -p 8000
```
브라우저에서 <http://localhost:8000> — `file://` 로 직접 열어도 동작합니다 (ES 모듈을 쓰지 않음).

처음 화면에서 **"내 실제 인바디로 바로 시작"** 을 누르면 실제 InBody270 결과지 3건이 채워진 상태로 시작합니다.

## 피드백 하는 법

화면의 모든 요소에 작은 고유번호 배지가 붙어 있습니다.

| 조작 | 결과 |
|---|---|
| 배지 클릭 | `P06-B21 · 중 선택` 형태로 클립보드에 복사 |
| **Shift** + 배지 클릭 | 그 요소에 메모 달기 (로컬 저장) |
| **Alt** + 배지 클릭 | 딥링크(`#P06-B21`) 복사 |
| `i` 키 | 배지 전체 켜기/끄기 |
| `f` 키 | 피드백 모드 — 아무 요소나 클릭하면 메모창 |
| `?` 키 | 단축키 도움말 |

메모를 다 달았으면 우하단 **내보내기** 버튼 → 마크다운이 클립보드에 복사됩니다. 그대로 붙여넣어 주세요.

### 번호 읽는 법

```
P06-B21
│   │└─ 21번째 버튼
│   └── B = 버튼 (F 입력 · C 카드 · T 탭 · L 리스트 · G 차트 · S 상태 · N 내비)
└────── P06 = 실현 강도 선택 화면 (M = 팝업, A = 토스트)
```

번호는 **화면 안에서만** 매겨지고, 한 번 배정되면 바뀌지 않습니다.
화면이 추가돼도 기존 번호는 그대로입니다.

## 설계의 핵심 결정

### 1. 실현 강도 상/중/하 = 난이도가 아니라 **기간**

엔진이 먼저 생리적으로 가능한 **최단 기간 `T_min`** 을 찾고, 거기서 세 갈래로 나눕니다.

| 강도 | 기간 | 성격 |
|---|---|---|
| **상** | `T_min` | 가장 빠름. 식단 제약 최대, 근손실 위험 가장 큼 |
| **중** | `T_min × 1.4` | 균형점 |
| **하** | `T_min × 2.0` | 생활 유지. 중도 포기 확률 최저 |

각 카드에 **실제 달력 날짜**가 박히고, 플랜 화면에는 D-day와 주차별 궤적이 나옵니다.

### 2. 강도를 올리면 오히려 느려질 수 있다 — 숨기지 않는다

적자가 TDEE의 15%를 넘어가면 근육 증가율이 거의 0으로 떨어집니다.
그래서 **근육 목표가 병목일 때는 공격적인 계획이 전체 기간을 늘립니다.**
엔진은 공격성 `a ∈ [0,1]` 을 51개 지점에서 스캔해 이 역설을 찾아내고, 발견되면 경고로 띄웁니다.

또 리컴프 목표에서는 두 전략을 모두 시뮬레이션해 더 빠른 쪽을 고릅니다.

- **동시 진행** — 지방을 빼면서 근육도 늘린다 (적자가 작을 때만 성립)
- **분할** — 감량 → 유지 2주 → 증량 → 미니컷

### 3. 주차별 시뮬레이션

나눗셈 한 번이 아니라 주 단위로 상태를 전진시킵니다. 체중이 줄면 TDEE가 줄고,
체지방이 줄면 안전하게 동원 가능한 에너지 상한(`31 × 체지방량` kcal/day)도 함께 줄기 때문입니다.
이 덕분에 궤적 차트와 4주 단위 마일스톤이 그냥 직선이 아니라 실제 곡선으로 나옵니다.

### 4. 판독 검수 화면은 선택이 아니라 필수

OCR은 완벽할 수 없습니다. 프로토타입의 판독 스텁은 **일부러** 복부지방률을 `0.94 → 0.34` 로
잘못 읽고 무기질을 놓칩니다. 검수 화면(P04)이 그걸 실제로 잡아내는지 보기 위해서입니다.
정합성 검사(`체지방률 = 체지방량/체중`, `제지방량 = 체중 − 체지방량`, `골격근량 ≤ 제지방량`, `BMI`)도 함께 돕니다.

## 화면 구성

| ID | 화면 | 역할 |
|---|---|---|
| `P00` | 앱 셸 | 앱바 · 하단 탭바 |
| `P01` | 온보딩 · 프로필 | 성별/나이/키/활동수준/운동경력/제약 |
| `P02` | 홈 대시보드 | 최신 인바디 · 목표 진행 · 오늘 할 일 |
| `P03` | 인바디 업로드 | 촬영/파일/샘플/직접입력 + 판독 스텁 |
| `P04` | 판독 검수 | OCR 결과 확인·수정 (신뢰도 표시 + 정합성 검사) |
| `P05` | 목표 설정 | 목표 3종 + 실시간 실현가능성 |
| `P06` | 실현 강도 선택 | 상/중/하 = 기간, 각각 달성 예정일 |
| `P07` | 플랜 | 요약 · 운동 · 식단 탭 + 궤적 + 마일스톤 |
| `P08` | 주간 체크인 | 실측 입력 → 예상 대비 비교 → 재조정 |
| `P09` | 진행 추적 | 지표별 추이 + 예측 도달일 재계산 |
| `P10` | 히스토리 | 측정 기록 목록 |
| `P11` | 스캔 상세 | 개별 측정 전체 필드 |
| `P12` | 설정 | 프로필/표시/데이터/프로토타입 도구 |
| `P13` | ID 인덱스 | 고유번호 검색 + 피드백 목록 |

팝업 `M01`~`M25`, 토스트 `A01`~ 은 화면에 종속되지 않는 전역 번호입니다.

## 구조

```
prototype/
  index.html
  css/  base.css        디자인 토큰 · 컴포넌트 (라이트/다크)
        uid.css         고유번호 배지
  js/   data.js         시드 데이터 (오너의 실제 InBody270 + 운동/식품 DB)
        engine.js       플래닝 엔진 — 에너지 모델 · 주차별 시뮬레이션 · 강도 역산
        store.js        localStorage 상태
        ui.js           h() 헬퍼 · 모달 · SVG 차트 (라이브러리 없음)
        uid.js          배지 주입 · 복사 · 메모 · 내보내기 · 딥링크
        modals.js       M01~M25
        app.js          앱 셸 · 라우터 · 화면 레지스트리
        screens/*.js    화면별 모듈 (각자 자기를 등록)
docs/
  design/               설계 단계 산출물 (도메인 모델 · IA · 엔진 · 판독 · ID 체계)
```

의존성 없음. 빌드 단계 없음. 네트워크 요청 없음. 모든 데이터는 브라우저 localStorage에만 저장됩니다.

## 아직 안 된 것

- **실제 OCR** — 지금은 스텁입니다. 실제로는 비전 LLM에 이미지를 주고 구조화 JSON을 받는 방식이 가장 정확합니다 (`docs/design/photo-ingestion.md` 참고).
- **백엔드/동기화** — 전부 로컬입니다. 기기를 바꾸면 데이터가 안 따라옵니다.
- **알림** — 체크인 리마인더 UI만 있고 실제 알림은 가지 않습니다.
- **운동/식품 DB** — 검증에 필요한 최소량만 들어 있습니다.
